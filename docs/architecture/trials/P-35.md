# P-35

Batch: 2

## Question

Where does each check run's workflow file come from, and in what form? Can it be read as the `path` of the check run's check suite's workflow run, with the permissions the reader and the Controller hold, in the one read of the facts, and does that `path` ever carry a ref suffix or take a `dynamic/` form, which the port passes on verbatim, never as null? Does the check run `CodeQL` that GitHub Advanced Security reports have a workflow run at all? Where does a check run created through the API with `GITHUB_TOKEN` and `checks: write` land, in which check suite and under which workflow path, and can that token update a check run of another workflow's run? And does a job a pull request adds in a file of its own, under a required Lens's check name, report under GitHub Actions with that file's path?

## Pass

Each answered and recorded; the path readable within the budget P-8 measures; CodeQL's check with no workflow run; a check created with `GITHUB_TOKEN` under its own workflow's path and unable to change another's. **Failed** on 2026-10-31 (`trials/P-35.json`), on its last part. The reader's token reads the path in the one read (P-8); the Controller's half stands on that by ruling, since it holds every permission that read needs, and was not run. No path carried a ref suffix. A dynamic run's path is `dynamic/...` over REST only: GraphQL gives its file as null. CodeQL's check has no workflow run. A job a pull request adds under a required check's name reports with its own file's path. A check run a job creates with `GITHUB_TOKEN` lands in the first Actions suite on the head and reads with that suite's path, another workflow's where that is another's. It can be posted to another branch's head, from a branch with no pull request. The token cannot change another job's status, conclusion, name or `details_url`: the last two answer 200 and stay as they were. It can change its `external_id` and output title. So a job can post a check that reads as a Lens's own. Once the real check is listed both are read, and any failing one fails the Lens; but a job with `needs` has no check run until it starts, and until then a forged success stands alone and reads as passing. A created check's `details_url` stays `/runs/{id}`, and a real job's is `/actions/runs/{run}/job/{id}`, which the checks port is to require (issue 439, which gates the first approval). A job could not forge that form, on its own created check or at creation, with the id of the run its suite is in, or its own: each answered 200 or 201 and the details stayed `/runs/{id}`. That tell rests on those attempts and is no promise from GitHub (decision 0103)
