## Question

Under the Controller App's installation token, narrowed to contents: read and pull_requests: read on the canary alone, what do the two reads `adapters/branches.py` makes of a work branch answer: REST's pull request list filtered by head, `GET /repos/{repo}/pulls?state=all&head={owner}:{branch}&per_page=100`, and the branch's ref, `GET /repos/{repo}/git/ref/heads/{branch}`, for a branch whose one pull request the trial-author App opened and left open, closed unmerged, or merged with its branch then deleted; for a branch that stands with no pull request; and for a name no branch ever had? (issue 1075)

## Pass

The list of each of the three branches the App opened a pull request on is 200 with exactly one pull request: its `head.ref` the branch, its `head.repo.full_name` the canary, its `user.id` the trial-author App's bot account's whole number and its `user.type` `Bot`, which the port compares, in the state it was left in, and no `link` header naming a next page; the list of the bare branch and of the name never used is 200 and empty; the ref of the open pull request's branch and of the bare branch is 200, its `ref` `refs/heads/` and the branch, its `object` of type `commit` with a whole sha; the ref of the merged and deleted branch and of the name never used is 404; otherwise `adapters/branches.py` miscounts the Factory's pull requests or misreads a branch as absent (decision 0242's limit row). Recorded, deciding nothing: the ref of the closed pull request's branch, which the port never reads, since it reads only the branch past the last one the opener's pull request is on; and what a token narrowed to pull_requests: read alone is answered for the bare branch's ref; the canary is public, so a grant the token lacks may not show there (decision 0068), and a private repo is not asked. Limit: a pull request from a fork's branch of the same name is not asked, since no account the Maintainer holds can fork the canary (the Maintainer, 2026-11-25). The unfavourable answer is taken in its place: the head filter lists such a pull request. `adapters/branches.py` already reads a branch whose pull requests are none of the opener's, or hold the opener's from another repo, as not told, so a branch from a fork is never the Factory's (`tests/test_adapters.py::test_the_head_is_a_commit_no_branch_or_not_told_and_the_branch_is_named_from_the_factorys_pull_requests`). What it costs: anyone may fork a public repo, and a stranger's pull request from a fork named like an issue's next work branch defers that issue's opening, `branch_unreadable`, for as long as GitHub lists it, which is in every state, so the issue goes stale past its State's limit and a person decides; a filter that in fact leaves forks out costs nothing
