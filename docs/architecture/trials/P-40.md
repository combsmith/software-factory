# P-40

Batch: 2

## Question

When only the base branch moves, does GitHub work out `mergeable` and `merge_commit_sha` again, for a pull request that still merges cleanly and for one the move makes conflict, and how long after?

## Pass

Each answered and recorded. **Failed** on 2026-11-13, twice. The first run (`trials/P-40.json`, by REST; `trials/P-40.graphql.json`, by GraphQL) read two pull requests every 15 seconds for 5 minutes after one push moved their base: the one the move made conflict read null a second after the push's answer and false at the next read, 16 seconds after it, and never true; the one that still merged read true at every read and kept the `merge_commit_sha` it had before the move to the last, which is what failed the condition written first. GraphQL gave `UNKNOWN` for both a second after the answer and each worked out at the next read. The second run (`trials/P-40.at-once.json`) asked the first second alone, of a pull request the move made conflict: reads begun 0.06 and 0.61 seconds after the push's answer still gave `mergeable` true, as before the move; reads begun 1.22, 1.83 and 2.27 seconds after it gave null; and the read begun 2.80 seconds after it gave false. So a pass that reads in about the second after a base move may read a merge state that no longer holds, and nothing in the read says so. The snapshot's last read of the pull request now holds the merge state its first read gave, so a pull request whose first read gave a merge state, true or false, that its last read does not give is `pull_moved` (`adapters/pull.py`), as when its base moves into a conflict with it, unless the snapshot's last read falls in the stale second; a move of the base that leaves the merge state as it was is not seen: the snapshot reads the base's head once, and a move after that read changes nothing it reads; the Kernel changes nothing, the next pass reads the conflict, and the merge queue builds on the base it finds (decision 0214). `updated_at` did not move with the base, which the port had taken from P-29. Nothing in the Factory reads `merge_commit_sha`. `base.sha` did not move in either run (P-29). Apps installed on the canary commented on each pull request and edited its description while the runs read; none pushed to a head. The transitions explorer's move "the base moves" (`tests/test_transitions.py`) still makes `mergeable` unknown at once: a move that reads the conflict with no unknown between is issue 811. The simulator's fake models no move of the base, so no rule in `sim/grounding.py` names this trial. What the queue answers to an enqueue of a head that conflicts is not shown here: issue 812
