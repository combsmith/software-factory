# P-65

Batch: 4

## Question

When a pull request's run of a workflow is cancelled mid-way, does its check suite, and its workflow run, conclude cancelled while the run's judging job, which needs the cancelled job under if: always(), concludes failure; does the same hold for a re-run attempt, and for the run a close and reopen starts on the same head; does a push back to a head (A, B, then A again) start a new suite on A beside the cancelled one; and does the one GraphQL rollup read of a head's checks give each check run its workflow run's id and its check suite's conclusion?

## Pass

Yes: a cancelled run's check suite and workflow run conclude `cancelled` while its `if: always()` judging check concludes `failure`, so a head may hold a Lens's failed check beside a later run's passing one, each told by its suite's conclusion and its run's id, which the one rollup read gives (issue 681). **Passed** on 2026-11-11 (`trials/P-65.json`): on canary pull request 102, a run cancelled mid-way, a push back to its head (A, B, A), a re-run of the cancelled run and a reopening each behaved so: each cancelled run's suite on A `cancelled` (R1's suite was read after its re-run, which shares it, so its first attempt's was not read on its own), `p65 / work` `cancelled` and `p65 / verify` `failure`; the push back and the reopening each a workflow run and a suite of their own on A, beside the cancelled one's, which stayed; the run left alone `success`. A re-run keeps its workflow run's id and its check suite, with new check runs, which the jobs API tells apart by `run_attempt`, and the rollup gives only the latest attempt's. Asking each check run's `checkSuite` its `conclusion` and its `workflowRun` its `runNumber`, beside the `databaseId`, the run's id, which the port reads already, cost 1, as the port's own query does, so P-8's measure stands. For the Kernel's rule, three limits: a run's id, number and suite follow the order runs were created, and a re-run keeps all three, so none tells a later attempt from an earlier run (R1's second attempt ran after R3 concluded); a job stopped at its own `timeout-minutes` concludes `cancelled` too (P-42), so `cancelled` does not say a person or a group cancelled it; and each judging check concluded a second before its suite, which the reads, made after, did not catch. Every cancel was by hand; a concurrency group's was not tried. A re-run hides its earlier attempt's checks from the rollup, and the suite takes the latest attempt's conclusion
