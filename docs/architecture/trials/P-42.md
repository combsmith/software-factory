# P-42

Batch: 2

## Question

On a pull request's head: after a push, is every required check pending again; does a required check conclude `timed_out`, `neutral`, `skipped`, `cancelled` or `stale` and keep that conclusion until the content changes or a person runs it again; is every check run read with its exact name and its App's id, two workflow runs on one commit both staying, since `filter=latest` is per check suite; and can any App with `checks: write`, or any Actions job, post a check run under a required Lens's check name, or a result for any criterion of a contract, one the contract does not name among them, which then stays on that head?

## Pass

Yes to each, so the Kernel's reading of checks (§4.2) and of acceptance results (§4.8) holds. If a check run can be deleted or renamed on the head, the port reads check runs from each check suite's own list. **Failed** on 2026-10-28 (`trials/P-42.json`), in the canary, on `timed_out` alone: a job GitHub stopped at its `timeout-minutes`, in a run no one cancelled, concluded `cancelled`, and so did its check run and its run; no check concluded `timed_out` (issue 388). A step stopped at its own `timeout-minutes`, below its job's, concludes `failure`, and so do its job and check run, a later `if: always()` step still running (`trials/P-42.step-timeout.json`); `continue-on-error` on the step turns all three to `success`. The rest held: `neutral`, `skipped` and `cancelled` were unchanged an hour after the last post, with no push and no re-run; each check run carried its name and its App's id; `filter=latest` kept one run of a name in each check suite and `filter=all` every run, two suites on one commit both staying; the pr-review App and an Actions job each posted a run under a required check's name and an unlisted criterion's, and all stayed; after a push the new head's required check was in progress. `stale` was not seen. The status rollup the port reads, read on 2026-11-03 (`trials/P-42.rollup.json`): a required check read queued, then success with no one asking; the rollup held the same runs as `filter=latest`, by id, name, suite and App, four Apps among them; a re-run replaced its own run and the other suite's stayed, and gave the run's other jobs new check runs though they did not run again; and a later post of a name in a suite replaced the earlier one too, so a post in a required check's own suite would stand in its place (issue 496)
