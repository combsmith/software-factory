# P-47

Batch: 2

## Question

Can the reader App read a login's repository permission from `GET /repos/{repo}/collaborators/{login}/permission`, for an owner, a collaborator with write, one with triage and an outsider, and does the answer tell write access apart? And which of its grants does each read need, and the read of a branch's activity (`GET /repos/{repo}/activity`), which P-28 made as a person? Run by `tools/trial_reader_reads.sh` at the Maintainer's terminal with the reader's key, each read made twice, narrowed once to `metadata: read` and once to `contents: read`

## Pass

Yes: `admin` or `maintain` for the owner, `write` for the collaborator, `triage` for the triage role and `read` or `none` for the outsider; and the least grant each read needs is the one `config/apps.json` names for it (decision 0035). **Passed** on 2026-10-21 (`trials/P-47.json`): with each grant, `metadata: read` and `contents: read`, the reader read `admin` for the owner, `write` for the collaborator and for the machine user, whose `role_name` is `maintain`, and `read` for an outsider; and the activity of `trial/p-9`. GitHub's `x-accepted-github-permissions` names `metadata=read` for the permission read and `contents=read` for the activity read, and `config/apps.json` names each so: the canary is public, so the token with `metadata` alone read the activity all the same. GitHub's `permission` folds `maintain` into `write`; write access reads the same from it. The triage role was not tried: the canary has none, and the Maintainer chose to run without one
