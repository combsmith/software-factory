# 1145. A pass reads the repo before and after the issues that left

Status: accepted. Extends decision 0235 with its part 3 for "A Factory write on an issue that closes before the next pass is never reconciled: issues that left are read" (issue 916), the pass's read of the repo for the issues that left, as the Solution Architect ruled on 2026-11-21 (option A, read fail-closed) and the Factory Builder narrowed it the same day. The rows below restate 0235's where this part widens them; decision 0235 stands as it is.

## Decision

| What | Decided | Because |
|---|---|---|
| How one is read first | By REST's read of the issue itself. Closed, it is read as decision 0235 says, with its close. Still open, left out of the issues served, as when `issues.served_from` moved, it is read as an open issue is, with no close. Answered 404 or 410, it is whole with nothing more read, only where the same token read the repo itself, by its full name, with its issues on, before the issues that left are read and again after them, in the same pass, and where the pass listed the issues whole; it is then named once in the view as information, `issue_gone`, write `other`, its answer as the key. Any other answer is short: a 403, a 429, a 5xx, none at all, a body of another issue, of a pull request, or with no state | Reconciliation that stays short for ever hides the real alert. A 404 or 410 is the end of what can be read there, where the repo still answers the token and still has issues; where it does not, access, or the issues themselves, may be what was lost (the Solution Architect's ruling of 2026-11-21, option A, read fail-closed) |
| What cannot be told | GitHub answers 410 for an issue deleted where the token can read, and 404 for one deleted or transferred where it cannot: so a 404 is also an issue moved to a repo the token cannot read, and it ends as a deletion does. A transfer to a repo the token can read answers 301, which stays short: the transport follows no redirect for such a read and keeps neither its code nor its address, by design, so a 301 reads as no answer. An issue converted to a discussion stays short too: what REST answers for one is unverified. Telling both is "transport: keep a redirect's code so a transferred issue reads as moved" (issue 1095), with a trial | What cannot be told apart from a lost answer stays short (the Factory Builder's narrowing of the ruling, 2026-11-21) |

## Why

Decision 0235 reads an issue that left first by REST's read of the issue, and lets a 404 or 410 end it only where the same token read the repo in the same pass. This part builds that read: the pass reads the repo once before the issues that left are read and once after where one ended, so access lost between the two cannot pass for a deletion, and it tells what a 404 can and cannot mean.
