# 0157. An act's shim is the Run's but for its name and the file it calls

Status: accepted. The Factory Builder's rulings of 2026-11-07 on the plan for the shims of "Workflows: the frozen entry shim, the poller, the Run's three jobs and the nudge, each held to its shape" (issue 196). This is its PR A: the three shims that dispatch a Run, landed before the poller's, which is its PR B. It widens the row "Its shape" of `docs/decisions/0057-a-shim-calls-the-release-and-holds-nothing-else-and-the-poller-wakes-on-a-workflows-end-and-reads-nothing-of-it.md`, where run.yml alone names its run, to the three.

## Decision

| What | Decided | Because |
|---|---|---|
| The shims | run.yml, approve.yml and queue.yml stand on `main`. Each is held word for word by its template in `tools/check_workflows.py`, `RUN_SHIM`, `APPROVE_SHIM` and `QUEUE_SHIM`, with its dispatcher the account `config/controller.json` names for the pass's own token, and by its hash in `SHIMS` | A template states the rule and a mutant can break it. A hash freezes only what the Maintainer approved |
| An act's shim | approve.yml and queue.yml are the Run's shim but for their names, `sf-approve` and `sf-queue`, and the file each calls, approve-job.yml and queue-job.yml. Each has the same three required inputs, the same `if:` (the pass's own token, a first attempt, no Pause), the same lane, `${{ inputs.item }}`, cancelling nothing, and `actions: write` for its act's `wake` | One act on an item runs after another in the item's lane, as the Run's jobs do. Only the pass starts one, never under a Pause (decision 0003) |
| Its name | A shim that dispatches a Run, the Run's or an act's, names its run, `run-name: ${{ inputs.name }}`. Before, run.yml alone did. No other shim names its run | The records port reads a Run by its run-name. An act's Run named by its workflow alone would be unidentified for ever, and an unidentified Run defers every admission (decision 0036). Decision 0128 names each queue act by its run-name |
| Its caller | No file but approve.yml calls approve-job.yml, and none but queue.yml calls queue-job.yml, as none but run.yml calls the Run's jobs. A job that calls any of the three holds its item's lane | An act's job holds a key, and only the shim the pass dispatches may call it |
| Live, and inert | The three shims run only on a dispatch. The poller is not on `main` yet, and the `if:` refuses a re-run, a Pause, and any dispatcher but the account `41898282`. That account is every workflow's own token here, not the pass's alone: a dispatch is the pass's because no job of the Factory's files but `pass`, `wake` and `lane` is granted `actions: write`, and a person with write access can still push a workflow of their own that dispatches one, which that story's ruling 10 accepts. The act's step then reads the item again and acts only on what the Kernel still wants (decision 0055). queue.yml is dispatched only once `config/controller.json` names the queue App (decision 0128). The Factory Builder holds this PR until the repo's own `FACTORY_PAUSED` reads `true` | Nothing goes live here. The poller's PR is the switch, and it lands under that Pause |

## Why

The approving act ("The approving act: the machine user approves from a Run with no Engine, bound to the admitted commit", issue 195) needs approve.yml to stand, and the poller turns the Factory on. Landing the shims that only a dispatch runs before the poller gives the approving act its shim with nothing live, and leaves a small PR, the poller's, as the one that switches the Factory on. The check refused a run-name in any shim but run.yml, which would have left every approval's Run unidentified.
