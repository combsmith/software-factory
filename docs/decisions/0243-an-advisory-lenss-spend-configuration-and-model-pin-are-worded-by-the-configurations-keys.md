# 0243. An advisory Lens's spend, configuration and model pin are worded by the configuration's keys

Status: accepted. The Solution Architect's ruling of 2026-11-21, relayed by the Factory Builder, after the advisory Lens's parts were found to reword three rows of decision 0224's Decision, which an accepted record may not do: those three rows, The model's name, The configuration and Spend, read from here as this record words them. Each figure is named by its key in `config/harness.json` and the rule that holds it, never by its number, so that tuning a figure, as trial P-78 did a reader's output cap and its share of the step, needs no record. Decision 0224 stands in all else. The Maintainer may overturn it in review.

## Decision

| What | Decided | Because |
|---|---|---|
| The model's name | Each advisory Lens's model is pinned by its full id in its block of `config/harness.json`, under `readers`, which `tools/check_repo.py` lists as a second place a model is named, with its deployment, which Azure may name after a model; an answer that names another model is `not_the_model`. The pin is what the API answers, which may differ from the catalog's name for the deployment (trial P-75) | Decision 0147 keeps an answer only from the pinned model, for a deployment as for the CLI |
| The configuration | In `config/harness.json`, under `readers`, for each advisory Lens the Factory itself asks: `host`, `deployment`, `model`, `api`, `effort` for each of the two classes of change under Spend, `output_tokens` (its output cap), `prompt_characters` (its largest prompt, in bytes of UTF-8), `seconds` (the most one request waits), `share` (the seconds of the advise step its turn may take: a reader's turn runs until only the shares of the readers after it are left of the step) and `usd_per_million`, the prices of a million tokens in and out, above nought. Beside the advisory Lenses and never among a reader's own: `advisory_ceiling_usd_per_day`, the day's ceiling in dollars, and `advisory_worst_case_usd`, the worst case one read is counted at. Each is a figure to tune in the file, held by `schemas/harness.schema.json` and the checks named below; a new figure needs no record. That block and the reader's fixed instruction are a model Lens's inputs (decisions 0046, 0052; `config/hooks.json`) | They decide what `pr-review` is given to read, and how long and at what cost it is read |
| Spend | The effort is the configuration's `effort.critical` where the change touches the Kernel, security or a critical path, and its `effort.elsewhere` elsewhere. A daily ceiling in dollars, `advisory_ceiling_usd_per_day`, is held by the Controller's pass: it sums the day's advisory usage from the run records and hands the Run a yes or a no beside its Decision; on a no the step asks nothing and the Result is `incomplete`, `budget`. The figure is the Maintainer's to set, and with none configured no reader is asked. A read that was asked and whose Result gives no cost counts as `advisory_worst_case_usd`, never as nought, and that figure has no default and is no less than what the readers' own `prompt_characters`, `output_tokens` and prices let one Run cost, which a check holds. A review Run still running, whatever day it started, or one of the day whose advice cannot be read, counts the worst case, so that a read is not refused because another is in flight; the answer is no only when the day's sum and this Run's own worst case together would pass the ceiling. A Run that stays in flight takes one worst case off every day until it ends; the Factory's own limit of active Runs defers every admission before enough of them could shut a day. A review a pass told yes, one told earlier in the same pass among them, and whose Run no record lists yet, counts at the worst case too, as one in flight, whatever day it was told: each pass record carries those to the next until GitHub lists the Run, which from then counts as its own record says, the worst case where it wrote no advice, or until an hour passes, since a Run GitHub has not listed an hour after its yes was never dispatched and asked no reader; a Run GitHub lists that no run-name names counts so too; with the records before unread, no review is told yes for an hour. One thing is an issue: a reader's refusal that bills nothing counts its Run at the worst case (issue 933, "A reader's refusal that bills nothing counts its Run at the worst case, so refused diffs can shut the day's readers at no spend") | The subscription has no spend cap. At about 50 review Runs a day, the critical effort on every read would end the credit months before it expires. The step reads nothing from GitHub, so the count is the pass's, from what each Run recorded; it asks the Kernel nothing |

## Why

Decision 0224 was accepted with these three rows in the words of its first part, and each later part of the advisory Lens reworded one of them as it built what the row says: the pin under `readers`, the prices and the worst case, the in-flight count. An accepted record's Decision is never edited, so the final words are put here once. Naming each figure by its key, as the Solution Architect ruled, keeps the record true when a figure is tuned: trial P-78 found Kimi cut short at its output cap and Astra past its share at its critical effort, and the caps and the shares were changed in the file with no new record.

What is owed: the checks below arrive with the parts that build them, and each row names its check when its part merges.
