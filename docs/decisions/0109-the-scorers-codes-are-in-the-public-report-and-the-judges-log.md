# 0109. The scorer's codes are in the public report and the judge's log

Status: accepted. Replaces `docs/decisions/0078-a-held-out-case-is-reviewed-by-the-task-and-the-engine-a-live-run-and-its-report-tells-nothing-it-expected.md` and `docs/decisions/0099-the-eval-job-holds-a-sets-split-where-its-cases-are-since-the-repo-cannot-hold-the-counts-true.md`. The Maintainer's word of 2026-11-01, "Yes, publish the codes", given to the Builder's direct question, which said that this goes beyond his ruling that closed issue 430, "Evals: the public report's per-case verdicts can publish each case's kind", cannot be taken back, and shows each case's kind and the exact split. That ruling said the report keeps its reason code as 0078 has it, with no change to `eval-report/1`'s cases, and 0099 said 0078's one code stands: this overturns both on those points, and on nothing else.

## Decision

Eval run 41306021919 on the commit a1be0cf read 1 pass, 41 `case_failed` and 2 `diff_not_whole`, and nothing in the report could say why.

| What | Decided | Because |
|---|---|---|
| What the report says of a case | Its verdict and its codes: those that say why it was not read, and now the scorer's own, `result_not_completed`, `finding_not_raised`, `category_differs`, `severity_differs`, `location_differs`, `coverage_disagrees`, `finding_raised_wrongly`, `criterion_not_met`, `answer_disagrees_with_verdict`, `location_unreadable` and `criterion_unknown`. A case the scorer calls `unreadable` is `unreadable`, and no longer `fail`. `eval-report/1` lists these codes, and no longer lists `case_failed` for a case | 41 identical codes could not tell a reviewer that missed from a scorer asking for what no Result can give, and the next run costs about 42 model calls. The Maintainer's word above |
| The run's verdict | `verdict` still returns `case_failed` for any case not passed, and the Release's gate reads that as before: every case passed, or nothing | What moved is what a reader can see, never what passes |
| The judge's log | On `engine_fault` or `case_failed`, `judge` prints one line before its code: how many passed, and how many carry each code. Those two come only once `verdict` has held the report to its schema, so what reaches the log is the enum's codes, whatever wrote the report | The log is what a dispatcher reads first |
| What is public, and what is not | Each case's kind by its id, and the exact split, since `finding_not_raised` and the like occur only on a case that expects a Finding, and `finding_raised_wrongly` and `criterion_not_met` only on one that expects a criterion met. A kind told of an id tells nothing without the case's content, which stays in the private home, and the reviewer cannot use it, since its Task holds a fresh Run id, the diff and the facts, and no case id, and it runs with `--tools ""`. A case whose content reaches someone who should not have it is spent. No category, severity, location or diff leaves, and no word of the model's: `severity_differs` says the two differ and not what either is, and a Result is never kept, so a reader never sees what the model answered. A criterion leaves in one case: `criterion_unknown` tells which ids asked about a criterion a merged change took out of the rubric | The Maintainer's word above. It cannot be taken back: an artifact a dispatch uploads is public for 90 days |
| A short set | The refusal itself, `eval_split_short`, still says no count. A set whose cases fail says the split by the line above, before it reaches that refusal | A rule of 0099's, narrowed to what it can still hold |
| What the codes are for | Telling a fault of the scorer, the Task or the set from a fault of the reviewer. Case ids are stable across dispatches, so a prompt could be fitted to the set by watching them. No code here acts on that, and no check stops it: changing the prompt, the scorer or the set after reading the codes is the Maintainer's call, as the set is the spec | The design holds a scenario unseen by its author |
| What was found first | Canary run 41307506047 ran the repo's two example cases three times each. The case expecting `met` on PR-1 failed all three, `criterion_not_met`: the model says `not_applicable`, `no_issue_or_contract_provided`, since a Task holds the diff alone, as `harness/read.py` says, in a live Run as in a case. The case expecting a Finding on PR-3 failed once, `finding_not_raised` and `coverage_disagrees`: it raised the Finding and cited no criterion. So the scorer reads a real Result correctly. No scorer, prompt or set change is made here | The mix of the 42 is unknown, and these codes will show it |
| The Task | A case's Task is built by `from_admission` in `harness/task.py`, the function `task.build` builds a live Run's by once it has read the admission from the pass record. The admission is the case's own: its Role and Intent, and the content its facts name. The Task is given the case's facts and its diff, the checkout's `roles/pr-review.json` and configuration, no texts, no Findings, and a fresh Run id. Its Release is the one the dispatch names, held by `plan` | What is measured is what runs (design §3.14). The first amendment made the dispatch name the Release, so the Task carries that and not the commit |
| A case that is no Run's | A case whose facts do not name the content its diff is, the sha256 of the diff, or whose facts are no pull request's, builds no Task. It is `unreadable`, `not_this_set`, and nothing is asked of the model | The third amendment: a case's `content_id` is its diff's, as a live Run's is, so the diff reaching the model is the content the case stands for |
| The answer | Each Task is answered by `answer` in `harness/run.py`, the function the `run` job answers a live Run's by: a diff the Task cannot carry whole, or a rubric that cannot be read, fails before the CLI starts; otherwise the Engine runs it at the pin, with the tier's limits, `--tools ""` and the scrub. The Result is scored in process and never written | One path, so a fault of a live Run is a fault of a case |
| Time | The job runs on `ubuntu-24.04`, the runner the CLI's install is for, with a timeout of 120 minutes, both held by `tools/check_workflows.py`. The time is counted from when `plan` was made, which it records by the runner's clock, so the fetch and the install spend it too: no case is started after 110 of the 120 minutes, nor once less time is left than that case's tier allows and the Engine's two reads of the CLI's version, and a case it does not start is `unreadable`, `unanswered`. The run fails, and does not hang | Ruling 9: a shorter timeout would end the job before the report is uploaded |
| A case's own fault | A case the review cannot be asked of is `unreadable` by its code; whatever else the review raises on a case is `unanswered`. An interrupt, a cancel landing during a case, asks nothing more: that case and every one after it are `unanswered`, the report is written, and the step prints one code. A cancelled run uploads nothing, since GitHub skips the upload, and it can pass no gate, which needs a run that succeeded; the upload is held without a condition of its own The report of every case is written all the same, so the upload finds it and `judge` fails the run | Ruling 4: the report is always uploaded |
| The steps | `plan`, the CLI's install, `fetch`, `run`, the upload and `judge`, in that order, as `docs/decisions/0106-a-fault-of-the-engine-is-never-the-reviewers-the-scrub-needs-bubblewrap-and-a-check-runs-the-engine-end-to-end.md` set them | apt runs as root, so the install comes before the token is used and before a case is on the disk |
| The CLI | `.github/workflows/eval.yml` installs the CLI before `fetch` by the block the Run's jobs install it by, word for word, given the Engine's pin in `config/harness.json` and its checksum in `CLI_CHECKSUMS`. The `run` step names the CLI's path beside the model's credential, and nothing else | The CLI a case is answered by is the CLI a Run calls |
| What runs beside both credentials | The vendor's CLI now runs in the one job that holds the held-out token and the model's credential, in separate steps: held by its sha256 at the pin, installed with the runner's own passwordless `sudo`, and given the model's credential alone. Decision 0053's list of what runs in that job, the pinned actions and this repo's code, gains it | The CLI must be the one a Run calls, and a Run's job installs it the same way |
| What reaches the CLI | The Engine's environment is its fixed names and the model's credential alone: nothing of the held-out home, its token or where it is, though the step's process holds what the runner gives every step | The scrub (decision 0050), held by a case's test |
| Verified on GitHub | Not here. Once this is on `main`, a dispatch from another branch is refused by `factory-eval`'s deployment branches, and a dispatch on `main` reads the home and uploads a report of hashes, verdicts and codes alone. A platform trial records both, its fixture holding hashes only. Then the story is done | Ruling 13: no session holds the home's credential, so the job's own runs are the evidence |
| The cost | Each dispatch spends one review-tier call for each of the set's cases, on the Factory's model credential, and the Maintainer dispatches it before a cut | Ruling 9 |
| Where a set's split is held | In the eval job, where the cases are: `harness.eval.split_ok` reads the verdict each fetched case expects, and the set must hold `KIND_LEAST`, 20, of each kind, the split of issue 183, "The review Intent's held-out eval set, from the proof of concept's merged-then-reverted pull requests" | The job is the one place that may read a case. Read there, each run, the split cannot drift from the set |
| What the repo holds of a set's kinds | No count, in place of the counts the first of those issues' checklist asks the manifest to hold. The manifest stays as it was, its count and each case's id and hash, and the review Intent's set is held to 40 cases at least by the test 0010 names | The check belongs where the cases are, and the repo cannot hold the counts true: a session here cannot read a case, so a count written here could only be taken on trust |
| What the report says | `eval-report/1` takes `split_ok`: true, false, or null where a case was not read or its answer is no kind. It holds neither count | The gate needs one word of the whole set, and nothing more |
| How it closes the gate | `harness.eval.verdict`, which the job's `judge` and the Release's gate both read the report with, refuses a report whose `split_ok` is not true, as `eval_split_short`, a code alone, after every case's own verdict. So the run fails with the code, its report uploaded all the same, and the gate is closed twice over: `adapters/candidate.py` takes only a dispatch that concluded `success`, and then reads the report by `verdict` | The gate reads the verdict's word, and a report is uploaded whatever the verdicts, so the word itself must refuse |
| What was public | The review set's split stood on pull request 413, "Evals: the job holds a set's split where its cases are, and no count of a kind is public", for a time, and can still be read in its history. That is harmless for the same reason, and nothing follows from it: a change to the set need not give its cases new ids | On that reading, 0094's rule that the next change to the set re-ids every case protects nothing, so the Factory Builder withdraws it |

## Why

The eval is the Factory's one measure of its reviewer, and it had come to say only that the reviewer failed. A case is reviewed by the two functions a live Run uses, so that the set measures the Run the Release ships, and the split is held in the job because that is where the cases are. Both stand. The one thing that moves is that the report can now say why a case did not pass. The rows above are 0078's and 0099's as they stood, word for word, but for those this overturns and the two on the steps, which 0106 had changed.
