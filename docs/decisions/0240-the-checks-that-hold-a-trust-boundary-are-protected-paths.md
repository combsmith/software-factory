# 0240. The checks that hold a trust boundary are protected paths

Status: accepted. The Solution Architect's rulings of 2026-11-20 on "A workflow on push beside a secret is not held to the base, and the check that holds workflows is no protected path" (issue 907) and on "Inputs that can blind the protected checks without touching them" (issue 1048), relayed by the Factory Builder.

## Decision

| What | Decided | Because |
|---|---|---|
| Which checks | `tools/check_workflows.py`, `tools/commits_are_the_maintainers.py`, `tools/check_writes.py` and `tools/check_repo.py` join `config/hooks.json`'s `protected` list, each at its own path | Each holds a boundary a Role's push could otherwise move: what a workflow beside a secret may read of a head, that every commit a pull request carries names the Maintainer, that only the callers it lists reach a GitHub write, and that nothing is installed or fetched and no secret written down (the Factory Builder's ruling, adding the fourth on Astra's and Kimi's reads). A push that edits one can blind it to a later change, though the edit exposes nothing by itself |
| The principle for what else joins | A file joins when its only job is to decide whether a protected check runs, what it reads, or its verdict: one hop from the four checks, and no further | Such a file blinds a protected check with one small, ordinary-looking edit and never touches the check. A file with other jobs, or two hops away, is edited by ordinary lane work, and a prompt on each edit would cost more than it guards |
| Which files, by that principle | `tools/verify.py`, the list of checks `make verify` runs; `tools/walk.py`, the files `check_writes` and `check_repo` read; and `tools/needs_passed.py`, the required check's verdict on the jobs it needs, join the list too, each at its own path | Dropping `check_repo`, `check_workflows` or `check_writes` from verify's list stops it running; a walk that leaves out a module hides any write or fetch in it; and the verdict decides whether the checks' failure fails the required check at all. The verdict and the commits' check run from the base, so for those two the list guards what later pull requests are judged by, which is this risk (the readers of the change that protects the four checks) |
| The same paths, by another name | A package at each of the seven names, the directory beside each module, named as it is without its suffix, joins as a directory; so do `tools/__init__.py`, the package the checks are imported from, and `Makefile` and `GNUmakefile`, which decide whether `make verify` runs the checks at all (the Factory Builder's ruling, within the principle) | Python imports a package in place of a module of the same name, and `python3 -m` runs its `__main__`, so a new package blinds a check as an edit of it would; `tools/__init__.py` runs before each check; and a `verify` target that does nothing, or a `GNUmakefile`, which make reads first, stops every check `tools/verify.py` lists, which is that file's job one step out. A compiled module beside a check, which Python would load first, is already refused by `tools/check_repo.py` (the Claude review and the security read of the change) |
| What follows | `apply` refuses a Role's push that changes, renames or copies one (decision 0188), a session is asked before an edit, and a change to one is read by every model Lens. Each stays an input of `verify` | The checks are a person's to change, as the workflows and the protected list already are |
| What stays | The other files under `tools/` stay `verify`'s inputs, pushed and read by every Lens, `tools/check_authority.py`, `tools/check_lifecycle.py` and `tools/check_purity.py` among them | Those are edited often by ordinary lane work, and a prompt on each edit would cost more than it guards; each is still read by `verify` and every model Lens's review |
| The limit: the transport | `adapters/github.py` is left out, though `tools/commits_are_the_maintainers.py` reads the pull request through its `Live` and `request` | It is the one transport for every port, edited by most changes that reach GitHub, so a prompt on each edit would cost more than it guards. A behaviour guard stands in its place: a test that the commits' check refuses a pull request when the transport's read fails or answers in another shape, with a mutant in the transport that the test kills |
| The limit: one hop | The list covers one hop from the four checks, not every module those files import: a check `tools/verify.py` imports for its own sake, such as `tools/check_context.py`, runs in the same process and so could reach a protected check, and it is not protected | Following every import would protect most of `tools/`, which ordinary lane work edits, and a prompt on each edit would cost more than it guards. Each such module stays an input of `verify`, read by every model Lens's review |
| The limit: a module of the standard library | A file or package at the top of the repo named as a module of the standard library, such as the one the checks parse with, is not protected, though `make verify` runs the checks with the repo's top first on Python's path, so it would be imported in place of that module | Every name of the standard library would have to be listed. The way to close it is to run the checks in Python's isolated mode, with the repo's top after the standard library: "verify takes its verdict from the checks' own exit, run isolated and apart from the tests, so a test module cannot turn a failure into a pass" (issue 1050), not the list |
| The limit: the tests run in the checks' process | `tools/verify.py` imports every test module in the process that ran the checks, so a test module that ends the process at import can turn the checks' failure into a pass, and the tests are not protected | Protecting the tests would ask a person on most changes. The fix is to run the checks in a process of their own, isolated, and to take the verdict from their exit alone, which "verify takes its verdict from the checks' own exit, run isolated and apart from the tests, so a test module cannot turn a failure into a pass" (issue 1050) owns as a change to `tools/verify.py` and the workflow, both protected |
| When | After decision 0225's pull request merges, so that it is not asked again mid-flight | A protected edit asks for the Maintainer's approval |

## Why

Decision 0225's limit row named `tools/check_workflows.py` as no protected path, read by `verify` and every model Lens's review and not refused; this changes that part of it alone. 0225 held a workflow on `pull_request` beside a secret to protected settings or the base, and named its own check as no protected path, a limit. The security read of 0225's pull request found that the check could be edited by a Role's push and so blinded; the Solution Architect ruled that the checks that hold a trust boundary are a person's. The readers of that change then found files a push could edit to blind those checks without touching them, and the Solution Architect ruled which of them join, by the principle above.
