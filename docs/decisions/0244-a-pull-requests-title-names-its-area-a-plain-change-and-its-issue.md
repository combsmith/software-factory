# 0244. A pull request's title names its area, a plain change and its issue

Status: accepted. The Solution Architect's ruling of 2026-11-21, relayed by the Factory Builder, on the readability lane's proposal for "tools: check that pull request titles keep the plain style" (issue 1089). The Maintainer set the style on 2026-11-21. This record makes its mechanical half a rule that a check holds.

## Decision

| What | Decided | Because |
|---|---|---|
| The rule | A pull request's title is `area: plain verb phrase (#issue)`. The area is a lowercase word of letters, digits, dots, slashes, dashes or underscores, then a colon and a space. The phrase starts with a lowercase letter, a to z, and ends with no full stop, comma, semicolon, colon or space. The title ends with the issue, ` (#N)`, or with a stacked part, ` (#N, part K of M)`, where 1 <= K <= M, M >= 2 and neither has more than four digits. The issue is required. The title is one line, with no tab, line end or other control character | The squash commit takes the title as its subject, so the title becomes main's log for good. A title that names its area and its issue tells a reader of the log where the change sits and why it was made |
| The length | At most 72 characters, counted on the title as GitHub holds it. The ` (#PR)` that GitHub adds to the squash commit is not counted | The Maintainer asked for about 70. His own example is 72, so 72 is the one limit |
| A name from inside the code | A backtick, two characters joined by an underscore, a record's or decision's number, a trial's number (`P-` and digits, in either case) and a schema's name and version (a lowercase word, a slash and digits) refuse anywhere after the area | These are the marks of a term a newcomer cannot parse, and they can be told without judgment. The area may hold an underscore, since it names a place in the repo. The schema mark also refuses a lowercase protocol such as http/2; written as HTTP/2 it passes |
| What is judgment | Whether the title names one change, whether "and" joins two changes, and whether its words are plain to a newcomer. No check holds these; the reviewers judge them. A rubric criterion for the Factory reviewer may come later, as a hand pull request, once there is data | A ban on "and" would refuse noun pairs that are one change. Readability for a newcomer cannot be told from the text alone |
| Where it is held | `tools/pr_title.py` holds the whole rule. `tools/commits_are_the_maintainers.py` makes one call to it from `main`, so the `commits` job of the required check runs it from the base, and the workflow does not change. The two concerns stay apart: the commits check holds trust and the title check holds style | The `commits` job already checks out the base, reads the event and holds a read-only token. A change cannot make its own title pass. A failed required check sends the item back to its author before any review (`kernel/derive.py`), when a retitle costs nothing |
| How the title is read | From GitHub, by the pull request's number, on both events: on a pull request, the number its payload names; on a merge group, the number the queue's ref names. Never from the payload's title | A re-run of a job reuses the payload it was first given, so a title edited after a failure is read again only from GitHub. The merge group reads the title the squash commit will take |
| What cannot be read | A title that cannot be read refuses with its own code, `title_unreadable`: no event, no number, no token, no answer, another status, another pull request or another repo's, or a creation time that is no real moment. A pull request opened before the cutover needs no title at all; one opened after it needs a title that is text | A check that passes what it could not read holds nothing. So a pull request's run now asks GitHub once, and an outage there turns the `commits` job red until the job is re-run |
| The cutover | A pull request opened before 2026-11-22T00:00:00Z, by its `created_at`, is not read. That includes every pull request approved before the cutover, which stays out of scope | A title cannot be edited once its pull request was ever approved: the fix is to close it and open it afresh. The style was announced on 2026-11-21, so a pull request opened from 2026-11-22 was opened knowing it |
| What is printed | A rule's code, the characters' positions and numbers that the rule itself read. Never a word of the title | The title is text from outside, and the job's log reads a line that starts with `::` as a command. A title must not write one |
| The desk | `python3 -m tools.pr_title "TITLE"` prints the same problems, so that an author can check a title before opening a pull request | Fixing a title before opening is cheaper than a red check |
| Titles made by something else | GitHub's revert button opens a pull request titled `Revert "..."`. It is held: the Maintainer retitles it, for example `revert: undo the push guard (#N)`. A dependency bot is not on `config/hooks.json`'s list of openers, so it is refused by who opened it and not by its title. `.github/workflows/release.yml` opens no pull request. Once a record adds the Factory's App as an opener, its opening Run's title is held too, and that Run's prompt must teach the style first (decision 0238 bounds that title) | A title that becomes main's log is held whoever made it. Where something else makes the title, the person who opens the pull request can change it |
| The limit: a reopened pull request | A pull request opened before the cutover keeps its `created_at` when it is reopened, so it stays out of scope after a reopen | Only an account on `config/hooks.json`'s list of openers can reopen one, and today that is the Maintainer alone. The record that adds the Factory's App as an opener weighs an end to the exemption |
| The limit: a title edited after it was read | The title is read when a pull request's run starts and when its merge group's run starts, and verify.yml runs on no `edited` event. A title edited after a green run is not read again until the next push or the merge group. If a review approves it in between, the merge group refuses it, and the pull request must be closed and opened afresh. A title edited after the merge group read it, and before the squash, is not read at all | Any account with write access to the repo can edit a title, not only its opener, so the window is open to every writer; a title missed this way costs main's log one line and never a trust check. The desk's command checks a title before it is written. Adding `edited` would run the whole required check again on every title edit |
| The limit: what can blind it | `tools/commits_are_the_maintainers.py` imports this check and runs it in the same process. An edit merged to `tools/pr_title.py` could therefore end that process early and blind the commits check for every later pull request | Decision 0240's principle covers it. `tools/pr_title.*` joins the protected list beside the commits check, in decision 0240's change if that change can still take it, and otherwise in the next change to that list |

## Why

The style lived only in the lanes' desk notes, and AGENTS.md accepts only rules that a check holds. The mechanical half can be told from the title alone, and the required check already has everything it needs to read the title: the base's tool, the event and a read-only token. Holding it there costs no workflow edit and catches a title before review, when changing it is still allowed. The half that needs judgment stays with the reviewers.
