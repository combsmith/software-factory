# 0193. When a Run began is read from its jobs, trusted only once a job is in progress or ran, and kept by the pass records

Status: accepted. The Factory Builder's ruling of 2026-11-11 on issue 724, "A record's start is read from its job's started_at, trusted only once the job is in progress or ran (P-64)". It adds one field to the run record and one read to the records port. The pass's keeping of what it read, `begun` and its hand-over, is the pull request that follows this one, and adds its rows below. No rule of the Kernel reads the field yet: the record that has `approval_anchor` read it follows, and closes the residual `docs/decisions/0168-the-simulators-world-dates-an-approval-by-the-acts-run-and-the-kernels-anchor-takes-the-records-always.md` names.

## Decision

| What | Decided | Because |
|---|---|---|
| The field | `began_at`, optional on a run record. `started_at` keeps its meaning, the run's `run_started_at` | The issue asked that `started_at` become the job's start. `controller/pass_.py`'s windows and the kept outcomes' key read `started_at`: a Run that never began, read as starting now, would hold an automatic pause at every pass, and its outcome would never be kept |
| What it says | The earliest `started_at` among the jobs GitHub lists for the run's latest attempt that are `in_progress`, or `completed` with a runner named. A re-run may list a job an earlier attempt ran, with its start, earlier than `started_at`: a start of the same run, and no job of a Run made while another of its item ran began before that one ended. Null for a completed Run whose jobs are all completed and none began. Absent where it has not begun yet, or was not read | `trials/P-64.json`: while a job waits, `pending`, the jobs API gives its creation as its start, as `run_started_at` is the run's creation; in progress, the start is when it began. `trials/P-44.json`: a job cancelled while it waited ends completed with no runner. A Run's jobs stand behind one lane (`trials/P-55.json`), so the first to begin is when the Run left it |
| What is asked | `GET /repos/{repo}/actions/runs/{id}/jobs`, as P-64 asked it, uncached, for each Run in progress or completed, and only for a caller that asks (`began`) | A queued Run has no job begun. A caller that does not ask reads as before |
| What is kept | `begun` reads the last two pass records, the earlier's word only for a Run the later does not list: a time for any Run, null for a completed one, by its Run id and when its attempt started, as outcomes are kept. A re-run, a row that names no start of its attempt and a key listed twice are asked afresh | A job's start stood at every read after the first that gave it (P-64), and a completed run's jobs change no more. So a Run is asked from when it is in progress until it has begun, and then no more |
| The cap | No more than 50 Runs are asked in one read (`JOBS`). A Run past the cap has no `began_at`, and the list is not whole | 50 is what a pass reads of passes and of Effects (decision 0190), inside its step's limit. With nothing kept, N Runs are read over N/50 passes, each of which defers every Run; on 2026-11-11 the Factory's repo held 27 |
| Jobs that cannot be read | An answer that is not 200, or no list of every job counted, each once; a job of another attempt than the list gave; a job in a status GitHub gives none; a start that is no time; a job not yet completed of a run the list gave as completed, begun or not. Each gives no `began_at` and leaves the list not whole | What cannot be read is said, never guessed. An answer older than the list would otherwise read a Run whose job began and ended inside it as never begun, for good |
| What does not read it yet | No caller asks yet. The pass asks, and keeps, from the pull request that follows this one; the Harness's two reads ask for their own item's Runs from the one after, a person's to approve; the Kernel's reading follows both | A Run reads its item as the pass does. Were the Kernel to read the field before both ask, one reading would lack what the other has |
| The residual | A job outside its item's lane that began before the lane's would give a start that is too early. The Run P-55 recorded has none | The jobs API does not say which jobs a concurrency group holds |
| A completed Run that lists no job | Null, kept for good | Read as unreadable, it would leave the list not whole at every pass. Null admits nothing |

## Why

`run_started_at` is when a run was made. A Run made while another of its item ran waits in the item's lane, and its record says it started when it was made. Decision 0168 names what that leaves open. P-64 asked GitHub when a job that waited began, and it answered: only once the job is in progress, or completed with a runner.
