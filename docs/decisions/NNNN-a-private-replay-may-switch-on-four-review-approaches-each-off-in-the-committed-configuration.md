# NNNN. A private replay may switch on four review approaches, each off in the committed configuration

Status: accepted. The Factory Builder's rulings of 2026-11-10 on issue 581, "The review Role's recall on planted faults": the design of lane d, its merge rule with coverage refined for a pass per file and held to what a kept Finding cites, one replay of each approach first, and one pull request of switches, all off. Each approach the issue names is to be measured by a private replay at the Maintainer's terminal against the same commit without it. This record makes each one switchable in a replay's own copy of the configuration, and changes nothing a live Run or the gate is asked.

## Decision

| What | Decided | Because |
|---|---|---|
| The switch | `config/harness.json` may give a `review` block: `passes` (`whole` or `per_file`), `runs` (1 to 3), `checklist` and `read_head` (true or false). The committed file gives none, and none is the defaults: one pass, once, told what a review is always told. A block that is not an object, has any other key or value, or switches on more than one approach at once, is refused before anything is asked, never read as something else | A replay copies the repo at a commit and changes its own copy of this file, as it already does for effort and limits, so one command measures one approach against the same commit |
| Where it acts | `harness/run.py`'s `answer`, the one function that answers both a live Run and a held-out case, reads the block for a reviewing Intent alone. Every call it makes is the call it always made, through `engine.run`; each call after the first is a session of its own | So a replay measures exactly what a live Run would do with the switch on |
| A pass per changed file | `per_file` asks one Task per changed file, the diff cut at each file's header and the head left whole, and joins the answers. Each pass is told, after its instructions, that it judges that file alone and which other files are judged in passes of their own, so that it neither answers `incomplete` for them nor judges the whole change on one file. A change of one file, of more than eight, or with a path git's header does not give whole and plainly, is asked whole | A fault in a file read late is not crowded out; the bound keeps a replay's cost per case in sight |
| Union across runs | `runs` asks the whole Task that many times and joins the answers | A true union, as ruled: what it costs on the clean cases is what the replay is to measure |
| The bound | One approach at a time, so a case makes at most eight calls (a pass per file) or three (union), each held to its tier's time and ceiling. The eval job starts a case only with time left for every call it will make, and their reads of the version | So a replay's cost per case has a bound, and a case started late is unanswered, not cut short |
| A fault checklist | `checklist` tells the review, after its rubric, the fault kinds each criterion covers, from `roles/pr-review/checklist.json`, and asks it to weigh each before it judges a criterion met. The file holds to `checklist/1`, names the Role and the Intent and only criteria of the rubric, is among the Role's own files and so a model Lens's input, and is written from the rubric's statements alone, never from a replay's output or a case. A checklist that cannot be read, of another Role or Intent, or naming a criterion the rubric does not, is `rubric_unreadable` | The rubric and its digest stay as they are, so the gate's identity of the review is unchanged |
| Reading the head first | `read_head` tells the review, after its instructions and so after the head's note, to read each changed file at the head around each hunk before it judges a criterion met. Nothing can enforce the reads; the replay measures whether the words move recall | The head is already readable (decision 0138) |
| The merge rule | Findings on the same path with lines that overlap are one, whatever each cites; the one most of the answers agree on by criterion, severity and category is kept, agreement counted by answer, not by Finding, and the earliest on a tie. A Finding elsewhere, or with no lines, is kept whole. Each kept Finding is posted once, as its own answer posted it, renumbered; a kind of Effect is posted only where a kept Finding is posted by it, or, where no Finding is kept at all, as the first answer posted it. Dispositions and Effects of any other type are the first answer's. A criterion is joined only where every answer covers it, counted by answer and not by row, not applicable counting as covered, one any answer leaves out left out, so that another file's word never stands for a pass that gave none. It is a finding where a kept Finding cites it; otherwise, of the answers' other words, met where one judged it met and every other met or not applicable, met too where no other word is left, every Finding that cited it merged into one kept at its place under another criterion; otherwise as the first of those words says. Usage is summed, each count of it, none where any call counted none. The joined Result is completed only if every call completed, and is otherwise the first that did not, by its own reason; one that does not hold to its schema is `result_invalid` | Decision 0160 fails a case with two Findings at its place, so a union that kept both would score a fault found twice as worse than found once. A criterion called a finding with no kept Finding citing it would leave the joined Result uncovered, and `apply` would refuse it whole (`kernel.coverage.covered`), so the replay would score what a live Run could not post. A pass of one file rightly calls a criterion of another file not applicable, and that must not hide the pass that judged it met |
| What is unchanged | The committed configuration, every live Run, the gate, the rubric, the Role's prompt and the eval report's identity of the review. An approach is kept only by its own pull request, which turns it on in `config/harness.json` and ships with a full replay at its head, as the issue asks | Measuring is not deciding |

## Why

The issue names four ways the review might find more of the faults planted in its cases, and asks that each be measured against the same commit without it. A replay at the Maintainer's terminal can only measure what the code can be told to do, so each approach is code that is switched off until a replay's own copy switches it on. Keeping every switch off in the committed file means building them changes nothing a pull request meets.
