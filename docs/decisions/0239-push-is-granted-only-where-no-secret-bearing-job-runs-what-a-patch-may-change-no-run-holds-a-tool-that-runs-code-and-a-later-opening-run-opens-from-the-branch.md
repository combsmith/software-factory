# 0239. Push is granted only where no secret-bearing job runs what a patch may change, no Run holds a tool that runs code, and a later opening Run opens from the branch

Status: accepted. The Factory Builder's rulings of 2026-11-20 on "Record 0219's secret-check boundary can't be held by push.py's list, its no-tool rule has no boundary, and its opening recovery wedges a later Run" (issue 952), which the reader audit of 0219's squash commit found once it had merged without the desk's readers, and his rulings the same day on the questions this record's first draft raised. It amends decision 0219's rows "What is left", where its last two sentences hold a secret-bearing check to the files a patch may change, and "Who opens the draft", where it says the next opening `apply` finds the branch at the handed-over patch's commit, by its digest; and 0219's Boundary rows on `qa-lead`'s opening Run and on a branch whose checks run with a secret stand amended by the rows below. The rest of 0219 stands.

## Decision

| What | Decided | Because |
|---|---|---|
| Where the secret clauses are held | Before a repo is granted `push_commits`, its base's workflows are read. At each push, right before `push_commits` is used, they are read again, and so are the workflows at the commit the patch lands on, the work branch's head: a job `on: push` runs the pushed branch's own copy, which can be an older base's that still holds a secret, and a secret-bearing workflow a person adds to the base between passes stops the next push. They are read again right before `open_pull_request` and `mark_ready`, after a push and on the recovery below alike, since opening a draft and marking it ready start the `on: pull_request` jobs that run the item's code, and both are refused on the same terms. At each of these, everything else the grant reads, below, is read again as well, since an outside builder installed after the grant would otherwise run the next push. And before each opening and mark ready, the files the work's commits change are held to decision 0188's list as the current base has it, as a push's are, and a file among them that the base has renamed or removed since the work's parent refuses it too, since the change would merge into a name the list may hold: a person can add a file to the list after the push. A job holds a secret where it names one or reaches them whole, by `secrets: inherit` or by `secrets` itself in an expression, and also where its `GITHUB_TOKEN` has any write permission, by the job, the workflow or the repo's default, or where it has `id-token: write`. A repo is not granted it where anything this read cannot see builds or reports on its branches: a job that calls a reusable workflow from another repo, a required check that is not a workflow it can see, such as an outside CI App's check, a workflow an organisation ruleset requires from another repo, or code scanning's default setup; any other check, status or deployment that reports on its branches from outside its workflows, such as CircleCI or a Vercel or Netlify preview; or an installed App that builds its branches. What such a system runs, and with what secret, cannot be read. A repo where, in either set, a job that holds a secret runs a file a Factory patch may change, its tests among them, or takes its configuration from one, is not granted it, and a push to it is refused: a required test job that holds a secret and runs `python3 -m unittest`, or a scan that reads `sonar-project.properties` from the head beside `SONAR_TOKEN`, as `.github/workflows/sonarcloud.yml` does here ("Security: the SonarCloud scan reads a pull request's sonar-project.properties beside SONAR_TOKEN, and no list protects the file", issue 845). A file such a job only reads as source to analyse is not such a file. The rule is read from the workflows, never from the files a push touches: the refusal of a push that touches the base's list, which `harness/bundle.py` holds (decision 0188), stands, and holds no secret clause | No list of files can keep a patch from the code a job runs, which 0219's own "What is left" says; and a check of the push's files let through a push that touches only `README.md`, which the clause, worded on the branch, forbade |
| What it costs | This repo is not granted `push_commits` while its scan reads `sonar-project.properties` from the head, so the Factory writes no code here until the scan reads the file from the base or the file is on the base's list. A Consumer whose secret-bearing job runs its tests, or whose branches anything the read cannot see builds or reports on, is not granted it until that changes; the Factory reviews there and writes nothing. Each push, opening and mark ready spends a read of the base's workflows and of the branch head's, and of what else the grant reads | Named, as the price of holding the rule where it can be held |
| No Run holds a tool that runs code or writes | No phase of any Role is given a tool that runs code or writes: no `Bash`, `Write`, `Edit` or the like. The Engine alone names a Run's tools, from its Task, by `--tools`, the flag that restricts them, in its one call of the CLI: a review and a Run that writes code are given exactly the read tools, `Read`, `Grep` and `Glob`, held to a head (decision 0138), and any other Run none. `config/harness.json` and each Role's manifest are what their schemas allow, and name no tool or argument of the CLI | 0219 decided it, and no Boundary row held it: a phase given `Bash` passed every check 0219 named |
| No job of a Run runs the item's code | In a Run's workflow, `.github/workflows/run-jobs.yml`, and the approving and queue acts', each checkout names its ref, the Release's own commit, and a later job's is the one the run job's first steps handed on; the wake jobs check out nothing. Each `run:` runs a module of the Release's `harness` from the folder its job starts in, the CLI's install from the vendor, word for word but for its version and checksum, or the wake's one call. The other steps are the pinned checkout, upload and download actions, each with its own inputs, and each upload and download names its `path`, one of the data folders the files use today. The CLI is the one the install placed, and every job runs on the runner named. No key moves where or how a step runs, or hands it more environment: no `working-directory:`, `shell:`, `defaults:` or `container:`, and no name of `env:` outside a fixed set. No step runs the item's tests or build, where the model credential or `ACTIONS_RUNTIME_TOKEN` could be reached | Every job can reach `ACTIONS_RUNTIME_TOKEN`, and the run job holds the model credential (0219's row "No build where the item's code could reach the model credential"). The Engine's step run from the head's folder would run the item's own copy of the harness beside the credential |
| A later opening Run | An opening `apply` opens the draft from what is on the work's branch, and pushes nothing, whenever the branch holds one commit beyond the default branch and that commit is, by its sha, the landed commit an `applied/1` of an earlier opening Run of this issue records, as decision 0238 holds, whatever the default branch's head is now. The sha pins the commit's tree and parent; the patch's digest is never compared. Since nothing is pushed on this path, the commit is one 0188's list held when it was pushed; and since a person can add a file to the list after that push, before it opens the files the commit changes from its parent are held to the list as the current base has it, as a push's are, and a commit that touches it opens no draft. The promise is to recorded pushes alone: a push GitHub accepted whose landed sha never reached `applied/1`, because the worker died between, opens no draft, and the issue ends at the `max_attempts` Hold for a person. Before it opens, the workflows are read again, as the first row says. Since it opens by the branch's name, `apply` then reads the opened pull request's head sha back and compares it with the recorded sha: on a mismatch it closes the draft and does nothing more. The opening after a push does the same with the sha it just pushed. Every other state opens no draft and is left to the push's write, harness/push.py, not built yet: another commit, more than one commit, or a commit no `applied/1` records | Run R1's `apply` pushes C1 and dies before it opens the draft; R2's model hands over another patch; refused by digest, R2 and every later Run stopped at C1 until `max_attempts` held the issue. A digest names a patch's text ("A Run that writes code reads its head, answers with a patch, and run hands it over by its digest (slice 2, S1)", issue 880), never a commit. The recorded sha already pins what was pushed and what 0188's list held then, and the list is read again because the first row's check of the workflows takes it as given: were `sonar-project.properties` put on the list after the push, the scan beside `SONAR_TOKEN` would pass that check and read the commit's copy; a base that moved since is ordinary for any open pull request, and a conflict is the fix Run's to handle. Refusing it would wedge the issue the same way: under 0238 a later opening Run admitted with C1 as its branch head is given no `push_commits`, so it could neither push nor open, and the issue would end at `max_attempts`. A commit no Run of this issue recorded holds what none handed over, so no draft is opened from it whatever its tree. The branch can move between the check and the opening; a closed draft runs no more `on: pull_request` jobs on what no Run handed over, and its close counts toward `max_unmerged_closes`, so a repeat brings a person. The read-back cannot unsend the opening's own `on: pull_request` event: whoever can move a branch of this repo can open a pull request from it, so that moment gives them nothing they lack |
| What this record leaves | Two more points of the same audit, and one its readers raised, are not decided here, and are left to a record of their own. 0219's row "One round, one Run" raises `max_attempts` for `implement`, a bound for one Intent that does not exist: `limits.max_attempts` in `config/defaults.json` is one number for every Intent's attempts. And for the first opening push, made before any pull request or branch head exists, neither 0219 nor 0238 says at which base commit 0188's list is read, or on which commit the patch lands. Nor is a mark ready held to a head: GitHub marks a pull request ready whatever its head is now, and the head its checks passed on is the `mark_ready` Effect's to carry, with its Role | Neither record decides them, and this one takes no point it cannot ground in a ruling |

## Why

0219 decided three things it could not hold. Its secret clauses were given to a list of files, which cannot keep a patch from the code a job runs, and one of them, read as written, forbade every push here while the check it named allowed one. Its rule that no Run holds a tool that runs code had no row, so nothing failed when one did. And its recovery, keyed on the patch's digest, wedged the next opening Run on the commit an earlier one left. The secret clauses are held where they can be, on the base's workflows, read before the grant and again at each push; the tool rule gets two checks, on the Engine and on the Run's workflow; and the recovery opens from the commit an earlier opening Run recorded, as 0238 holds, wherever the base has gone since, and from nothing else.
