# 0239. Push is granted only where no secret-bearing job runs what a patch may change, no Run holds a tool that runs code, and a later opening Run opens from the branch

Status: accepted. The Factory Builder's rulings of 2026-11-20 on "Record 0219's secret-check boundary can't be held by push.py's list, its no-tool rule has no boundary, and its opening recovery wedges a later Run" (issue 952), which the reader audit of 0219's squash commit found once it had merged without the desk's readers. It amends decision 0219's rows "What is left", where its last two sentences hold a secret-bearing check to the files a patch may change, and "Who opens the draft", where it says the next opening `apply` finds the branch at the handed-over patch's commit, by its digest, and refuses a branch at any other; and 0219's Boundary rows on `qa-lead`'s opening Run and on a branch whose checks run with a secret stand amended by the rows below. The rest of 0219 stands.

## Decision

| What | Decided | Because |
|---|---|---|
| Where the secret clauses are held | Before a repo is granted `push_commits`, its base's workflows are read. A repo where a job that holds a secret runs a file a Factory patch may change, its tests among them, or takes its configuration from one, is not granted it: a required test job that holds a secret and runs `python3 -m unittest`, or a scan that reads `sonar-project.properties` from the head beside `SONAR_TOKEN`, as `.github/workflows/sonarcloud.yml` does here ("Security: the SonarCloud scan reads a pull request's sonar-project.properties beside SONAR_TOKEN, and no list protects the file", issue 845). A file such a job only reads as source to analyse is not such a file. The rule is on the repo, read once before the grant, and never on a push: the refusal of a push that touches the base's list, which `harness/bundle.py` holds (decision 0188), stands, and holds no secret clause | No list of files can keep a patch from the code a job runs, which 0219's own "What is left" says; and worded on the branch, the clause forbade even a push that touches only `README.md`, which no push check would refuse |
| What it costs | This repo is not granted `push_commits` while its scan reads `sonar-project.properties` from the head, so the Factory writes no code here until the scan reads the file from the base or the file is on the base's list. A Consumer whose secret-bearing job runs its tests is not granted it until that job holds no secret; the Factory reviews there and writes nothing. A workflow a person changes on the base after the grant is not seen by the read before it; whether it is read again before each push is left to the push's write, not built yet | Named, as the price of holding the rule where it can be held |
| No Run holds a tool that runs code or writes | No phase of any Role is given a tool that runs code or writes: no `Bash`, `Write`, `Edit` or the like. The Engine alone names a Run's tools, from its Task: a review and a Run that writes code are given the read tools alone, `Read`, `Grep` and `Glob`, held to a head (decision 0138), and any other Run none. Nothing in `config/harness.json` or a Role's manifest names a tool | 0219 decided it, and no Boundary row held it: a phase given `Bash` passed every check 0219 named |
| No job of a Run runs the item's code | Every job of a Run's workflow, `.github/workflows/run-jobs.yml`, and of the approving and queue acts, checks out the Release's own commit alone, and each of its steps runs a module of the Release's `harness`, the CLI's install from the vendor, or the wake's one call. No step runs the item's tests or build, where the model credential or `ACTIONS_RUNTIME_TOKEN` could be reached | Every job can reach `ACTIONS_RUNTIME_TOKEN`, and the run job holds the model credential (0219's row "No build where the item's code could reach the model credential") |
| A later opening Run | An opening `apply` that finds the work's branch already holding one commit whose parent is the base the Run was admitted on takes it as an earlier opening Run's push: it pushes nothing, leaves its own patch, and opens the draft from what is there, as section 4.1 says, whatever the commit's tree. The comparison is by the commit's parent and tree, never by the patch's digest: the tree says only whether the commit is this Run's own patch, a retry, or an earlier Run's, and both open the draft. A branch at a commit whose parent is not that base, or holding more than one commit, is left to the push's write, not built yet, which decides whether it opens a draft from it; until it does, none is opened | Run R1's `apply` pushes C1 and dies before it opens the draft; R2's model hands over another patch; refused by digest, R2 and every later Run stopped at C1 until `max_attempts` held the issue. A digest names a patch's text ("A Run that writes code reads its head, answers with a patch, and run hands it over by its digest (slice 2, S1)", issue 880), never a commit, which also hangs on its parent, message and dates |

## Why

0219 decided three things it could not hold. Its secret clauses were given to a list of files, which cannot keep a patch from the code a job runs, and one of them, read as written, forbade every push here. Its rule that no Run holds a tool that runs code had no row, so nothing failed when one did. And its recovery, keyed on the patch's digest, wedged the next opening Run on the commit an earlier one left. The secret clauses are held where they can be, on the repo before the grant; the tool rule gets two checks, on the Engine and on the Run's workflow; and the recovery opens from what is on the branch, as section 4.1 always said.

## Boundaries

| Boundary | Check |
|---|---|
| A repo is granted `push_commits` only once its base's workflows are read, and never where a job that holds a secret runs a file a Factory patch may change, its tests among them, or takes its configuration from one, the scan's `sonar-project.properties` among them; a push is never refused or let through by this rule | waiting on `adapters/settings.py`, the read of the base's workflows, and waiting on `harness/push.py`, the push a repo not granted never makes |
| No Run is given a tool that runs code or writes: the Engine names a review's and a writing Run's tools as `Read`, `Grep` and `Glob` alone, any other Run's as none, and nothing in `config/harness.json` or a Role's manifest names a tool | `tests/test_harness.py::test_no_run_is_given_a_tool_that_runs_code_or_writes`, `tests/test_harness.py::test_the_cli_is_given_no_tool`, `tests/test_harness.py::test_a_review_reads_its_head_with_the_read_tools_alone_held_to_it`, `tests/test_harness.py::test_a_writing_run_reads_its_commit`, `harness/engine.py`, mutant: "a Run that reads is given a shell beside the read tools", mutant: "a Run that neither reviews nor writes code is given a tool that writes" |
| No job of a Run runs the item's code: each job of `.github/workflows/run-jobs.yml`, `.github/workflows/approve-job.yml` and `.github/workflows/queue-job.yml` checks out the Release's own commit alone, by a pinned action, and each step runs a module of the Release's `harness`, the CLI's install or the wake's one call | `tests/test_tools.py::test_no_job_of_a_run_runs_the_items_code`, `tests/test_tools.py::test_the_runs_jobs_keep_each_key_apart_and_always_leave_the_outcome`, mutant: "the run job runs the item's tests beside the model's credential", mutant: "the Run's first job checks out the item" |
| An opening `apply` that finds the work's branch holding one commit on the base its Run was admitted on pushes nothing and opens the draft from that commit, whatever its tree, never comparing the patch's digest; a branch whose commit is on another parent, or that holds more than one, opens no draft until the push's write decides it | waiting on `harness/push.py`, the push `apply` makes before the `open_pull_request` Effect |
