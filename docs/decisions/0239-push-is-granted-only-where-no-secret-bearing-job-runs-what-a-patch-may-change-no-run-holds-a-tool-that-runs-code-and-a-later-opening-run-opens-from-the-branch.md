# 0239. Push is granted only where no secret-bearing job runs what a patch may change, no Run holds a tool that runs code, and a later opening Run opens from the branch

Status: accepted. The Factory Builder's rulings of 2026-11-20 on "Record 0219's secret-check boundary can't be held by push.py's list, its no-tool rule has no boundary, and its opening recovery wedges a later Run" (issue 952), which the reader audit of 0219's squash commit found once it had merged without the desk's readers, and his rulings the same day on the questions this record's first draft raised. It amends decision 0219's rows "What is left", where its last two sentences hold a secret-bearing check to the files a patch may change, and "Who opens the draft", where it says the next opening `apply` finds the branch at the handed-over patch's commit, by its digest; and 0219's Boundary rows on `qa-lead`'s opening Run and on a branch whose checks run with a secret stand amended by the rows below. The rest of 0219 stands.

## Decision

| What | Decided | Because |
|---|---|---|
| Where the secret clauses are held | Before a repo is granted `push_commits`, its base's workflows are read, and again at each push, right before `push_commits` is used, so a secret-bearing workflow a person adds to the base between passes stops the next push. A repo where a job that holds a secret runs a file a Factory patch may change, its tests among them, or takes its configuration from one, is not granted it, and a push to it is refused: a required test job that holds a secret and runs `python3 -m unittest`, or a scan that reads `sonar-project.properties` from the head beside `SONAR_TOKEN`, as `.github/workflows/sonarcloud.yml` does here ("Security: the SonarCloud scan reads a pull request's sonar-project.properties beside SONAR_TOKEN, and no list protects the file", issue 845). A file such a job only reads as source to analyse is not such a file. The rule is read from the base's workflows, never from the files a push touches: the refusal of a push that touches the base's list, which `harness/bundle.py` holds (decision 0188), stands, and holds no secret clause | No list of files can keep a patch from the code a job runs, which 0219's own "What is left" says; and a check of the push's files let through a push that touches only `README.md`, which the clause, worded on the branch, forbade |
| What it costs | This repo is not granted `push_commits` while its scan reads `sonar-project.properties` from the head, so the Factory writes no code here until the scan reads the file from the base or the file is on the base's list. A Consumer whose secret-bearing job runs its tests is not granted it until that job holds no secret; the Factory reviews there and writes nothing. Each push spends one more read of the base's workflows | Named, as the price of holding the rule where it can be held |
| No Run holds a tool that runs code or writes | No phase of any Role is given a tool that runs code or writes: no `Bash`, `Write`, `Edit` or the like. The Engine alone names a Run's tools, from its Task: a review and a Run that writes code are given the read tools alone, `Read`, `Grep` and `Glob`, held to a head (decision 0138), and any other Run none. Nothing in `config/harness.json` or a Role's manifest names a tool | 0219 decided it, and no Boundary row held it: a phase given `Bash` passed every check 0219 named |
| No job of a Run runs the item's code | Every job of a Run's workflow, `.github/workflows/run-jobs.yml`, and of the approving and queue acts, checks out the Release's own commit alone, by a pinned action, and each of its steps runs a module of the Release's `harness` from the folder its job starts in, the CLI's install from the vendor, word for word but for its version and checksum, or the wake's one call. No key moves where or how a step runs, or hands it more environment: no `working-directory:`, `shell:`, `defaults:` or `container:`, and no name of `env:` outside a fixed set. No step runs the item's tests or build, where the model credential or `ACTIONS_RUNTIME_TOKEN` could be reached | Every job can reach `ACTIONS_RUNTIME_TOKEN`, and the run job holds the model credential (0219's row "No build where the item's code could reach the model credential"). The Engine's step run from the head's folder would run the item's own copy of the harness beside the credential |
| A later opening Run | An opening `apply` opens the draft from what is on the work's branch, and pushes nothing, only where the branch holds a single commit, on the base the Run was admitted on, that is the commit an `applied/1` of an earlier opening Run of this issue records as its push's landed commit, as decision 0238 holds. It is compared by its sha, which pins the commit's tree and parent, never by the patch's digest. Since nothing is pushed on this path, the commit is one 0188's list already held when it was pushed. Every other state opens no draft and is left to the push's write, harness/push.py, not built yet: another commit, another parent, more than one commit, a commit no `applied/1` records, and a base that has moved since that push | Run R1's `apply` pushes C1 and dies before it opens the draft; R2's model hands over another patch; refused by digest, R2 and every later Run stopped at C1 until `max_attempts` held the issue. A digest names a patch's text ("A Run that writes code reads its head, answers with a patch, and run hands it over by its digest (slice 2, S1)", issue 880), never a commit. A commit no Run of this issue recorded holds what none handed over, so no draft is opened from it whatever its tree |
| What this record leaves | Two more points of the same audit are not decided here, and are left to a record of their own. 0219's row "One round, one Run" raises `max_attempts` for `implement`, a bound for one Intent that does not exist: `limits.max_attempts` in `config/defaults.json` is one number for every Intent's attempts. And for the first opening push, made before any pull request or branch head exists, neither 0219 nor 0238 says at which base commit 0188's list is read, or on which commit the patch lands | Neither record decides them, and this one takes no point it cannot ground in a ruling |

## Why

0219 decided three things it could not hold. Its secret clauses were given to a list of files, which cannot keep a patch from the code a job runs, and one of them, read as written, forbade every push here while the check it named allowed one. Its rule that no Run holds a tool that runs code had no row, so nothing failed when one did. And its recovery, keyed on the patch's digest, wedged the next opening Run on the commit an earlier one left. The secret clauses are held where they can be, on the base's workflows, read before the grant and again at each push; the tool rule gets two checks, on the Engine and on the Run's workflow; and the recovery opens from the commit an earlier opening Run recorded, as 0238 holds, and from nothing else.

## Boundaries

| Boundary | Check |
|---|---|
| A repo is granted `push_commits` only once its base's workflows are read, and never where a job that holds a secret runs a file a Factory patch may change, its tests among them, or takes its configuration from one, the scan's `sonar-project.properties` among them | waiting on `adapters/settings.py`, the read of the base's workflows that grants `push_commits` for a repo |
| Right before each push uses `push_commits`, the base's workflows are read again, and the push is refused where a job that holds a secret runs a file a Factory patch may change or takes its configuration from one, so a secret-bearing workflow added to the base between passes stops it | waiting on `harness/push.py`, the push `apply` makes |
| No Run is given a tool that runs code or writes: the Engine names a review's and a writing Run's tools as `Read`, `Grep` and `Glob` alone, any other Run's as none, and nothing in `config/harness.json` or a Role's manifest names a tool | `tests/test_harness.py::test_no_run_is_given_a_tool_that_runs_code_or_writes`, `tests/test_harness.py::test_the_cli_is_given_no_tool`, `tests/test_harness.py::test_a_review_reads_its_head_with_the_read_tools_alone_held_to_it`, `tests/test_harness.py::test_a_writing_run_reads_its_commit`, `harness/engine.py`, mutant: "a Run that reads is given a shell beside the read tools", mutant: "a Run that neither reviews nor writes code is given a tool that writes" |
| No job of a Run runs the item's code: each job of `.github/workflows/run-jobs.yml`, `.github/workflows/approve-job.yml` and `.github/workflows/queue-job.yml` checks out the Release's own commit alone, by a pinned action; each step runs a module of the Release's `harness`, the CLI's install word for word but for its version and checksum, or the wake's one call; and no step, job or workflow names a key outside a fixed set, `working-directory:`, `shell:` and `defaults:` among those refused, or an `env:` name outside a fixed set | `tests/test_tools.py::test_no_job_of_a_run_runs_the_items_code`, `tests/test_tools.py::test_the_runs_jobs_keep_each_key_apart_and_always_leave_the_outcome`, mutant: "the run job runs the item's tests beside the model's credential", mutant: "the Run's first job checks out the item", mutant: "the Engine step runs from the head's folder", mutant: "the CLI's install runs a command after an allowed start" |
| An opening `apply` pushes nothing and opens the draft from the work's branch only where it holds a single commit, on the base the Run was admitted on, whose sha is the landed commit an `applied/1` of an earlier opening Run of this issue records; another commit, another parent, more than one commit, a commit no `applied/1` records, or a base moved since that push opens no draft | waiting on `harness/push.py`, the push `apply` makes before the `open_pull_request` Effect |
