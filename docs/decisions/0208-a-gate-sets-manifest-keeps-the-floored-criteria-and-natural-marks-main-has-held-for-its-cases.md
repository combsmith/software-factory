# 0208. A gate set's manifest keeps the floored criteria and natural marks main has held for its cases

Status: accepted. The Factory Builder's ruling of 2026-11-12 on "Differences between a gate set's manifests across commits can isolate a group under ORIGIN_LEAST" (issue 695): a repo check, which stops a pull request and never a dispatch. It takes up, for cases that have not changed, one residual of `docs/decisions/0180-a-gate-set-holds-a-floor-per-criterion-read-from-each-cases-expected-criterion.md`: "the least holds within one manifest, not between two". All of 0180 stands.

## Decision

| What | Decided | Because |
|---|---|---|
| The rule | A gate set's manifest floors the criteria, and marks natural the cases, that every gate set's manifest main has held of the same cases does. The cases are the same where each id and its sha256 are, in any order | Two manifests of the same cases that count them in other groups publish counts whose difference is a group of fewer than `ORIGIN_LEAST` cases. With a floor on one criterion at one commit and on another at the next, what is left is the findings on neither, which may be one case. With one more case marked natural, it is that case, under its public id |
| Under any name | A manifest is held to those of the same cases under any directory of `evals/`, in main's history and beside it in the tree | A case is fetched by its Role and its id, never by its set's name, so the same cases under another name are the same cases |
| At any commit of main | What main has held is every manifest under `evals/` as each commit of main's history that changed anything there left it, read from the merge base with origin/main back, by first parents: not the merge base's alone, no commit of the branch's own, and no commit of a branch a merge brought in but as the merge left it. Only a regular file is a manifest | A set taken away and put back, made a development set and a gate set again, or given a case and a moved floor in one change and losing the case in the next, would each pass a comparison with the last manifest alone |
| What may change | A floor's fraction, each kind's bar, the least of a kind, the record, the preflight and the order the cases are listed in | None of them is a group a report counts |
| Where it is held | `tools/check_gate_sets.py`, a check `tools/verify.py` runs, "gate sets". It fails a pull request and its merge group. It reads no case and stops no dispatch | Decision 0180 left the differences unheld because a rule at the fetch, on criteria a set does not floor, could stop a set no builder can see. Every change to main is a pull request, and each is held to all main held before it; in a merge group, where the entries ahead are not on origin's main yet, to those too, read from the commit before its own |
| A history that cannot be read | Fails, where the tree holds a gate set. An export, which has no history, is held to its own tree alone, but in GitHub Actions, where a checkout always has one and it fails | It never passes what it could not compare, as the decision records' check does not |
| What it does not hold | A manifest main held as a development set, as a link, or as nothing that can be read; and a set whose cases differ from every set's that main has held | The first counted no such group; `tools/check_repo.py` refuses a link. The last is the residual below |
| What it rests on | Main's ruleset: the merge queue is the only way onto main, by squash and with no bypass, so main's own line is every commit's first parent. Were a branch merged with main as its second parent, what main held on that side would not be read | The walk is by first parents, so that a branch's own commits are not read as main's |
| What it costs | Two git commands for each commit of main that changed anything under `evals/`, each time the checks run, and none while the tree holds no gate set | A tree with no gate set has nothing to hold; the history is short |
| Residual: cases added, dropped or issued again | A manifest that adds, drops or issues again a few cases, and keeps them so, may move a floor or a mark with them, and the difference between the reports' counts before and after may then be a few cases | Out of scope, by the Factory Builder's ruling of 2026-11-12; written on that issue. A manifest is a protected path, each change to it reviewed, and only the Maintainer dispatches a gate set |
| Residual: an overlap within one manifest | Two groups one manifest counts may still overlap in fewer than `ORIGIN_LEAST` cases, as 0180 names | The other part of that issue, an advisory at the fetch, which the Factory Builder ruled a change of its own |

## Why

Decision 0180 holds every group a report counts to none or `ORIGIN_LEAST` cases under one manifest, and wrote down that two manifests of the same cases are not held to each other. The groups a manifest makes are the criteria it floors and the cases it marks natural, and both are in the manifest, which is public. So the rule can be held where the manifest changes, against all that main has held, with no case read: while the cases stay, the groups stay.

The first form of this change compared a manifest with the merge base's at its own path. Its reviews showed two ways round that needed no case to change: the same cases under another name, and two pull requests in a row. Reading main's history, under any name, closes both.
