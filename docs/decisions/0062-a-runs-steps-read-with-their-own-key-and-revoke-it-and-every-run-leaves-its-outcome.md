# 0062. A Run's steps each read with their own credential and revoke it, and every Run leaves its outcome

Status: accepted. A working ruling of 2026-10-25 for "Workflows: the frozen entry shim, the poller, the Run's three jobs and the nudge, each held to its shape" (issue 196), its PR 2b-1, the steps its workflow files run, with the Maintainer's answers of 2026-10-21 on rulings 7 and 8. The Maintainer may overturn it in review. It adds to `docs/decisions/0054-apply-writes-a-roles-effects-with-a-token-narrowed-to-them-and-claims-only-what-it-reads-back.md`, whose `apply` step it wires, to `docs/decisions/0055-the-approving-act-holds-the-machine-users-token-alone-approves-the-commit-it-re-read-and-says-whose-fault-each-failure-was.md`, whose act it wires, and to `docs/decisions/0060-the-pass-entry-reads-through-the-ports-with-a-token-of-reads-and-the-last-two-pass-records.md`, whose reads the steps share.

## Decision

| What | Decided | Because |
|---|---|---|
| The reader's step | `harness/read.py`, the `run` job's first step, given NAME, ITEM and PASS, the Run's three inputs. It mints the reader App's token from `READER_APP_KEY`, for the home repo, with every read its grant allows and no write. It finds the pass record by PASS among the poller's runs, whatever their status, since a Run may start before its pass ends (what cannot be read raises, the environment's, never no Decision), and in it the Decision of the Run id the run-name names, which must be of the run-name's item, Intent, Role and content. It reads the pull request's facts and the diff's bytes, which must hash to that content, at the head the snapshot was held to. It writes the record, the Run id, the facts, the diff, the texts, the manifest and the Findings into a new folder for `run`, and revokes its token before it ends: a token GitHub did not revoke fails the step | The Maintainer's answer (b): the reader's key in a step of its own, revoked before the model's step, so the model's step holds no secret but its own. `harness/task.py` stays a function of what it is given |
| What the reader does not read yet | The texts, whose port is not built, so a Task carries the diff alone; the Finding records a Decision names, so the review Intent, which names none, is the one a Run can carry; an issue's Run, `issue_not_built`. The facts' `runs` is read as whole, since no Kernel is asked in `run` | Each waits on the story that holds its port |
| `run` from the folder | `python3 -m harness.run TASK OUT` takes each input from the reader's folder by name, and the Run id from it, held to its form | The workflow hands nothing from step to step but files |
| `verify` | `harness/verify.py` takes the Result by the digest `run` reported, `RUN_DIGEST`, holds it to `result/1`, and writes `verdict/1`: the Run, its Release, the digest, and `checks: not_run` for an Intent that pushes nothing | L-54: a repo with no test is not run, never passed. The checks for code come with the fix Intent |
| `apply`'s step | `harness/apply_step.py`. Unless `NEEDS` shows `run` and `verify` succeeded, nothing is minted and nothing written, and the Run ends `environment`, `run_failed` or `verify_failed`. Otherwise it mints the pr-review App's token of reads alone, `apply.READS`, from `PR_REVIEW_APP_KEY`, finds the pass record by PASS, and hands `harness/apply.py` the Decision, the Result taken by `RUN_DIGEST`, the item read again and a mint of the write token its Effects need. A read token GitHub did not revoke ends the Run `environment`, `token_not_revoked`. No Decision for the Run, or one of another item, Intent, Role or content than its run-name's, ends it `superseded`, `no_decision`; a record that cannot be read, `environment`, `record_unreadable`; a record of another Release than `RELEASE`, the one the job runs, `environment`, `release_differs`, and nothing is written | Decision 0054: `apply` always runs, so a failed `run` still leaves its outcome, and its code decides that nothing is written |
| The last step | `harness/outcome.py`, run whatever failed: the outcome `apply` recorded when it is this Run's and this Release's, `RELEASE`; otherwise `environment`, `apply_failed`. An outcome that names a fault fails the step by its code once it is written, and the approving act's step does the same, so that the run concludes as it ended; the upload after it runs whatever failed | No Run that died leaves nothing, and the pass reads the outcome of a Run that did not succeed alone (section 3.10); a fault the run concluded `success` on would count as a success in the automatic pause |
| The approving act's step | `harness/approve_step.py`: the machine user's token, `APPROVER_TOKEN`, held by the effects port's `Approving` to the item's repo and reads and the one approval; the pass record found, and the item read again, through it, the Decision held to the run-name's item and content as the reader holds it, and the record to the job's Release. No key is minted | Decision 0055 |
| The item read again | `harness/reread.py`, for `apply` and the act: the run records, the Pause on the org and the item's repo, and the snapshot with the head it was held to, its accounts those of `config/controller.json`; the context built by `context_of` in `controller/pass_.py`, the pass's own, with no pass records before, so `passes_since` is unreadable, which defers nothing. A run list that cannot be read raises | One reading of the item, the pass's, so `apply` and the act ask the Kernel what the pass asked |
| The Controller's token in the effects step | Minted from `CONTROLLER_APP_KEY`, for the home repo, with the needs among the status's and the tracking issue's writes the App is granted, and revoked when the writes end; a token GitHub did not revoke fails the step. A need that waits on its grant is not minted, and its write is refused for want of a credential | The workflows' ruling 4 gives the step the key, never a token in the environment |
| Shared | `from_key` in `adapters/identity.py` mints any App's token from its key; `accounts_of` and `dispatcher_of` in `adapters/facts.py` read the accounts of `config/controller.json` for the entry and the steps alike; `controller/configuration.py` reads what a pass and a step are told; `harness/steps.py` makes each step's folder and files new, its own user's alone, and prints one code | One way to mint, and one to read the configuration |
| Refused until the grants | `apply`'s reads need the pr-review App expanded, `checks: write`, `actions: read` and `issues: read` (decision 0054), and the Controller's tracking issue and the Pause's read need its grants (decision 0056). Until each registration changes and P-39 reads it again, the token is refused, and the step records why | Nothing runs on a grant no trial has recorded |

## Why

The workflow files of the same story run these steps, and none had an entry: `run` had its own, and the pass's, but nothing read the Task's inputs, verified a Result, wired `apply`, left an outcome whatever failed, or ran the approving act. They land before the workflow files, so that the files only call them.
