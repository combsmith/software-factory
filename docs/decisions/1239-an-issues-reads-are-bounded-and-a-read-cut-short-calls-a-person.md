# 1239. An issue's reads are bounded and a read cut short calls a person

Status: accepted. Replaces `docs/decisions/0234-an-issues-reads-are-bounded-by-pages-and-by-a-budget-of-requests-a-pass-and-an-issue-past-its-bound-calls-a-person.md`, `docs/decisions/0250-an-issues-references-and-links-are-cut-past-their-one-page.md`, `docs/decisions/0251-a-pass-reads-issues-to-a-budget-of-requests-oldest-left-out-first.md`, `docs/decisions/0252-a-short-issue-list-reads-no-issue-and-stops-no-pass.md`, `docs/decisions/0253-a-chain-of-spans-broken-while-an-issue-is-named-calls-a-person.md` and `docs/decisions/1167-the-view-shows-an-issue-left-unread-as-the-pass-before-decided-it.md`. 2026-11-26, the Solution Architect; issues 849 and 1238. Nothing decided changes.

## Decision

| What | Decided |
|---|---|
| Page bounds | The issues port reads an issue's timeline, and each linked pull request's, to ten pages (`BOUND` in `adapters/timeline.py`), and linked pull requests only while 25 at most (`CANDIDATES` in `adapters/linked.py`). References and links: one page each |
| A read past a bound | The facts say `timeline_bounded`. The issues' Kernel defers on it, open or closed, before any short read, and calls a person (`kernel/issue.py`). A flag not exactly true or false is a gap, `facts_incomplete` |
| Read on | Within the bounds every pull request is read, though another read is short or cut |
| A budget a pass | Once `max_issue_requests` (`config/controller.json`) issue requests are sent, answered or not, permission reads in and the listing out, no new read starts. Those unread are left out as `issue_budget`, alert `issue_budget_spent`. A begun read finishes; one issue is always read |
| Which first | Issues the newest record left out by the budget come first, in its order, then the listing's. A record whose list was read short is passed over (`controller/pass_.py`) |
| A short list | No issue is read; the pull requests are decided. One itemless entry, `issue_list_unreadable`, and its alert. Every issue that might have left is owed again |
| Broken spans | Keyword spans pass over a record the budget left the issue out of. Broken while a pull request, or anything but an issue, names it, the chain defers `spans_broken` and calls a person; otherwise, as a linked list read short |
| The view | An issue left unread by the budget or a short list is shown as the record before decided it, one pass deep (`controller/feed.py`); its age skips them |

Limits: an issue past a bound waits on a person, who may close it; more comments never mend it. One pull request commented past its bound stalls every issue it names. An outsider can force a call by opening about forty issues or forcing a short list. A `spans_broken` flag not exactly true is no break. The last read begun can overrun the budget by 390 requests (decision 1203), two more a Run where a branch stands (decision 1207), and a permission read a new login.

## Why

Anyone can comment on an issue or open pull requests that name it, so a read with no bound, every pass, is an amplification an outsider controls (the security read of S3 PR2e). At 100 a pass and 20 passes an hour, no issue read starts past 2,000 requests an hour, under half an App's 5,000. A short list must not starve the pull requests; a cut read only grows, so a person must see it. Calling a person for every broken chain was rejected: one nothing names mends in a pass or two.
