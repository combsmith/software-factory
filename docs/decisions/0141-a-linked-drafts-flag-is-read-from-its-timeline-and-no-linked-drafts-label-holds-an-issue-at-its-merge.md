# 0141. A linked draft's flag is read from its timeline, and no linked draft's label holds an issue at its merge

Status: replaced by `docs/decisions/NNNN-two-pull-requests-linked-by-hand-before-an-issues-merge-leave-it-held-and-its-type-changes-are-read-whole.md`, which holds the rule in force.

## Decision

| What | Decided | Because |
|---|---|---|
| The fact | Each linked pull request in `issue-facts/1` carries `draft_events`: each conversion to a draft and each marking ready on its timeline, with its time, in the timeline's order, which is the order they happened. One opened as a draft has none for it; each changes the flag, so the two alternate; and the last is its flag now. A flag that disagrees with its last event, two of one kind in a row, a time out of order, or an event that cannot be read defers, `linked_unreadable`; two in one second, in order, are read | `trials/P-33.json`: a canary pull request marked ready, converted to a draft and marked ready again has each as its own event, a second or two apart; one left a draft from its opening has none. An unreadable fact never yields an action, and an author converting and marking ready in one second must not stall the issue (Claude's security read, Codex) |
| How the flag reads at a time | A linked pull request was a draft at a time where its flag now, with every event after that second undone, says so, or where it was one at any moment of that second; before its first event it was what that event undid. Nothing in the Kernel reads it yet: row 1 needs, beside the flag, when the pull request became linked, which the third issue the Status names is to give | So the fact is ready the day a link's time can be proven, and its reading is decided now, not then |
| Row 1 at the merge | Row 1 reads only the issue's own labels at the first merge: a person's hands-off on the issue keeps `not_served`, `merged_while_hands_off`; a Hold on the issue, or hands-off no person placed, keeps `held`, `merged_while_held`, unless a person's hands-off on the issue stood beside it. No linked pull request's label is read there | No fact with no time moves a terminal State, in either direction: the Factory Builder's ruling (A) on "A platform close keeps the State a person set on an issue held or not served" (issue 522), held whole by ruling (ii) here. When a pull request became linked carries no time: one opened before the merge may have been named by a keyword an edit added after it (`trials/P-46.json`), so its labels, read at the merge, could move a `done` issue to `held` or `not_served`, and read as they stand now, its flag could too |
| What row 1 no longer reads | A Hold on a linked draft, hands-off anyone but a person placed on one, and a person's hands-off on one that let a Hold on the issue pass, each of which decisions 0028 and 0139 read from the draft's flag and the link as they stand now | The flag now was itself a fact with no time; taking it out completes ruling (A) rather than weakening it |
| What carries no time | When a pull request became linked, the Consumer entry, whose configuration has no history, a left-out label, whose list is the entry's as it stands now, and the issue's type. So the queue's merge under a Hold or hands-off on a linked draft, on an issue the entry leaves out, or from two links may still leave `held` or `not_served` by the platform, a change the Lifecycle does not declare. The trial the Status names asks for a type and a link by hand; the third issue it names gives a keyword's link the time of the first pass that saw it, and leaves the entry, as ruled, until a Consumer needs it | GitHub dates a keyword's link at the first mention of the issue, not at the keyword (`trials/P-48.json`), and a link by hand and a type change are untried; a left-out label read at the merge against today's list would bring back what ruling (b) on the same issue as ruling (A) took out |
| The exploration | The queue merges the Factory's and an admitted outsider's ready pull request from a Hold or a person's hands-off on the issue itself, never under a linked draft's, and records each change of a draft's flag | The issue's own labels are placed at the merge; a draft's are not, and that merge waits on the link's time |
| What stays | Everything else decision 0139 decides, as it words it, and with it decision 0028 and decision 0132 as 0139 keeps them | Only what row 1 reads of a linked draft is overturned |

## Why

Decision 0139 kept the State a person set on an issue where the facts could place it at the merge, and still read a linked draft's labels from its flag and link as they stand now. A pull request's timeline gives each change of its flag with its time, but not when it became linked, so a draft's labels still cannot be placed at the merge: row 1 stops reading them, and the draft facts wait, read whole, for the link's time.
