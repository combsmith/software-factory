# 0216. The author Role's fix is admitted only on a pull request the Factory opened

Status: accepted. The Factory Builder's rulings of 2026-11-13 on "The author Role's fix is admitted only on a pull request the Factory opened: the reach of fix-findings (slice 2, S9b)" (issue 823), after the Solution Architect's read of slice 2's draft, which found that naming `author_role` would admit the fix on every pull request the Factory serves. It adds to `docs/decisions/0189-no-author-role-is-named-until-its-manifest-exists.md`: the manifest is one condition for naming the Role, and this rule is another.

## Why

Slice 2 names `dev-lead` as the author Role. `kernel/decide.py` asked only whether a Role was named: with one, an item in `addressing` wanted its fix whoever opened the pull request. Every pull request the Factory serves today is a builder's session's, a person's or the dependency bot's, so the first pass after the naming would have dispatched the Role to push to each of them that had a failed check or an open Finding.

The fix is safe only where the branch is the Factory's own to change. That is the pull request the Factory opened for an issue: its branch is named for that issue, the App of the Role that opens pull requests authored it, and its opening Run recorded it. The acceptance port already reads exactly that, to find which issue's contract binds the pull request, so the Kernel is given that reading and no second one.

The fact is optional because the other way costs a person's approval for nothing gained: the Kernel reads its absence on the closed side, and the port's test holds that every snapshot gives it.
