# 0120. The gate holds a bar of the set and of each kind, and a fault of the Engine or the run still closes it

Status: accepted. Replaces `docs/decisions/0071-a-release-is-cut-from-main-through-the-eval-gate-and-never-moved-and-next-is-rolled-back-with-no-gate.md`, `docs/decisions/0100-an-eval-cases-expected-finding-is-as-its-rubric-gives-it-read-at-run-time-where-the-case-is.md` and `docs/decisions/0109-the-scorers-codes-are-in-the-public-report-and-the-judges-log.md`. The Maintainer's choice of 2026-11-02, of the Factory Builder's wording, asked "The gate needs every case to pass, but the model varies between runs: even a sound reviewer may miss one or two. Should the bar change?": "At least 90%, and each kind 80%", described as "36 of 40 opens the gate, with neither kind below 80%, so a reviewer can't pass by approving everything. Set now, before the next results, so it isn't fitted to them. Failures show in the report. It does let a Release through with up to 4 failing cases." Asked again the same day, "Should a case that expects a blocking finding always have to pass?", he chose "Yes, blocking cases must pass". Told that the word for those cases can reveal which cases expect a blocking Finding and narrow their criterion, that no case content leaves, and that it goes beyond his earlier approval, he chose "Accept it". Asked whether a set must hold one, he chose "Yes, at least one". All were set before any result with issue text: no run has yet read a case that holds its issue. It overturns "every case passed", on his word, and nothing else in those records.

## Decision

| Why a bar | The model varies between runs, so even a sound reviewer may miss a case, and a gate that needs every case closes on that miss. Run 41339197743 passed 1 of 42 | A reviewer that approves everything clears no bar here, as it fails the kind that expects a Finding |
| The bar | At least 90% of the set passes, and at least 80% of each kind, `BAR_OF_THE_SET` and `BAR_OF_A_KIND` in `harness/eval/__init__.py`. | A blocking case | A case that expects a Finding of severity `blocking` must pass, whatever the bar, or the run is `case_failed`. It is computed in the job as `blocking_pass`, one word and never how many, null where a case was not read. A set must hold one, `BLOCKING_LEAST`: with none, `split_ok` is false and the run is `eval_split_short`, a code and no count. A case is blocking by the severity it states or by what the rubric gives its criterion, so one that states less, off its rubric and never asked, does not leave the rule. A case's own fault on such a case closes the gate too, as it is not passed. A clean case on a blocking criterion expects no Finding, and is the bar's | The Maintainer's word above. | Where it is computed | The set's share in `verdict`, from the report's own cases. A count of a kind stays out of the report, whose counter-example holds it |
| What closes it whatever the bar | `engine_fault`, any of `ENGINE_FAULTS`. `run_fault`, a new code, any of `RUN_FAULTS`: `schema`, `not_found`, `hash_differs`, `too_large`, `unanswered`, which stop the run reaching or trusting a case. `eval_split_short`, and every other check `verdict` makes first | Such a run says nothing of the reviewer, and a hash that differs says the set is not the one named. No share of passes can stand on it |
| What counts as not passing | Every other case not passed: the scorer's own codes, and a case's own fault, `not_this_set`, `facts_not_current`, `facts_read_short`, `diff_unreadable`, `diff_not_content`, `pusher_unnamed`, `diff_not_whole`, `issue_not_whole`, `issue_unreadable`, `answer_off_rubric`, `answer_disagrees_with_verdict`, `location_unreadable`, `criterion_unknown`. | What the bar does not hold | No floor by criterion, or for any severity but `blocking`: a reviewer blind to one criterion clears if few cases rest on it and none expects a blocking Finding. A commit under the bar may be dispatched again, as the gate takes the newest run that succeeded, and the model varies, so a run near the bar may clear on a later try: only the Maintainer dispatches, and that is his to weigh. ## Why

The eval is the Factory's one measure of its reviewer, and a measure that must read perfect measures nothing but the hardest case. A case is reviewed by the two functions a live Run uses, so that the set measures the Run the Release ships, and the split is held in the job because that is where the cases are. Both stand, and so do the rest of the rows above, from 0071, 0100 and 0109, word for word but where they said a case not passed fails the run: what changes is what a run must clear, and what the report needs to say so.
