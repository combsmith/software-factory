# 0147. The Engine runs the pinned model by its full id, at the tier's effort, and keeps an answer only from that model

Status: replaced by `docs/decisions/0151-the-artifact-storage-is-any-productionresults-account-numbered-in-one-to-three-digits.md`, which holds the rule in force.

## Decision

| What | Decided | Because |
|---|---|---|
| The model | `config/harness.json` names the model by its full id, `claude-opus-5-5`, and `schemas/harness.schema.json` admits nothing else: `^claude-[a-z]+(-[0-9]+)+$`, so `opus`, `best` or `opus[1m]` is refused | The pin said `opus`, an alias the CLI resolves at each call. At 2.1.306 the CLI's own catalog, in its binary, resolves it to `claude-opus-5-5` for a first-party login, and the same code reads an alias through a model list it is given at run time, so the alias is not fixed by the pin. Anthropic's models page lists `claude-opus-5-5` as both the id and the alias of Opus 5.5, and says each dateless id from 4.6 on is a pinned snapshot, so there is no dated form to name |
| Where a model is named | In `config/harness.json` alone, and in the counter-examples of its schema, which copy that id and no other. `tools/check_repo.py` refuses a model's full id anywhere else but a document or a fixture, in any file whatever it is called. It reads a model with whatever is joined to it on either side and any suffix in brackets, so `-latest`, a prefix of letters or others, or `[1m]` makes another model than the pin, and it takes the pin as one only where it is a full id in the form the schema holds | L-34: a model named in one place is changed in one place. Its rule waited on the engine port, which now exists |
| The model that answered | `usage.answering_model` records the one model the CLI's `modelUsage` names, or null where it names none, more than one, or one in a form `schemas/result.schema.json` does not hold. An answer whose answering model is not the pinned one is no Result: `failed`, `engine_model`, its findings and Effects dropped, as one at another version is `engine_version`. So is a Run that erred or ran out where `modelUsage` names any model but the pin alone, whatever its own reason; one that names no model, in any empty form, or that the CLI never answered, keeps its own reason. Which model answered is decided before an answer is held to any schema, so another model's answer that fails one is `engine_model`, never `result_invalid` | The pin names the model asked for; only the CLI's answer says which model answered. An eval score is of the model that answered, so an answer from another model, by a fallback, a remapped alias or a change on the vendor's side, cannot be scored as the pin's, and nor can its errors or a schema it failed, which are the reviewer's codes in the eval |
| The fault | `engine_model` is an Engine fault in the eval (`ENGINE_FAULTS`, the eval report's reasons), never the reviewer's. In a live Run it is an attempt on its item, as `no_answer` is, and never the environment's: it costs the item an attempt and counts toward no pause | Decision 0106: a fault of the Engine is never the reviewer's. Decision 0121: a code an item's text can bring about stays the item's, or text on two items could pause every Run. The pinned CLI's catalog gives `claude-opus-5-5` a fallback on refusal, so an item's text can call another model |
| The effort | Each tier in `schemas/harness.schema.json` has an `effort`, one of the CLI's levels (`low`, `medium`, `high`, `xhigh`, `max`). Both are `medium`. A Task carries its tier's, `harness/engine.py` gives it to the CLI as `--effort`, and `usage.effort` records it | `medium` is the default the pinned CLI's catalog gives `claude-opus-5-5` today, so nothing a Run does changes. Named, the effort no longer moves when the CLI's default does. The pinned CLI lists `--effort <level>` with these five levels in its help |
| No update | The CLI is given `DISABLE_UPDATES=1` beside `DISABLE_AUTOUPDATER=1`: the names it is given are exactly `PATH`, `LANG`, `HOME`, `TMPDIR`, `DISABLE_UPDATES`, `DISABLE_AUTOUPDATER`, `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` and the model credential under `CLAUDE_CODE_OAUTH_TOKEN` alone | The pinned binary reads both names. The version is held before and after each call (L-35), and a CLI that does not try to update cannot fail that check by doing so |
| The CLI's version | Stays at 2.1.306 | Moving the pin is the Maintainer's call, after the cut |

## Why

The eval scores the review Role on held-out cases, and the cut rests on that score. A score means something only of the thing that will run: the same CLI, the same model and the same effort. The version was pinned and checked; the model and the effort were left to the CLI's defaults of the day. Each is now named, given to the CLI and recorded in `usage`, and the model that answered is checked against the pin.

What is owed: no trial has recorded `modelUsage` from a review Run under the read tools, or with `--effort` given. P-13 at 2.1.306 recorded one model in `modelUsage` with no tool. If a later pin names a second model there for a Run that uses one, such as a smaller model for a tool, every such Run fails `engine_model` until a record says how to read it.
