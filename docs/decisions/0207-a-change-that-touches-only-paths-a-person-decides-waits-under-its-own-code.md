# 0207. A change that touches only paths a person decides waits under its own code

Status: accepted. Decided for "The reason a person-only path waits is named for itself, not as a model Lens's input" (issue 746). It amends two rows of `docs/decisions/0200-a-path-only-a-person-decides-is-listed-apart-from-a-lenss-inputs-and-a-change-to-it-needs-a-persons-approval.md`. "The code it waits in" kept `model_lens_input_needs_person` for a person-only path; for a change that touches no model Lens's input it no longer does. "How the Kernel is told" said the Kernel changes by no line; it now reads a second list. The rest of both rows stands, and so does every other row of 0200.

## Decision

| What | Decided | Because |
|---|---|---|
| The code | A change waits in `verifying` as `path_needs_person` where every path it touches, of the two lists below, is one only a person decides. The evidence names each such path as the configuration has it, once | No Lens reads such a path, and the code a person is shown said one did. The wait and who ends it were already right |
| Beside a model Lens's input | A change that touches a model Lens's input as well keeps `model_lens_input_needs_person`. Its evidence names every path of either list that it touches, the Lenses' inputs first, each once | A Decision has one reason. Of the two, the Lens's says that what judges a change has itself changed, which is the more a person must know; the path stands beside it in the evidence |
| Who ends the wait | As 0052 and 0200 have it, for both codes: a person with write access other than the author and the last pusher approves the head. One approval ends both. In the merge queue without one the change is taken out | Only the name changes |
| How the Kernel is told | It is given a second list, `person_only_paths`: each path of `person_only` in `config/hooks.json` that no model Lens reads, once, from the one reading `tools/hooks/protected.py` makes of that file. `controller/configuration.py::person_only` builds it, for the Controller, the simulator and the tests alike. `model_lens_inputs` is given as 0200 has it, the person-only paths after a model Lens's own | `tools/hooks/protected.py` and `config/hooks.json` are a model Lens's inputs, and neither changes here: the reading already returns both lists. One function for the three that tell a Kernel leaves nothing to drift |
| Either list holds the wait | A path on `person_only_paths` waits for a person whether or not `model_lens_inputs` holds it too. The code follows `person_only_paths` alone: a path that is on `model_lens_inputs` and not on it is taken for a Lens's input, the stricter name | Were the two ever given apart, the wait must not be lost with the name, and a list that leaves a path out errs to the Lens's code |
| A path on both | No path is listed both as a model Lens's input and as a person's today. Were one, it is left off `person_only_paths`, so a change to it waits as `model_lens_input_needs_person` | A model Lens's input is the stricter and the more specific reason (0052), and is never to be masked by the other (the Factory Builder's ruling of 2026-11-13) |
| A list that cannot be read | `person_only_paths` not there, or not a list of patterns in the shape every path has, is `protected_paths_unreadable`: the item defers for the Maintainer, and leaves the merge queue. A list that names none is read | A configuration from before 0200 names none. One that says nothing of the list could be hiding one, and a fact that cannot be read is never taken for its default (I-13) |
| What a person is asked | `config/feed.json` gains the row `path_needs_person`: the question `a_path_needs_you`, and the choices of a model Lens's input, approve or close | `tools/check_examples.py` asks a row of every reason that needs a person |
| From when | From the first Release cut after this record merges. Until then the Release on `next` names the wait as 0200 has it | The Kernel and the Controller that tells it ride one Release |

## Why

0200 put the Maintainer's decision file under the rule for a model Lens's input without a new rule in the Kernel, and said plainly that the code was then narrower than what it held. The person who must act reads the code and the question it maps to, and both told him a Lens's input had changed when none had. The Kernel already matched the change against the list; it needed only to be told which of those paths are a person's.
