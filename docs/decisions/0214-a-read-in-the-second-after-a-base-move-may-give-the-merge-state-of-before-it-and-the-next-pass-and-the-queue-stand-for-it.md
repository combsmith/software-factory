# 0214. A read in the second after a base move may give the merge state of before it, and the next pass and the queue stand for it

Status: accepted. The Factory Builder's ruling of 2026-11-13 on "Trial P-40: a move of the base alone makes GitHub work out mergeable again, for a pull request that still merges and for one the move makes conflict" (issue 809), whose trial failed.

## Decision

| What | Decided | Because |
|---|---|---|
| What GitHub does | After a push that moves only the base, a REST read of a pull request gives `mergeable` as GitHub had worked it out before the move for about a second after the push is answered. Then it gives null, and then the answer against the new base. Nothing in the stale read says it is stale: its `updated_at`, `mergeable_state` and `merge_commit_sha` are those of the read before the move | Trial P-40, run twice in the canary on 2026-11-13 |
| The second run's timings | `trials/P-40.at-once.json`, one pull request the move makes conflict. The base's commit is dated 05:13:11Z and its push was answered at 05:13:12Z. Reads begun 0.06 s and 0.61 s after that answer gave true; reads begun 1.22 s, 1.83 s and 2.27 s after it gave null; the read begun 2.80 s after it gave false, and GraphQL at 3.32 s `CONFLICTING` | It asks the first second alone, with its condition written before it ran: no read after the push gives true. It failed |
| The first run's timings | `trials/P-40.json` by REST and `trials/P-40.graphql.json` by GraphQL, two pull requests read every 15 s for 5 minutes. The push was answered at 05:05:30Z. The one that still merges, read in that second, gave true, and true at every read after. The one the move makes conflict, read a second later, gave null, and false from the next read, 16 s after the answer. GraphQL gave `UNKNOWN` for both a second after the answer, and each worked out at the next read | It read the conflicting one a second after the other, so it caught no stale true of it |
| `merge_commit_sha` | The pull request that still merges kept the `merge_commit_sha` it had before the move at all 21 reads; GraphQL's `potentialMergeCommit` was null at the first read after the move and the same commit at the 20 after it. That failed the first run's third condition. Nothing in the Factory reads either field | `adapters/pull.py` takes `mergeable` alone, and reads the base's head from the branch, never from `base.sha`, which did not move in either run |
| The Kernel | Changes nothing. It reads `mergeable` at every pass and keeps nothing of an earlier read: true goes on, null defers, and false is the author's turn and takes a queued pull request out | A stale true cannot be told from a true one. A wait after every move of the base would hold every open pull request at each merge to `main`, for a window one run measured |
| What stands for the read | The next pass, which reads the conflict; and the merge queue, which merges a pull request only as built on the base it finds | The first is the Kernel's own and is held below. The second is GitHub's |
| Residual: what a pass in that second does | It acts as for any head that merges: it may admit a review Run or the owner's ruling Run, resolve a Lens's thread, or enqueue. An approval takes two such reads, since the approving act asks the Kernel again on a read of its own. A Run is counted at the Run ceiling as any is, and an approval of a head that must change is dismissed by the fix's push | The merge state gates no Lens: a stale true gets a head nothing a true one would not get for the same content, and nothing unmergeable lands by it |
| Residual: an enqueue not shown | The enqueue and a thread's resolution are the queue App's acts, which read only that the pull request is open at the head the pass read, and are not asked of the Kernel again. So a pass in that second may enqueue an approved head that now conflicts. No trial here shows what the queue answers to that. "Trial: what does the merge queue answer to an enqueue of a head that conflicts with its base?" (issue 812) asks it; if the queue keeps or merges such a head, a record says what stands for the read then | P-2's fixtures show the queue merging, ejecting, and refusing a push and a draft, and none enqueues a head that conflicts |
| Residual: the explorer | `tests/test_transitions.py` still makes `mergeable` unknown at once when the base moves, so it reads a conflict only two moves after a head that merges. "The transitions explorer reads a conflict only two moves after a head that merges, and one move finds a Hold the Lifecycle does not declare" (issue 811) holds the move and what it finds | The move finds a Hold from `addressing` that the Lifecycle does not declare, which is a ruling of its own |
| Residual: the other way | A conflict that a base move clears would, by the same reading, read false for about a second: a fix Run admitted, or a dequeue. Neither run asked it | Neither act lands anything |
| What the runs do not say | How long the stale read lasts under load, what a pull request reads that nobody reads for minutes after the move, or what follows a merge by the queue, which is how `main` moves: both runs moved a branch by one commit through the contents API on a quiet repo, and read at once and often. Apps installed on the canary commented on each pull request and edited its description while the runs read; none pushed to a head, and in the second run nothing was written between the last read before the move and the first false after it | Two runs on one day in one repo |

## Why

The design held that the merge state is as GitHub last worked it out, and the Kernel treats a null as unreadable. The trial shows a third case that neither names: for about a second after the base moves, the read is a definite answer that is no longer true. The Kernel is a function of what it is given and cannot see that. What it can do is what it already does, read again at the next pass, and what is left between the two is one Run or one approval, or an enqueue that the queue is taken to refuse. That last is written down as not shown, with the issue that asks it.

## Boundaries

| Boundary | Check |
|---|---|
| Where nothing read before a conflict stops it, an approved pull request read as conflicting is its author's turn at that pass, whatever an earlier pass read; one in the queue is taken out by that pass's act; and one whose merge state is not worked out stays in it | `tests/test_decide.py::test_a_conflict_read_a_pass_late_is_the_authors_turn_at_the_next_pass_and_leaves_the_queue`, `kernel/derive.py`, `tools/mutants.py`, mutant: "an approved head that conflicts is not sent back to its author", mutant: "a queued pull request that conflicts stays in the queue" |
