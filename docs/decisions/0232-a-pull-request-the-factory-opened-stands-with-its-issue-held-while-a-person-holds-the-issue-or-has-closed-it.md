# 0232. A pull request the Factory opened stands with its issue: held while a person holds the issue or has closed it

Status: accepted. The Factory Builder's rulings of 2026-11-18 on "On a person's hold or close of an issue, the Controller dequeues the Factory's pull request for it (decision 0003's row)" (issue 850), from the Maintainer's ruling on "Design: does a merge end a held or a declined issue? The issue world met it on seeds 20, 22 and 99" (issue 227).

## Decision

| What | Decided | Because |
|---|---|---|
| Who decides | The Kernel: a rule of `kernel/derive.py` holds the pull request on a fact of how its issue stands. The Controller fills the fact and decides nothing | A dequeue is the Kernel's own act, under the Pause, the dequeue ceiling and the check for one in flight; one the Controller planned would pass none of them |
| The fact | `facts/1` may carry `issue_stands`: `open`, `held`, `closed`, or null where it was not read, as `stands` below gives them. Not required, as `opened_for` is not | Facts made before it, an eval set's among them, name no issue, and the rule reads it on no other pull request |
| The rule | A pull request with `opened_for` an issue's number is held, `issue_stopped`, while `issue_stands` is `held` or `closed`, with that word as evidence; a queued one is dequeued as any held item is. `open` stops nothing | No merge lands while the issue is held or declined (decision 0003's row), and no Run is admitted: a person stopped the work |
| What cannot be read | With `opened_for` an issue's number, an `issue_stands` absent, null or any other value is `issue_stands_unreadable`: deferred, nothing admitted, a queued one dequeued | An unreadable fact yields a deferral or a Hold, never an action |
| Where it is read | After the pull request's own hands-off and a person's Hold on it, before anything admits a Run or converges. A merged or closed pull request is ended however its issue stands | Either Hold names who must end it, and the item stops whichever is read first. Under a person's hands-off a queued pull request stays queued however its issue stands: the Factory never acts under it (decision 0139, row 1) |
| Who needs to act | A person, for both reasons. `config/feed.json` asks of `issue_stopped` its own question (end the Hold, reopen the issue, or close the pull request), and of `issue_stands_unreadable` what it asks of any unreadable fact | Only a person ends what a person placed on the issue |
| How an issue stands | `kernel/issue.py`'s `stands`, from the issue's state and its own label events alone: `closed` while GitHub says so, whoever closed it; `held` while a Hold stands on it, whoever placed it, or hands-off anyone but a person placed; `open` otherwise, and under a person's hands-off, a Hold beside it too; None for a state GitHub does not give, or label events read short or not whole. No row of the issue's own reading is read: served or not, linked or not, a Hold on the issue stops its pull request | Who placed a label is the Kernel's reading. The Factory's merge ends the pull request before it closes the issue, so a closed issue beside an open pull request was closed some other way and waits for a person, the side that fails safe. A person's hands-off keeps one meaning, as in row 5; the cost, ruled: under it the pull request goes on being served. The issue's own rows read being served before a Hold, which would let a pull request go on under a Hold on an issue left out |
| The join | The Controller fills the fact, in the part the last boundary row waits on: for each open pull request with `opened_for` N it reads issue N's own facts, served or not, open or closed, never its linked pull requests, and asks `stands`; one it cannot read gives null. The facts port gives none of it. `stands` is the one entry point the Controller gains | `opened_for` names exactly the pull request the Factory opened for that issue. A closed issue is in no list of open issues, so it is read for the pull request's sake |
| The bound | One read of an issue for each open pull request the Factory opened, and no more | The reads grow with the Factory's own open work, never with the issues of the repo |
| The simulator | Its agent's pull request says its issue stands open in every world; the explorer, `tests/test_transitions.py`, makes the hold, the close and the letting go | The world's draws, and so every pinned seed, stay as they were. The Lifecycle declares each change of State the rule makes |

## Why

The Maintainer ruled that a person who holds or closes an issue has stopped its work, and the Factory's pull request for it must not merge behind them. The Kernel already dequeues a held pull request; what was missing was a fact that says the issue is held. In the Kernel the rule keeps one place that decides, and one set of brakes on the act.
