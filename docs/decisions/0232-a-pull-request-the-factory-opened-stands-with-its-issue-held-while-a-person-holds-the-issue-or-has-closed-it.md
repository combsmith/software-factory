# 0232. A pull request the Factory opened stands with its issue: held while a person holds the issue or has closed it

Status: accepted. The Factory Builder's rulings of 2026-11-18 on "On a person's hold or close of an issue, the Controller dequeues the Factory's pull request for it (decision 0003's row)" (issue 850), from the Maintainer's ruling on "Design: does a merge end a held or a declined issue? The issue world met it on seeds 20, 22 and 99" (issue 227).

## Decision

| What | Decided | Because |
|---|---|---|
| Who decides | The Kernel. A pull request's facts say how its issue stands, and a rule of `kernel/derive.py` holds the pull request. The Controller joins the two and decides nothing | A dequeue is the Kernel's own act, made under the Pause, the dequeue ceiling and the check for one in flight. A dequeue the Controller planned itself would pass none of them |
| The fact | `facts/1` may carry `issue_stands`: `open`, `held` while a person's Hold stands on the issue, `closed` once a person closed it, and null where it was not read. It is not required, as `opened_for` is not | Facts made before it, an eval set's among them, name no issue a pull request was opened for, and the rule reads the fact on no other |
| The rule | A pull request with `opened_for` an issue's number is held, `issue_stopped`, while `issue_stands` is `held` or `closed`, with that word as its evidence. A queued one is taken out of the merge queue by the act that takes out any held item. `open` stops nothing | No merge lands while the issue is held or declined (decision 0003's row). Held, the pull request admits no Run either: a person stopped the work |
| What cannot be read | With `opened_for` an issue's number, an `issue_stands` that is not there, null, or any other value is `issue_stands_unreadable`: the item is deferred, admits nothing, and a queued one is taken out, as on any read that failed | An unreadable fact yields a deferral or a Hold, never an action |
| Where it is read | After the pull request's own hands-off and a person's own Hold on it, and before anything admits a Run or converges. A merged or closed pull request is ended however its issue stands | A person's Hold on the pull request names who must end it, and so does the issue's; whichever is read first, the item stops. Hands-off is the one reading that stops nothing of a queued item: the Factory never acts on what a person marked hands-off, so a queued pull request under a person's hands-off stays queued however its issue stands, as it does under every other rule |
| Who needs to act | A person, for both reasons. `config/feed.json` asks of `issue_stopped` a question of its own, with the ending of the Hold, the reopening of the issue and the closing of the pull request as its choices, and of `issue_stands_unreadable` what it asks of any fact that cannot be read | Only a person ends what a person placed on the issue |
| The join | The Controller fills the fact, in the part the last boundary row waits on: for each open pull request with `opened_for` N it reads issue N, served or not, open or closed, and says how it stands. An issue it cannot read gives null. The facts port gives none of it | `opened_for` names exactly the pull request the Factory opened for that issue. A closed issue is in no list of open issues, so it is read for the pull request's sake |
| The bound | One read of an issue for each open pull request the Factory opened, and no more | The reads grow with the Factory's own open work, never with the issues of the repo |
| The simulator | Its agent's pull request says its issue stands open, in every world: no person holds or closes the issue there. The explorer, `tests/test_transitions.py`, makes the hold, the close and the letting go | The world's draws stay as they were, so every pinned seed does. The Lifecycle already declares each change of State the rule makes |

## Why

The Maintainer ruled that a person who holds or closes an issue has stopped its work, and that the Factory's pull request for it must not merge behind them. The Kernel already takes a held pull request out of the queue; what was missing was a fact that says the issue is held. Keeping the rule in the Kernel keeps one place that decides, and one set of brakes on the act.
