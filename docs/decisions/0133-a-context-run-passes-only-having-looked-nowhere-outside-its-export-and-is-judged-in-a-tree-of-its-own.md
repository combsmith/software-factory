# 0133. A context run passes only having looked nowhere outside its export, and is judged in a tree of its own

Status: accepted. Replaces `docs/decisions/0129-the-contexts-task-is-held-by-its-sentences-sha256-and-a-run-records-whether-it-added-a-test-a-mutant-and-the-code-never-what.md`. The Factory Builder's ruling of 2026-11-03 on "Context test: a run passes only with no outside reads or unreadable commands, and the judge runs the export's mutation runner" (issue 511), from Argon's read of the pull request that built 0129: both gaps are real and close before the three runs of issue 8. It keeps 0129's rows, restated below, but for when the held-out test is placed, how a run is judged and when it passes, and it names what a shell with no sandbox leaves open.

## Decision

| What | Decided | Because |
|---|---|---|
| The task | One Kernel rule the repo does not hold and no `@pending` test states, chosen by four criteria: the design states it; it is one reason code in one Kernel module behind one boundary; it needs no new fact and no new limit; it is decided. Its boundary test is the known answer, written in the private held-out home by a private session. The sentence names the rule and its code and nothing of how. Only the sha256 of each is here, the sentence's taken of its one line with no newline: the sentence and its code are never in this repo, a pull request, an issue or a shared transcript, before the runs or after them | A task whose answer is in the repo measures nothing; as first written the test could not fail. The Maintainer chose that the rule is named nowhere here, so the record carries hashes alone |
| Who runs it, and on what | `tools/context_eval.sh` at the Maintainer's terminal, never CI: the CLI at the pin of 0033, on the configuration directory logged in to his own subscription, headless, with the sentence as its whole prompt, on a `git archive` export of one commit of `main` outside every repo, with a scratch HOME and its login alone, its network tools refused, a cap on turns. Its shell is not sandboxed, since trial P-26 found that the CLI's sandbox hands a tool the parent's environment: the record counts each path it named outside the export, by a tool's path, a command or a glob (an absolute path not the export's, the home, or the parent), and each command it could not read, and a run that did either does not pass. Every clone of the private home on this machine is moved out of reach first, and the runner refuses to start while a place `CONTEXT_EVAL_AWAY` names exists or while it names none; the held-out test is not on the machine while the agent runs, since the runner refuses a HELD_OUT already there and waits, once the agent has stopped, for the Maintainer to fetch it and place it. A shell with no sandbox still cannot be shown not to have read something on the machine: the answer's absence and the count narrow that, and do not close it | CI runs no model and fetches nothing; the credential lives where 0033 put it; an export has no history, remote or other checkout to read from; what cannot be confined is counted, so a run that looked elsewhere says so, and a run that may have read the answer proves nothing; what a record cannot prove is said, not claimed |
| How a run is judged | After the agent stops, the runner, not the agent, in a tree of its own made fresh beside the agent's: the export as made, with the agent's own text files under `kernel/` and `tests/`, a link among them left out, and `tools/mutants.py` as made with each entry the agent added to one of the lists `MUTANTS` is made of, in that list, and each it changed in place of the one of its name. An entry is held to data alone (constants, names, tuples and lists, strings joined, a star, the file's own helpers and a string's `replace`), so the mutation check runs the export's own runner. Everything else the agent changed, a package or a module that would shadow one the judge runs, an entry that is code, an entry it took out, is left out of that tree and recorded as put back, by where. Then the held-out test, placed by the Maintainer, copied in, run on its own and taken out again; `make verify`; the whole mutation check, which must kill every mutant, the agent's among them, and whose runner reads whether a named test exists in a process of its own, so a test module's import never runs in the runner's. A run passes on all three, having named no path outside its export and run no command that could not be read; the story passes at three of three | The held-out test says whether the rule is the one asked; verify says the change is finished; a killed mutant says the agent followed the three-part rule and not only made a test pass, and only if the runner that killed it is the export's and nothing of the agent's ran beside it |
| What a run records | A `context-eval/1` run in `evals/context/task.json`: the commit, the date, the CLI's version, the cap and the task sentence's sha256; the paths read, and of each command its program, its flags and the paths and modules the export as made holds, from the transcript's tool uses alone, a word shaped like a token never recorded; a file the export as made does not hold, made or only named, by its folder alone; how many paths were named outside the export and how many commands could not be read; what changed, by file, in lines, a file the export does not hold under its folder, and what of the judge's was put back; whether the agent added a test, a mutant and the sentence's reason code on a line of the Kernel, three booleans and no name; the result's counts, null when the CLI gave none; the three verdicts. Of the model's text only those words, each held to a pattern: never a text block, a tool's result, a prompt, an answer, or a name the agent chose. Nothing the runner leaves in OUT or prints names the sentence, its code, or the test or mutant the agent added | What CI can hold is a fixture of the runs, honest about what it holds; a word of the model's would leak the answer, and a name the agent chose for its test, its mutant, a file or a search, or the code, would name the rule. An existing file the agent changed, the one Kernel file it edited among them, is kept by its path: it is the repo's own name and says where, not what, which the Factory Builder accepted |
| A failed run | Recorded too; the context changes, never the task, in a pull request of its own that names the failed run; then three fresh runs. The test counts the newest three on the task's sha256 | The measure is of the context; a task changed after a failure would be the proof of concept's stub again |
| A later change to the context | Re-run at the Maintainer's call, not by CI; the record's commit says what was tested | CI cannot run a model, and cannot tell which change to the context matters |

## Why

Slice 0's exit is that an agent given only the repo and one sentence adds a rule to the Kernel and passes the required
check (design §9.1, §9.14). Nothing in CI can run a model or read the private home, so the test is two things: a
runner that makes and judges the runs where the model and the answer are, and a record in the repo that a test in
`make verify` holds. 0042 kept the sentence out of the repo only until the runs were recorded, and recorded the code
and the names the agent chose. The Maintainer chose that the rule is named nowhere here, so the sentence is held by
its sha256 as the answer is, and a run says whether it added each part, which is what the test needs, and not what.
