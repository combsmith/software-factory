# 0102. A pull request is opened from this repo by an account the configuration lists

Status: accepted. The Maintainer's approval of 2026-10-30, for "Identity: a keyless check that the pull request's opener and head repository are the Maintainer's (raised by 0087's review)" (issue 409). It extends `docs/decisions/0087-the-commits-job-holds-the-name-each-commit-carries-and-a-forged-name-is-a-risk-the-maintainer-accepts.md`, taking the option C it left not yet weighed. What 0087 holds of the commits' names stands, and so does its refusal of A and B.

## Decision

| What | Decided | Because |
|---|---|---|
| What is refused | A pull request whose opener is not on the list, by its login and its id, or whose head repository is not this repo: a fork, the Maintainer's own among them, or one GitHub no longer names. A payload, a list or an answer that cannot be read refuses too | GitHub writes both values, and the commit's maker writes neither |
| Who may open one | `openers` in `config/hooks.json`, as the base holds it, each with what the account is: today the Maintainer alone. The id is read beside the login, since a login can be renamed and taken. So a listed account that renames itself is refused, the pull request correcting the list among them, since the job reads the base's list: the way out is to rename it back, or for a person to change the ruleset. A refusal names everyone on the list and what each is | The list sits beside the Maintainer's name, on a path a change cannot take itself off (decision 0020) |
| When the Factory opens its own | A record adds that App's login, `name[bot]`, and its bot account's id, as the payload gives it in `user.id` and never the App's own id, to `openers`, when an Intent can open one. The schema and the check already read such a login, and nothing else changes. It lands with the writer of decision 0097 | The opener is then not always the Maintainer, and each account is added by a decision |
| Where it reads them | On a pull request's event, the event's payload, the file the runner leaves at `GITHUB_EVENT_PATH`, and not values the job is given, as 0087's option C had it. So a pull request another account opened fails early, on its own run. On a merge group, whose payload names no opener, the pull request the queue's ref names, read from GitHub | A job's env is written in the workflow a pull request can change; the payload is not, though the step that reads it can be (below) |
| Where it runs | Inside `tools/commits_are_the_maintainers.py`, the `commits` job's one step, which prints the refusals of both and passes only on both, saying what it held only then. The commits are read just as before. The job gains `pull-requests: read` and its own token by name, and no other permission, and its shape holds that. The read goes through `adapters/github.py` | A new job runs the base's tool, which the pull request adding it would not find, and it would fail itself; decision 0041's tool took two pull requests for that |
| A pull request retargeted | Caught at the queue, not on the pull request. A retarget starts no run, so a pull request opened against a branch that holds an older tool or its own list keeps its green check on main. A merge group always runs main's tool and main's list, so it reads the opener there and refuses. The commits of such a pull request go back to the gap decision 0087 states: the merge group reads the queue's own squash commit, not theirs | The Factory Builder's ruling on the security pass, between this and `edited`. No form of `edited` is safe and cheap: one that skips the job on a body edit leaves the required check red or, skipped whole, reads as passed (decision 0022), and one that does not skip runs the whole check on every title or body edit |
| On a merge group | The ref must be `refs/heads/gh-readonly-queue/{base}/pr-{n}-{sha}`, whole, naming exactly one pull request, on the base the group merges to. The answer must be that pull request, open, on that base. Anything else refuses, with a code: `merge_group_unreadable`, `merge_group_ref_unreadable`, `merge_group_pull_unreadable`. Each entry in the queue runs a group of its own, whose ref names it, as this repo's queue and P-2's show | An unreadable fact never passes. Reading here means no reliance on the queue refusing a pull request whose required check failed, which is not tried |
| A and B | Still not taken. Either needs the Maintainer's key in every checkout a builder commits from, and B's effect on a squash through the queue is not grounded (0087). This stops a forger from outside who leaves the workflow alone. "Keyless" in the issue means no signing key to keep: the job's read-only `GITHUB_TOKEN`, which GitHub mints and ends with the job, is within what the Maintainer approved. B, a ruleset's rule, would not be undone by rewriting the workflow, though A's check would | The Maintainer's choice in 0087 stands, and this asks nothing of it |
| What it does not hold | That the Maintainer opened it: a holder of their login passes, as every builder here does by design. Who pushed: the opener is fixed when the pull request opens, so an account with write that pushes to a listed opener's branch passes, and its commits are held only to the names they carry. A pull request that rewrites `.github/workflows/verify.yml` can rewrite this job, since `pull_request` runs the workflow its merge commit holds; `.github/` is on the list, a change to it needs a model Lens, and an outside one waits on a person (`outside_not_admitted`), each the Kernel's and none GitHub's, since the ruleset requires `verify` alone. Not tried | A rule says what its check holds, and no more |

## Why

0087 left a forged name to the one gate a forger from outside meets, the Kernel's admission. This puts a second in front of it, at the required check, for no key and no token: a fork's forged commits now fail on who opened them, whatever names they carry, unless that fork also rewrites the workflow. It also stops an account inside the repo opening under its own login, which the commits' names never could, though not pushing to a pull request a listed account opened.
