# 0219. A Run that writes code hands over a patch by its digest, `apply` alone pushes, and the item's own checks on the draft are its build

Status: accepted. The Maintainer's ruling of 2026-11-13, given in chat to the Factory Builder and posted on issue 314. To "which shape should slice 2 build on?" he chose "Shape C (Recommended)", whose option read "No Intent gets a tool: the model answers with a patch, and the item's own checks on the draft serve as the build". To "Which Role's App opens the Factory's draft PR?" he chose "qa-lead (Recommended)", whose option read "qa-lead's Run writes the one commit and opens the draft". Asked the same day whether "No Intent gets a tool" means no tools at all or no tool that runs code or writes, he chose "No run/write tools (Recommended)", whose option read that the implementing Run keeps read-only tools held to its head but has no tool that runs code or writes; the Factory Builder posted it on issue 314 beside the first ruling. It takes the Solution Architect's read of 2026-11-03 and the design record draft of 2026-11-13, both on "Design: a Run with tools cannot both hide the model credential and hold writes (P-26, P-50, P-51); choose the run job's shape before the first Intent with tools" (issue 314), in shape C's narrowest form, as the Solution Architect's ruling on slice 2's draft (rulings-422, section 3) gives it.

## Decision

| What | Decided | Because |
|---|---|---|
| The gap | The CLI's sandbox cannot both hide the model credential from a tool and keep a tool's writes inside its directory. Without the scrub, a tool reads the parent's environment, the credential among it (P-26, P-50). With the scrub, every write outside the work directory lands (P-51). So no Run that holds the model credential holds a tool that runs code or writes | Three trials at the pin, 2.1.306, on macOS and on `ubuntu-24.04` |
| The shape | C, in its narrowest form. No Intent gets a tool that runs code or writes: the model answers with a patch. A Run that produces a change has the read tools alone, held to a head, as the review has them (decision 0138, whose rule decision 0151 holds in force), so that it reads the code it changes; it has no shell. No `build` job or workflow of the Factory's runs the item's code. The item's own checks on the draft, its required checks on the head the patch was pushed to, serve as `build` | It is the one shape whose security needs no trial of a sandbox: the item's code runs only where it runs today, in the item's own checks, which hold no model credential and no write credential of the Factory's. The Maintainer's option named the Solution Architect's recommendation, whose narrowest form gives the implementing Run the read tools held to a head and no shell (rulings-422, section 3) |
| No build where the item's code could reach the model credential | Nothing of the Factory's runs the item's code on a hosted runner where the model credential, or a token that writes the Run's own artifacts, could be reached. On a hosted runner a job has passwordless sudo (decision 0053), so the item's code in a job of the Run's own workflow run could read `ACTIONS_RUNTIME_TOKEN` and upload an artifact under one of the Run's names, an `outcome` before the real one (unverified) | The Solution Architect's caveat of 2026-11-03 |
| The hand-over | The Run hands over its patch as an artifact, named by its digest. `apply` alone pushes it, through the Role's own App (decision 0005), taking the bundle only by its digest and refusing a push that touches the base's list, as decision 0188 holds, which also refuses a push that touches `.github/`, so no patch adds a workflow that reads a secret. The model process holds no write credential | FR-10 and FR-60. The hand-over is the same in every shape, so the pushing Intents can be built while a wider shape waits |
| One round, one Run | Each round of test and fix is one Run: the model cannot run a test and react within a Run. While the draft the Factory opened fails its required checks, the issue admits another implementing Run, bounded by `max_attempts` and `max_runs_per_item` (decision 0217). Before another shape is reached for, the bound on implementing rounds, `max_attempts` for `implement`, is raised | The Solution Architect's read: the price is iteration across Runs, which the Lifecycle already bounds and the records show |
| What the checks say | The draft's required checks are facts, read by their conclusions alone. Nothing here gives the model what the item's code printed in them. If a later record does, it enters a Task as `outside` text alone, never as evidence or a gate (FR-11) | The item's code wrote it |
| A hang | A failing required check of the item's, one timed out among them, is the item's: it admits an implementing round, bounded as above, and never counts toward the automatic pause, or an outsider could pause the Factory. A check that gives no verdict, cancelled at its job's limit among them, is read as decision 0098 and trial P-42 have it, not as a round. The model's Run, which runs no code, is read on a timeout as decision 0136 reads it today | Once code runs, the item can hang it. The model's Run runs none |
| Who opens the draft | `qa-lead`'s Run writes the first commit on the work's branch, the acceptance contract and its failing tests (section 4.8), as one commit handed over as the hand-over row says; its `apply` alone pushes it and opens the draft through `qa-lead`'s own App (decision 0005). So section 4.1's recovery holds: an opening `apply` that dies after its push leaves the whole commit on the branch, and the next finds the branch at the commit the handed-over patch makes, by its digest, pushes nothing, and opens the draft from it. A branch at any other commit is refused, and no draft is opened from it. `dev-lead`, `author_role`, authors after, its implementing Runs pushing to that draft | It closes section 4.1's open question, which Role's App opens the draft when `qa-lead` writes its first commit and `dev-lead` is the declared author |
| Owed by the Maintainer | `qa-lead`'s App, `combsmith-sf-qa-lead`, registered and installed as the Maintainer's own act, before `qa-lead` runs live; `dev-lead`'s before its implementing Runs do. Nothing here waits on either to be built | An App's registration is an org setting under his login |
| A wider shape later | A `build` workflow of its own, with `permissions: {}`, no secret and no cache, running only the Consumer entry's setup and test commands read from the base, waits until the cost in Runs shows it is needed, and then needs its isolation trial in the canary. Shape B, the model's tools as an MCP server of this repo's own in a container with no network, comes after that. Shape A, tools inside the CLI's own sandbox, never at this pin. A newer CLI build and a self-hosted runner are not pursued | The Solution Architect's order: C first, then B, A never at this pin |
| What is left | Each lands with its own check: the push's write, which `harness/AGENTS.md` names as not built; the grants in `config/apps.json` for `push_commits`, `open_pull_request` and `mark_ready`; `qa-lead`'s Role and its opening Run, with the `open_pull_request` Effect; `dev-lead`'s implementing Run and FR-14's guard; the facts port's read of a draft's checks (decision 0217); `result/1`'s patch field; sections 3.5, 3.6, 3.10, 4.1, 4.9 and 9.9 of the design brought into line. And before a Role's patch is pushed to a branch whose checks run with a secret, no such check takes its configuration from a file a patch may change, a file that says what the check runs or where it sends what it holds, as against the source it only analyses; and no check that runs a file a patch may change, its tests among them, holds a secret in that job, since no list can keep a patch from the code the job runs: `sonar-project.properties`, which `.github/workflows/sonarcloud.yml`'s scan reads beside `SONAR_TOKEN`, is on no list today ("Security: the SonarCloud scan reads a pull request's sonar-project.properties beside SONAR_TOKEN, and no list protects the file", issue 845) | This record decides the shape; it builds none of it. The Claude review of this record found the scan's file |

## Why

The fix and implement Intents of slice 2 need code run: a build, the tests. Run as the model's tool, that code and the model's credential share one process tree, the case every trial at the pin failed. Run as the item's own required checks on the draft, it needs no new job of the Factory's, no sandbox trusted, and no credential near it. The model hands over a change by its digest, `apply` pushes it, and the checks' verdict admits the next round. It costs a Run for each round, which the Lifecycle already bounds. A `build` workflow of the Factory's own waits until that cost is shown.

## Boundaries

| Boundary | Check |
|---|---|
| `apply`'s push lands exactly the patch the Run handed over, by its digest, on the work's branch, through the Role's own App | waiting on `harness/push.py`, the push's write |
| `qa-lead`'s opening Run hands over one commit, the contract and its failing tests, which its `apply` alone pushes before it opens the draft through `qa-lead`'s own App; a retry after the push finds the branch at the patch's own commit, by its digest, and pushes nothing; one at any other commit is refused and opens no draft | waiting on `harness/push.py`, the push `apply` makes before the `open_pull_request` Effect |
| `dev-lead`'s implementing Run answers with a patch and pushes nothing itself | waiting on `harness/push.py`, through which alone its patch lands |
| No Role's patch is pushed to a branch where a check that runs with a secret takes its configuration from a file the patch may change, the scan's `sonar-project.properties` among them; the source such a check only analyses is not such a file. Nor to one where a job that runs a file the patch may change holds a secret | waiting on `harness/push.py`, whose refusal of a push that touches the base's list must cover each such file first |
