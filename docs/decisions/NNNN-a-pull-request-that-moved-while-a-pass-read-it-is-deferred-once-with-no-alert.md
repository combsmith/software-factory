# NNNN. A pull request that moved while a pass read it is deferred once with no alert

Status: accepted. The Factory Builder's ruling of 2026-11-08 on issue 658, "Controller: a pull request that changes while a pass reads it raises facts_unreadable and reconciliation_unreadable, though Moved means read it again". From 2026-11-08 05:38Z, Factory alerts were opened seven times and closed within minutes. Each time, one pull request had merged, taken a commit or taken a comment less than a minute before the pass read it. The snapshot raised `Moved`, which means "read it again at the next pass". The entry took it as any read GitHub did not answer, so it raised `facts_unreadable`, and the item's writes, never read, left reconciliation short. It adds a grace pass and amends nothing else: decision 0056's tracking issue still opens on a pass's first cause.

## Decision

| What | Decided | Because |
|---|---|---|
| Why an item is left out | `pass/1` keeps `left_out`: each item the pass left out, in the order read, with its code. `pull_moved` is a snapshot that moved while it was read. `facts_unanswered` is any other read the facts port could not make. `not_facts` is facts that do not hold to their schema, and `listed_twice` an item listed twice, whatever its read said. The item is null where none can be named. A record written before it holds none | The cause is seen in the record, not inferred: which read failed, on which item |
| The grace pass | A pull request whose code is `pull_moved`, and which the last pass record read did not leave out as `pull_moved`, is deferred with no alert: no facts, no Decision and no act, as now, but not `facts_unreadable`. Its writes are not read in this pass. They are owed to the next, as a pull request read short is, so this reconciliation stays whole. The pass its change started, through `workflow_run`, reads it again | A merge, a push or a comment during a read is the Factory working, not a fault. A person assigned to an issue that closes itself minutes later learns nothing from it |
| What still alerts at once | A second move in a row. Any other code. A last record that cannot be read, that is not there, or that holds no `left_out`: it cannot say the move is a first, so the move counts as a second | Something that never settles still reaches a person, and only `Moved` earns the grace. A pass fails closed |
| Derived, never kept | Whether a move is a first is read from the last pass record at each pass, in `controller/pass_.py`'s `moved_once`. The entry asks the same of it to leave the owed writes unread | State is derived from facts and run records at every call, never stored |
| Not here | `adapters/checks.py` still raises a plain `Unanswered` when the head moves while the checks are read. That read shows as `facts_unanswered` and alerts at once. Making it a `Moved` would also change how the approving act classes it | The record's codes will show whether it happens. It is a change of its own |

## Why

The tracking issue is how the Factory's faults reach the Maintainer. Seven alerts in a day for pull requests that were only changing would teach him to ignore it. Deferring a moved pull request for one pass keeps the Kernel's rule: an unreadable fact defers. Raising it on the second move keeps the alert for what does not settle.
