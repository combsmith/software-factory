# 0242. Implementing rounds have a limit of their own, and the first opening push lands on the default branch's head its admission carries

Status: accepted. The Factory Builder's rulings of 2026-11-20, from the Solution Architect's, on "An implementing Run's attempt bound, and the base commit the first opening push is held to" (issue 1038), the follow-on to issue 952: the two points that decision 0239, "Push is granted only where no secret-bearing job runs what a patch may change, no Run holds a tool that runs code, and a later opening Run opens from the branch", left to a record of their own. It gives decision 0219's row "One round, one Run" the bound for `implement` it raised, reads decision 0217's Hold of the implementing rounds at `max_attempts` as a Hold at that bound, and says for decision 0188's list and decision 0238's opening where the first opening push is read and where it lands. The rest of 0217, 0219, 0238 and 0239 stands.

## Decision

| What | Decided | Because |
|---|---|---|
| The rounds' own limit | `limits.max_implementing_rounds`, a required key of `config/defaults.json`, starting at 3, bounds an issue's implementing rounds. `kernel/brakes.py`'s `implementing_rounds` reads it, and nothing else does: no other loop reads it in place of its own key, and it reads no other key in its place. `max_attempts` does not move | 0219 raised `max_attempts` for `implement`, a bound for one Intent that does not exist: `limits.max_attempts` is one number, and it bounds every loop in the brakes, so raising it would raise every Intent's attempts with it |
| What 0217's and 0239's Hold now means | Decision 0217's `max_attempts` Hold of the implementing rounds (its row "The bound" and its first Boundary row), and any `max_attempts` Hold decision 0239 reads for implementing, is now at `max_implementing_rounds`. Its reason stays `attempts_exhausted`, with the rounds as evidence, calling a person, with a Run in flight or none. `attempts_exhausted` is unchanged for every other loop: an implementing Run's own attempts, the Runs of it that failed by a fault of the item, are still held at `max_attempts` through the brakes, as every Intent's are, and so is the opening Run's that 0239's row "A later opening Run" ends at | A round is any implementing Run that completed, whatever it concluded; an attempt is one that failed by the item. The two counts are kept apart, and only the first gets the new key |
| An implementing Run that keeps failing | `max_attempts` still holds an implementing Run that keeps failing, whatever `max_implementing_rounds` is, through the brakes, as it holds every Intent's: raising the rounds above `max_attempts` lets no failing Run go round past it. An attempt is an implementing Run that failed by a fault of the item; a round is one that completed, whatever it concluded, admitted while the draft's checks failed. A Run that failed by the item is both, and is counted by each | The Solution Architect's ruling on this record's draft: the rounds' key bounds the test-and-fix loop, never the item's own failures, which `max_attempts` bounds for every Intent |
| A key that cannot be read | A key missing, null, or no whole number of at least one, holds the issue, `limits_unreadable`, calling a person, with a Run in flight or none, naming no Run. It is never read from `max_attempts` or any other key | An unreadable limit yields a Hold, never an action; a fallback to another key would bound the rounds by a number no one chose for them |
| Its relation to the Run ceiling | `tools/check_lifecycle.py` counts it among the limits the Kernel keeps for each item, as a bound only the issue's Lifecycle may name, and holds it a whole number at or below `max_runs_per_item`, a Run ceiling that is no whole number holding nothing under it. The Run ceiling bounds the rounds as it bounds every Run, and the Lifecycle's termination stands as `tools/check_lifecycle.py` shows it | Each round is a Run, so a limit past the Run ceiling would never be reached, and could be read as raising the cost ceiling |
| Who raises it | Raising `max_implementing_rounds` above 3 is the Maintainer's, by hand, as every change to `config/defaults.json` is | 0219's "is raised" names no number; the key is a model Lens's input and the brakes' limit |
| The order it lands in | The key goes into `config/defaults.json` and `schemas/config.schema.json` by hand first, with nothing reading it. Then this record, the brakes' read of it, its check and its mutants go by the Factory's route | A Kernel that read a key main lacked would hold every implementing round, and its tests would fail on main; a key no code reads yet changes nothing |
| The first opening push's base | An opening Run admitted with no branch head, before any branch or pull request exists, lands its patch's commit on the default branch's head as the Run's admission carries it, and the work branch is made at that commit. It is never read from the work branch, the Result or the default branch at the push | 0238 names only the admitted branch head, of which there is none here, and the default branch as the draft's target; neither 0219 nor 0238 says on which commit the first push lands |
| What the push checks | At the push, harness/push.py, not yet built, reads the default branch's head and, before `push_commits` is used, tells three cases apart: the admitted sha is that head, and the push goes on; it is an ancestor of that head, and the push goes on; it is neither, and the push is refused and nothing is pushed. A later record may name the refusal's code and fault, and may not narrow the three cases. Decision 0188's list is read both at the admitted commit and at the default branch's head at push time, as 0188 reads it, and a patch that touches a path on either list is refused, `push_protected`; either list that cannot be read is `push_list_unreadable`, as 0188 has it. Decision 0239's read of the workflows at the commit the patch lands on is, at the first opening push, the read of those at the admitted sha, beside the default branch head's: a job there that holds a secret, as 0239 says one does, and runs or takes its configuration from a file a Factory patch may change, refuses the push. The checks hold the write: the work branch's ref is made only while the default branch's head is the one the checks read. harness/push.py makes the write wait on that, and where the head has moved since, reads it and checks again, or refuses | The default branch can move between the admission and the push: a path protected, or a model Lens named, since the admission would otherwise be pushed, and one taken off since cannot let the patch through either. A sha that is no ancestor of the default branch's head was rewritten away, and a patch on it lands on a history the repo no longer holds. The branch made at the admitted sha runs that commit's own `on: push` workflows, which can be an older base's that still holds a secret. A check the write does not wait on holds nothing once the head moves between them |
| A moved base | A default branch that moved past the admitted sha refuses nothing else: the patch lands on the admitted sha, and the draft opens to the default branch as any pull request whose base has moved. `applied/1` is unchanged | 0239's row "A later opening Run" reads a moved base as ordinary for any open pull request, and a conflict as the fix Run's to handle |
| The admission's base | `issue-facts/1` gains `default_head`, required: the sha of the default branch's head, or null where it could not be read. The issues port reads it once for each repo in a pass and gives it to each issue's facts. The opening Run's admission in `issue-decision/1` carries it as `base` while `branch_head` is null, and never once a branch head exists. A `default_head` that cannot be read defers an opening admission with no branch head, and nothing else | The Kernel can carry only what a fact holds; one read for each repo, not for each issue, spends no more of the rate limit than the pass needs, and an unreadable head stalls only the one admission that would read it |
| What `apply` compares | `apply`'s asking again (`still_admitted`) compares the Role, the Intent, the content and the branch head, never the base. `apply` lands the push on the base of the admission it recorded, never on the base its asking again gives | A moved base is no refusal; a base read again at `apply` would be one the checks above never read |
| When the base lands | The fact, its read, the admission's field, its schema, example and counter-example, its boundary tests and mutants come in a change of their own after this one, by the Kernel procedure, and add their Boundary rows here. Until then no first opening push has an admitted base, harness/push.py is not built, and no Role is named to open pull requests (decision 0215) | Each lands with its own check |

## Why

Decision 0239 left two points of the reader audit of 0219 unsettled. The implementing rounds were bounded by `max_attempts`, which 0219 said would be raised for `implement` alone, though it is one number for every Intent's attempts; a key of their own lets the rounds be raised without raising every other loop, and a check keeps that key under the Run ceiling. And the first opening push had no base commit for 0188's list or for the patch to land on; the default branch's head, carried in the Run's admission, is that base, held to the default branch's history at the push, with both commits' lists read so that neither a protected path added since nor one taken off since lets a patch through.
