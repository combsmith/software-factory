# 0214. A read in the second after a base move may give the merge state of before it, and the snapshot's last read holds it

Status: accepted. The Factory Builder's rulings of 2026-11-13 on "Trial P-40: a move of the base alone makes GitHub work out mergeable again, for a pull request that still merges and for one the move makes conflict" (issue 809), whose trial failed.

## Decision

| What | Decided | Because |
|---|---|---|
| What GitHub does | After a push that moves only the base, a REST read of a pull request gives `mergeable` as GitHub had worked it out before the move for about a second after the push is answered. Then it gives null, and then the answer against the new base. Nothing in the stale read's body says it is stale: its `updated_at`, `mergeable_state` and `merge_commit_sha` are those of the read before the move | Trial P-40, run twice in the canary on 2026-11-13 |
| The second run's timings | `trials/P-40.at-once.json`, one pull request the move makes conflict. The base's commit is dated 05:13:11Z and its push was answered at 05:13:12Z. Reads begun 0.06 s and 0.61 s after that answer gave true; reads begun 1.22 s, 1.83 s and 2.27 s after it gave null; the read begun 2.80 s after it gave false, and GraphQL at 3.32 s `CONFLICTING` | It asks the first second alone, with its condition written before it ran: no read after the push gives true. It failed |
| The first run's timings | `trials/P-40.json` by REST and `trials/P-40.graphql.json` by GraphQL, two pull requests read every 15 s for 5 minutes. The push was answered at 05:05:30Z. The one that still merges, read in that second, gave true, and true at every read after. The one the move makes conflict, read a second later, gave null, and false from the next read, 16 s after the answer. GraphQL gave `UNKNOWN` for both a second after the answer, and each worked out at the next read | It read the conflicting one a second after the other, so it caught no stale true of it |
| `merge_commit_sha` | The pull request that still merges kept the `merge_commit_sha` it had before the move at all 21 reads; GraphQL's `potentialMergeCommit` was null at the first read after the move and the same commit at the 20 after it. That failed the first run's third condition. Nothing in the Factory reads either field | `adapters/pull.py` takes `mergeable` alone, and reads the base's head from the branch, never from `base.sha`, which did not move in either run |
| The snapshot's last read | `adapters/pull.py::unchanged`, the read of the pull request that ends a snapshot, holds the merge state too: where the first read gave true or false and the last does not give the same, the pull request moved while it was read. That is `pull_moved`, deferred once with no alert and read again at the next pass, as `docs/decisions/0172-a-pull-request-that-moved-while-a-pass-read-it-is-deferred-once-with-no-alert.md` has it. A first read that gave no merge state is kept: its facts say it is not worked out, and the Kernel defers on them. Every snapshot ends with this read, not the pass's alone: a base that moves while a Role's Run reads ends that Run as the environment's, counted at its ceiling; while apply reads again, a finished Result is put aside as overtaken; while the approving act reads, no approval is made. Each already did so for a comment that landed while it read, and a second move in a row at the pass is the alert 0172 names | A snapshot makes ten reads or more between its first and its last, and the stale read lasted about a second: the last read is then null or the new answer. It needs no wait, and the Kernel is not asked to tell what one read cannot |
| The port's ground, corrected | `unchanged` compared `updated_at` on the ground that GitHub moves it when the base moves (P-29). It does not: in the second run `updated_at` was 05:13:01Z at the read before the move and at every read through true, null and false. In `trials/P-29.base.json` it moved 50 s after the base did. So before this, a base that moved anywhere inside a snapshot went unseen | The fixture says so, and the port's comment and its test's now do |
| The Kernel | Changes nothing. It reads `mergeable` at every pass and keeps nothing of an earlier read: true goes on, null defers, and false is the author's turn and takes a queued pull request out | A wait after every move of the base would hold every open pull request at each merge to `main`, for a window one run measured |
| What stands for the read, in order | The snapshot's last read; then the next pass, which reads the conflict; then the merge queue, which merges a pull request only as built on the base it finds | The first two are the Factory's own and are held below. The third is GitHub's |
| Residual: a last read in the stale second | Where a snapshot's last read falls in that second, whenever its first was, the two agree and the pass acts as for any head that merges: it may admit a review Run or the owner's ruling Run, resolve a Lens's thread, or enqueue. An approval takes one more such read, since the approving act asks the Kernel again on a snapshot of its own. A Run is counted at the Run ceiling as any is, and an approval of a head that must change is dismissed by the fix's push | The merge state gates no Lens: a stale true gets a head nothing a true one would not get for the same content, and nothing unmergeable lands by it |
| Residual: an enqueue not shown | The enqueue and a thread's resolution are the queue App's acts, which read only that the pull request is open at the head the pass read, and are not asked of the Kernel again. So such a pass may enqueue an approved head that now conflicts, and so may any pass whose queue job runs after the base has moved, with no stale read at all. No trial here shows what the queue answers to that. "Trial: what does the merge queue answer to an enqueue of a head that conflicts with its base?" (issue 812) asks it; if the queue keeps or merges such a head, a record says what stands for the read then | P-2's fixtures show the queue merging, ejecting, and refusing a push and a draft, and none enqueues a head that conflicts |
| Residual: the other way | A conflict that a base move clears would, by the same reading, read false for about a second. The snapshot's last read holds that too. Neither run asked it | A fix Run admitted or a dequeue lands nothing |
| Residual: the explorer | `tests/test_transitions.py` still makes `mergeable` unknown at once when the base moves, so it reads a conflict only two moves after a head that merges. "The transitions explorer reads a conflict only two moves after a head that merges, and one move finds a Hold the Lifecycle does not declare" (issue 811) holds the move and what it finds | The move finds a Hold from `addressing` that the Lifecycle does not declare, which is a ruling of its own |
| What the runs do not say | How long the stale read lasts under load, what a pull request reads that nobody reads for minutes after the move, or what follows a merge by the queue, which is how `main` moves: both runs moved a branch by one commit through the contents API on a quiet repo, and read at once and often. Nor how long a snapshot takes: six reads took 3.3 s in the second run. Apps installed on the canary commented on each pull request and edited its description while the runs read; none pushed to a head, and in the second run nothing was written between the last read before the move and the first false after it | Two runs on one day in one repo |

## Why

The design held that the merge state is as GitHub last worked it out, and the Kernel treats a null as unreadable. The trial shows a third case that neither names: for about a second after the base moves, the read is a definite answer that is no longer true, and one read cannot tell. A pass does not make one read. It reads the pull request first and last, and by the last the answer has changed; the port already compared the two, on a ground the trial showed to be wrong for a base move. Holding the merge state between them costs no wait. What is left is a snapshot whose last read falls in the stale second, and for that the next pass reads again and the queue builds on the base it finds, which is written down as not shown, with the issue that asks it.

## Boundaries

| Boundary | Check |
|---|---|
| A snapshot whose first read of the pull request gave a merge state, true or false, that its last read does not give as the same word is of a pull request that moved, whichever way it changed; one whose last read repeats it, or whose first read gave none, is kept; and a last read with no time is a read GitHub did not answer, whatever its merge state | `tests/test_adapters.py::test_a_snapshot_whose_merge_state_changed_while_it_was_read_is_refused`, `adapters/pull.py`, `trials/P-40.at-once.json`, `tools/mutants.py`, mutant: "a merge state that changed while the snapshot was read is kept", mutant: "a conflict that cleared while the snapshot was read is kept", mutant: "a conflict that stays a conflict is a move", mutant: "a last read of 1 is taken for true", mutant: "a first read of no merge state is a move" |
| Where nothing read before a conflict stops it, an approved pull request read as conflicting is its author's turn at that pass, whatever an earlier pass read; one in the queue is taken out by that pass's act; and one whose merge state is not worked out stays in it | `tests/test_decide.py::test_a_conflict_read_a_pass_late_is_the_authors_turn_at_the_next_pass_and_leaves_the_queue`, `kernel/derive.py`, `tools/mutants.py`, mutant: "an approved head that conflicts is not sent back to its author", mutant: "a queued pull request that conflicts stays in the queue" |
