# 0200. A path only a person decides is listed apart from a Lens's inputs, and a change to it needs a person's approval

Status: accepted. The Factory Builder's ruling of 2026-11-11, on the Maintainer's behalf, on what 0194's row "What is not held" left open: "A change to the continue-or-stop file must need a person's approval, as a model-Lens input does; a model review alone isn't enough." It adds a second kind of path to what 0052's rows "Which paths" and "How the Kernel is told" give the Kernel; 0052 and 0194 both stand.

## Decision

| What | Decided | Because |
|---|---|---|
| The list | `config/hooks.json` gains `person_only`: each path only a person decides, with what it is. Its first row is `release/decision-points.json`, the Maintainer's continue or stop. It is its own list, not rows of `lens_inputs` | `lens_inputs` is each file a Lens reads to judge a change, and 0052 is built on that meaning. No Lens reads the decision file; a row for it there would make the list mean two things |
| How the Kernel is told | `tools/hooks/protected.py` reads the list in the one reading of `config/hooks.json`, and what the Kernel is given as `model_lens_inputs` is the model Lenses' own inputs and then the person-only paths, each once; where no model Lens's input is named it is given nothing, and defers on that as before. The Kernel changes by no line: a change to such a path waits until a person with write access other than its author and its last pusher approves its head, and in the merge queue without one it is taken out, as 0052 has it for a model Lens's input. A Role's push may not touch one | One function, one reading and one rule in the Kernel leave nothing to drift. 0052 already says whose approval counts and why the machine user's never does |
| The code it waits in | `model_lens_input_needs_person`, unchanged. From this record the code also covers a person-only path, which is no Lens's input; the evidence beside it names the path | A new code is a change to the Kernel, the feed and the Decision's schema. The name is narrower than what it now holds, and renaming it is its own change |
| The edit is asked | Every person-only path is a protected path as well, or the file is not read at all. So a session hook asks the person before an edit to one, a stop lists it, and no Role's push may touch it, whatever Lens is named | A session should meet the question at the edit, before the pull request |
| A commit with no such list | A `config/hooks.json` with no `person_only` names none, and is read as before. One that has the list holds at least one path, each a protected path and so of the shape every path here has, with what it is, or the file is not read at all | A pull request's base may be a commit from before this record, and its list is that commit's. The schema asks nothing of the list's presence for the same reason |
| What it means for the Maintainer's decision | His own change to the decision file is not converged by the Factory on his own approval, which is its author's, nor on the machine user's, which is nobody's. With no other person's approval it merges by his hand, as the machine user (0198), and that approval is the act that shows a person decided. A session may type the three fields on his word; it cannot bring them to `main` | 0194 said the check holds the name written and not the hand. The hand is now an approval, which a session cannot give |
| What is still not held | The approval that passes a change to the file is any person's with write access but the author's and the last pusher's, as 0052 has it, not the Maintainer's alone: another person with write could pass a decision typed in his name. And the person's approval is tied to the one path: a change that points `tools/check_release.py` at another file is judged by the model Lens alone | 0052's rule is taken whole, and narrowing it for this list is a change to the Kernel. The list names what a person decides, not every file that says where the decision is kept |
| From when | The Kernel is given the list by the Factory's own checkout, so the rule holds from the first Release cut after this record merges | The Controller reads its configuration from the Release it runs |

## Why

The continue-or-stop record is the one file in the repo whose content is a person's decision and nothing else. 0194 held the name written in it and said plainly that a session could type that name, since every commit names the Maintainer and the Factory would approve the change as any other. The Kernel already has a rule for a change no model may be the only judge of. Putting the decision file under it, by a list that says what the file is, narrows the gap to those two cases without a new rule to test in the Kernel.
