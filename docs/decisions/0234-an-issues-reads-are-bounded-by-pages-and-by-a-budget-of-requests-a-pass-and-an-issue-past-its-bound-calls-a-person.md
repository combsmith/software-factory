# 0234. An issue's reads are bounded by pages and by a budget of requests a pass, and an issue past its bound calls a person

Status: accepted. The Factory Builder's rulings of 2026-11-19 on "Once issues are served, each touched open issue is re-read every pass with no budget of its own, and a short list stops the whole pass" (issue 849): Q1 to Q6, with Q2 re-ruled (B), the bound widened to the issue's own timeline, and its deferral given its own code, (A). It is built in three parts: the fact and the Kernel's code first, then the port's bounds, then the budget, the order and the short list; each part adds its rows below.

## Decision

| What | Decided | Because |
|---|---|---|
| A timeline's bound | The issues port reads an issue's own timeline, and each linked pull request's, to ten pages of a hundred events at most (`BOUND` in `adapters/timeline.py`). A tenth page that names an eleventh leaves the timeline not whole, and the eleventh is never asked. It reads an issue's linked pull requests only while there are 25 at most to read (`CANDIDATES` in `adapters/linked.py`); past them it reads none, and the list is not whole. The issue's references, and its timeline of links, closes and cross-references, are read in one page each; more than a full page holds is cut too, and what was read is read on; a page not full that says there is more is a read short, not a bound | Anyone can comment on an issue or a pull request, or open pull requests that name it, and a read with no bound, again on every pass, is an amplification an outsider controls (the security read of S3 PR2e) |
| A read past its bound | The issue's facts say so, `timeline_bounded` in `issue-facts/1`, whichever read the port cut: the issue's own timeline, beside `complete.timeline` false, or a linked pull request's timeline, or the pull requests past 25, or the references or links past their one page, beside `complete.linked` false. The issues' Kernel defers it `timeline_bounded`, before any list read short, a closed issue's too, and calls a person. A flag that is not exactly true or false is a gap in the timeline, `facts_incomplete`, never read as within the bound | A read short mends itself at a later pass; one past its bound only grows, and pass records keep a pull request once seen with its keyword. A person must see why the issue waits, so it is its own code, and calls one: a pull request's author who comments past the bound on their own pull request must not stall the issue in silence (the Factory Builder's re-ruling (A) of 2026-11-19) |
| Read on though not whole | Every pull request within the bound is read, whatever is short or cut elsewhere, the issue's own timeline among them: a record not whole still opens a span for each keyword it read (decision 0186), so one left unread would be seen a pass late, and a rival would read as first seen later | The unsafe direction at a merge is a keyword seen late; the cost is bounded by the 25 instead |
| A budget a pass | The issue reads a pass sends are counted, and once `max_issue_requests` of the Controller's configuration are spent no further issue's read starts: each issue not read is left out as `issue_budget`, and the pass raises one alert, `issue_budget_spent`. A read already begun finishes, and every pass reads one issue at least | The issue reads are mostly REST, which P-8 did not measure, and `served_from` never moves forward, so the issues read only grow |
| Which first | The issues the newest pass record that read the issues left out as `issue_budget` are read first, in the order it left them out, then the rest in the listing's order. A record whose list was read short, which read no issue, is passed over (ruling B4); one that cannot be read, or holds none, gives the listing's order. So, while the list stays the same, each issue listed is read within as many passes as the budget's fit goes into the list | Derived from the records before alone, which a replay holds: no field is added and nothing is stored apart. A short list, which an outsider can force, must not empty the queue |
| A short list | An issue list read short, or not answered, no longer stops the pass. The pull requests are decided as ever, no issue is read, and the pass writes one left out entry naming no item, with the code `issue_list_unreadable`, and the alert of that name | As the issues alone are refused when their Apps cannot be told, by "The issues port drops a comment by a Role App held only under `roles`, and a queue's or Lens's name declared as an App's refuses that App's real comment" (issue 901). The keyword spans' chain passes over a record whose itemless left out entry has that code, so one such pass costs one pass's window, and two in a row break it (decision 0186) |
| Why the budget is what it is | `max_issue_requests` is 100. Twenty passes an hour at most (decision 0043) then start no issue's read past 2,000 issue requests an hour, under half of an App's REST budget of 5,000, and each issue costs five requests or more. It is a bound on what starts, not on what is sent: the read begun last in a pass finishes, so a pass can pass 100 by what that one issue's read costs, at most 25 × 11 + 14 = 289 requests: the issue, its timeline's ten pages, its edits, its links, and its second read, then each of 25 pull requests and its timeline's ten pages; and beside them one permission read for each login acting in what was read that the pass has not asked of, at most one an event, so a thousand accounts that each comment once cost a thousand more | The number is configuration; changing it is a change to a protected path. A budget that cut a read short would leave that issue read short at every pass that reached it last |

## Why

It asks that the issue reads have a bound of their own and that a list read short never starve the pull requests. The bounds cap what one outsider can make one issue cost; the budget caps what all the issues together cost a pass; the order makes sure the budget never leaves one issue out for good; and the short list refuses the issues alone.
