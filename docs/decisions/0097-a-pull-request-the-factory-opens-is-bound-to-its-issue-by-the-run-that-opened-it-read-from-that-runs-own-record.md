# 0097. A pull request the Factory opens is bound to its issue by the Run that opened it, read from that Run's own record

Status: accepted. The Factory Builder's ruling of 2026-10-30 on "Acceptance: a pull request the Factory opens is bound to its issue by the Run that opened it" (issue 342): option (a), the opening Run's own `applied/1` holds the binding, as a Lens's holds its Findings. It holds what decision 0068's row "The Run record" left waiting, and the Run-record half of decision 0047's binding.

## Decision

| What | Decided | Because |
|---|---|---|
| The record | The opening Run's own `applied/1` names the pull request it opened, in an `open_pull_request` Effect keyed by the pull request's number as read back. `applied/1`'s Effect types gain it, beside `approve`, as one no Result asks for yet | A Run record names the issue it served, its run-name's item, and never the pull request it made; its own record of what it wrote joins the two, as the Lenses' records join their threads (decision 0069) |
| The reader | `adapters/applied.py`'s `opened` reads, once a pass, each completed Run of the Role the configuration names for `open-pull-request`, of that Intent, on an issue of the home repo: the pull request each one's landed `open_pull_request` Effect names, by number, with the issue it served. An issue whose opening Run has not finished, cannot be read, is named by more than one GitHub run, names more than one pull request, or names a number that is none, is unreadable; the list is whole only when the run list was read whole and lists no Run before its name, which may be an opening Run (decision 0036). A Run that did not succeed and uploaded no record names none, as a Lens's does: reading it as unreadable would hold every pull request the opener opened for as long as the Run is listed, and the writer's rule below covers what it may have opened. With no Role named, nothing is read | What cannot be read is never read as none (I-13) |
| The binding | A pull request the opener's App authored, on a branch of the Factory's shape, is bound to the issue its branch names when the Runs that name it agree: one that names it for another issue, two that name it, or any opening Run that cannot be read or has not finished, of whatever issue, leaves it not read whole, and the Kernel defers, since that Run may be the one that opened it on another issue's branch. Where no Run names it, the branch alone binds it, as decision 0068 has it, until the writer lands. A person's pull request keeps its closing references' reading | Where both are present they must agree, as the issue asks; an opening Run that pushed to another issue's branch is caught by its own record |
| Where it is read | Wherever a snapshot is: the pass, the Run's read step and `apply`'s read again each read the opening Runs and hand them to the snapshot, which takes them as a required argument, so no caller can leave them out. Handed none, the opener's pull request is never bound | The binding is read wherever the ask is |
| The writer | `apply`'s open Effect, which writes the record, lands in slice 2 with the push Effect, as decision 0070's refusal waits on push. No Role opens pull requests in slice 1, so none is bound yet, and nothing is read. Once it lands, an opener's pull request that no Run names is not whole: the branch alone no longer binds it | The Factory Builder's ruling: build the record, the reader and the binding now. Before the writer, no Run can name one; after it, a pull request no Run names was opened by none the Factory can read |
| Retention, the accepted miss | An opening Run's `applied/1` past the artifact retention is read as recording nothing, as a Lens's is (decision 0069), so its pull request is bound by its branch alone until the writer's rule above makes it not whole | What the artifact retention keeps is what can be read |
| The lookup's grant | The bound issue's lookup under the Controller App's grant is a trial the release builder runs, before a Role opens pull requests on a private repo (decision 0068) | It is a trial, not this change |

## Why

Decision 0068 bound a pull request the Factory opens by its branch, and named its own limit: anyone who may write the repo can rename a head branch, so an opening Run that names another issue's branch answers to that issue. The Run's own record of the pull request it opened closes that gap without reading the body.
