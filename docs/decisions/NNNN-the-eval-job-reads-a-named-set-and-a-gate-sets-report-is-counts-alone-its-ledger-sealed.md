# NNNN. The eval job reads a named set, and a gate set's report is counts alone, its ledger sealed to the Maintainer's certificates

Status: accepted. The Factory Builder's ruling of 2026-11-07 on issue 612, "The eval job reads a named set, and a gate set's report is aggregates only", on the builder's design and the Solution Architect's ruling on where the ledger goes, of which this lands the half common to its options A and D: the seal, with no new credential. For a gate set alone, it amends decision 0099's row "What the report says" and decision 0150's row "Where it is computed", each where it keeps a count of a kind out of the report. A development set's report, `eval-report/1`, and everything else in either, are unchanged.

## Decision

| What | Decided | Because |
|---|---|---|
| The set a dispatch judges | `.github/workflows/eval.yml` takes an input `set`, `pr-review` by default, which the plan step alone is given as `EVAL_SET`. The plan reads `evals/<set>/cases.json`, the name one path part, and keeps the name for each step after it. The Release's gate still reads the review Intent's set, from the commit's latest successful dispatch: a later run of another set on that commit closes it, `another_set` or `report_of_another_kind`, so the review Intent's set is dispatched last before a cut | A fresh gate set (issue 562, "A fresh held-out gate set for the Release after v0.1.0, never replayed") is a manifest of its own beside the development set, and a dispatch must say which it runs. A name of more than one part could reach a file outside `evals/` |
| A gate set | A manifest may say `gate: true`, and then says of each case whether it is `natural`, taken from a change as it was made, or not; each group it marks holds `ORIGIN_LEAST`, ten, at least, or none. Absent, a set is a development set, as every set was. Nothing the Role is given carries the mark: its Task is built from the case's bytes | Natural and constructed cases measure different things, and the report counts them apart. A group of one would tell its case's verdict by its count. The Role must not learn which a case is |
| A set beside a gate set | The plan refuses a set that is not a gate set and names a gate set's case by its id or its hash, `eval_set_overlaps_a_gate_set`, reading every manifest under `evals/`; one it cannot read stops the run. Another gate set may share a case | Its report, case by case, would tell what the gate set's keeps back. What remains is an edit that drops `gate` from a gate set's own manifest: a reviewed change to `evals/`, which no hook protects. Whether to protect it is the Maintainer's |
| A gate set's report | `eval-aggregate/1`, of counts alone: how many passed; of each kind its cases, its passes and their Wilson interval at 95%; the natural and the constructed apart; each code of a case not read, by how many; the usage summed; the Engine, its model and the sha256 of the Role's instructions and rubric; the bars applied; `split_ok`, `kinds_pass` and `blocking_pass`; and the ledger's two hashes. No case id, per-case verdict or a case's code | Per-case outcomes under stable ids are what a prompt can be fitted to, and the report is public. Raw counts let runs on one commit be pooled (issue 613, "The gate pools k dispatches on one commit and reads all of them") |
| A count of a kind | A gate set's report holds each kind's count, which 0099 and 0150 keep out of `eval-report/1` | 0099 kept them out because the repo cannot hold them true. The job counts them where the cases are, as it computes the words, and `verdict` holds the counts to the words and to the set |
| The gate's verdict | `verdict` reads a gate set's report by `aggregate_verdict`: this set, commit and Release; no fault of the Engine or the run; counts that add up to the set's, the manifest's natural cases and its own words; each kind's interval its counts'; the bars and the least of a kind the job applies, else `bars_differ`; each kind's bar cleared, as decision 0150 has it. A report of the other kind than its set's is `report_of_another_kind` | The words alone, as `eval-report/1` gives them, are held by the cases beside them; a gate set's have no cases beside them, so the counts carry that weight |
| The ledger | Each case of a gate set's run, by its id, with its verdict, codes, cause, whether it is natural, and the Result the review returned, `eval-ledger/1`, under a salt drawn for the run. It is written to the scratch alone, readable by the runner's user alone, and never uploaded in the clear | Retiring a set needs what each case did. The salt keeps its hash in the public report from telling what it holds |
| The seal | A step after the run, `python3 -m harness.eval.seal`, given nothing, encrypts the ledger with `openssl cms`, RSA-OAEP with SHA-256 and AES-256, to each certificate pinned by its sha256 in a file under `.github/`, a protected path, that `harness/eval/seal.py` names `RECIPIENTS`. It seals copies of the certificates and of the ledger it checked, into the scratch; reads back that openssl wrote an envelope of RSA-OAEP with SHA-256 to each and AES-256; copies the ciphertext into the workspace to a name nothing holds, through no link; writes its sha256 into the report and removes the plaintext. A file or a link already where the ledger is uploaded from fails the run, for either kind of set, `ledger_in_workspace`. A gate set's report without the hash is unreadable to the gate; nothing yet holds the hash to the artifact, which the step that keeps the ciphertext will | The repo is public and GitHub has no private channel between jobs. A ciphertext no key in the job opens is safe to upload. A certificate whose bytes are not those its pin names is refused, `recipient_changed`; changing both the certificate and its pin is an edit under `.github/`, which the session hooks ask about, and its merge is the Maintainer's, as every merge is. The standard library has no public-key encryption, and openssl is on the runner |
| With no certificate pinned | Until the Maintainer has made his key pair and committed its certificate and pin, no pin file exists. The seal then refuses, `no_recipient`, and the run fails there: nothing after it runs, so neither the ledger nor the report is uploaded, and the plaintext stays in the scratch of a runner thrown away. A development set's run is untouched | A ledger is never uploaded in the clear, nor sealed to nobody, and a gate set's run with no ledger it can keep must not count for the gate |
| The upload | The ciphertext alone, sealed by this step, as the artifact `eval-ledger`, for 90 days, before the report's upload; a development set has none, and its run uploads nothing there | The ruling's half common to A and D. Where a ciphertext is kept past its 90 days is the Maintainer's to choose, and a later record's |
| The job's time | The run step's budget and limit are 109 minutes, one less, which the seal takes | The job's 120 minutes hold every step's limit with two to spare (`tools/check_workflows.py`) |

## Why

The review Intent's set is a development set: its report lists each case's verdict and codes, which `verdict` and the judge read, and nothing is lost by that while the set is tuned against. A gate set must stay held out while it is in service, and a public report of its per-case outcomes is how it stops being so. Counts keep what the gate and the pooling of runs on one commit need, and the sealed ledger keeps what its retirement needs, readable by the Maintainer alone.
