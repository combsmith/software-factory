# 0139. A platform close keeps the State a person set on an issue held or not served

Status: accepted. Replaces `docs/decisions/0028-an-issues-state-is-derived-in-a-module-of-its-own.md`, and keeps all of it but one line, which it overturns: "A person's hands-off that stood at the merge, with a Hold beside it or not and lifted since or not, … leave it done". The Factory Builder's ruling of 2026-11-04 on "A platform close keeps the State a person set on an issue held or not served" (issue 522), of "Epic: slice 1, first approval. A Release on next reviews a pull request to this repo, and the machine user's approval stands" (issue 182), found by the read of "An outsider's merge never makes an issue done (P-48)" (issue 521). It narrows row 1 of the issue's States again, after decision 0132.

Where it is one only a person ends, `not_served` or `held`, it stays, and the merge reads on only once a person has ended it. It holds for the Factory's merge, a person's and an admitted outsider's alike | The queue's merge closes an issue whatever its State: an outsider's late keyword can name an issue the Controller does not watch (`trials/P-48.json`), and the Factory leaves a queued item to merge under a person's hands-off. ## Why

The Lifecycle says only a person ends `held` and `not_served`, and the Kernel moved an issue out of both on a merge no person made. Keeping the State is the reading that needs no exception, where the facts can say what the State was at the merge: the person who set it ends it, and until then the feed asks them. Where the facts cannot say, reading them as they stand now would trade one undeclared change for another, out of a terminal State, which a stranger, or turning issues off, could make; so the rule waits for the facts.
