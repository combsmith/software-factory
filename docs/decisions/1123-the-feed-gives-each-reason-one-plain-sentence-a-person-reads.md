# 1123. The feed gives each reason one plain sentence a person reads

Status: accepted. The Solution Architect's ruling of 2026-11-22, relayed by the Factory Builder, on the readability lane's plan, item 4, for "status: the factory check shows only codes a newcomer cannot read" (issue 1120). It holds the sentences to `REASONS`, from decision 0248. Part 1 of 2 lands the sentences and their checks. Part 2 lands the writer in `adapters/effects.py`, whose rules are decided here.

## Decision

| What | Decided | Because |
|---|---|---|
| The sentences | `config/feed.json`, feed/1, gains `sentences`: one fixed plain sentence for each reason, keyed by the reason alone. A sentence holds no placeholder, no text of the item and no number known only at run time | The factory check shows codes only, so a reader new to the project cannot tell what the Factory waits for. The check's title already shows the State, so each sentence is written to read true in every State its reason comes with, and no reason needs a sentence by its State |
| Which reasons | The keys are exactly `REASONS` in `kernel/terms.py`: a pull request's reasons. An issue's own reasons have none. `tools/check_examples.py` refuses a missing sentence and a sentence for any other key | The status is written on a pull request's head alone. An issue has no check to show it (decision 0248) |
| What a sentence holds | One sentence, by one pattern, `SENTENCE_PATTERN` in `tools/check_examples.py`: a capital first; then letters, digits, spaces and the marks `, ; : ' ( ) -`; one full stop, at the end; at most 100 characters. So no `@`, backtick, line break, placeholder, slash, Markdown mark, or address such as `www.` with a full stop in it. The schema gives that pattern, and `tools/check_examples.py` holds each live sentence to it again, whatever the schema says. It also refuses what GitHub would still make of a plain sentence: a code between colons, capitals with a dash and digits, an advisory's id, and a word of seven or more hex digits in either case. Each form has a counter-example or a case | GitHub renders the summary as Markdown: a mention notifies someone, a backtick or a link renders as one, a bare address becomes a link, a code between colons an emoji, `GH-12` a reference, `GHSA-` an advisory and a hex word a commit |
| The one text the feed holds | feed stays in `CODES_ONLY`. `tools/check_examples.py` lets text through at one place alone: the property `sentences` of the kind `feed`, and only while its schema keeps the shape. The shape is an object whose values are strings, each held by `SENTENCE_PATTERN` itself and a `maxLength` of 1 to 100, with no other keyword beside. Any other kind or name, the same name deeper in the feed, the feed's schema reached by a reference from another kind, or a looser shape, is swept as text a Run carries | A reason stays a code. The sentence is configuration text that only a reviewed change to a protected path writes, never text from outside, and nothing that decides reads it. An exemption that trusted the schema would let a later edit widen it unseen |
| Where it is shown (part 2) | The sentence for the Decision's reason is the first line of the status's summary, above the code lines, which stay. The title stays `state: reason`, and the Decision is unchanged. The sentence goes nowhere else: not into a view-item, a Task, or anything the Kernel is given. The writer shows a sentence only if it keeps the pattern, the length and the refusals above when it is written, and otherwise shows the codes alone. Its output's title and summary are read back as sent | The waiters and the sweep read the title, and stop on `held:`. A sentence is for a person to read, and nothing reads it back |
| When it changes on an item (part 2) | The status's key, `status_id`, stays a hash of the Decision alone, and I-17 holds whole. The sentence is read when the status is written. A Release that changes a sentence writes nothing. An item shows the new sentence when its Decision or its head next changes | The summary already carries `pass:` and `release:` lines that the key does not hash. Rewriting every open item at a Release would change a status with no change of its Decision |
| The limit accepted | A corrected sentence reaches a long-open item only at its next change of Decision or head | A wrong sentence misleads a reader but decides nothing, and the codes beside it stay right |

## Why

The plan's item 4 puts a sentence a newcomer can read beside the codes. The rule that a reason is a code, never a sentence, still holds: the Kernel gives codes, and the sentence is only looked up from them, by code, for display. The sweep that keeps the feed to codes would refuse any text, so this record names the one place text is let through. It also holds that place to a shape and to the one pattern, so that widening it takes a reviewed change to `tools/check_examples.py`. The writer's tests in part 2 join this record's Boundaries, which may gain rows that change nothing decided.
