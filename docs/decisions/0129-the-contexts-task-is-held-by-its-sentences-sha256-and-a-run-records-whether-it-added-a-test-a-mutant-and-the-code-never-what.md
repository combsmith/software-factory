# 0129. The context's task is held by its sentence's sha256, and a run records whether it added a test, a mutant and the code, never what

Status: accepted. Replaces `docs/decisions/0042-the-context-is-tested-by-a-task-run-outside-ci-and-held-as-a-fixture.md`. The Maintainer's choice of 2026-11-03, through the Factory Builder, for "The context's test: a fresh agent adds a rule to the Kernel without being told how" (issue 8): hash only, so that the task's rule is named nowhere in this repo, even once the runs are recorded. It keeps 0042's rows, restated below, but for what the record holds of the task and of what the agent added, and it says what trial P-26 found.

## Decision

| What | Decided | Because |
|---|---|---|
| The task | One Kernel rule the repo does not hold and no `@pending` test states, chosen by four criteria: the design states it; it is one reason code in one Kernel module behind one boundary; it needs no new fact and no new limit; it is decided. Its boundary test is the known answer, written in the private held-out home by a private session. The sentence names the rule and its code and nothing of how. Only the sha256 of each is here, the sentence's taken of its one line with no newline: the sentence and its code are never in this repo, a pull request, an issue or a shared transcript, before the runs or after them | A task whose answer is in the repo measures nothing; as first written the test could not fail. The Maintainer chose that the rule is named nowhere here, so the record carries hashes alone |
| Who runs it, and on what | `tools/context_eval.sh` at the Maintainer's terminal, never CI: the CLI at the pin of 0033, on the configuration directory logged in to his own subscription, headless, with the sentence as its whole prompt, on a `git archive` export of one commit of `main` outside every repo, with a scratch HOME and its login alone, its network tools refused, a cap on turns. Its shell is not sandboxed, since trial P-26 found that the CLI's sandbox hands a tool the parent's environment: the record counts each path it named outside the export and each command it could not read | CI runs no model and fetches nothing; the credential lives where 0033 put it; an export has no history, remote or other checkout to read from; what cannot be confined is counted, so a run that looked elsewhere says so |
| How a run is judged | After the agent stops, the runner, not the agent: the held-out test copied in, run on its own and taken out again before anything else; the Makefile and every tool but `tools/mutants.py` put back as made, each one the agent had changed recorded; `make verify`; the whole mutation check, which must kill every mutant, the agent's among them, and no mutant may be dropped from the list. A run passes on all three; the story passes at three of three | The held-out test says whether the rule is the one asked; verify says the change is finished; a killed mutant says the agent followed the three-part rule and not only made a test pass |
| What a run records | A `context-eval/1` run in `evals/context/task.json`: the commit, the date, the CLI's version, the cap and the task sentence's sha256; the paths read, and of each command its program, its flags and the paths and modules the export as made holds, from the transcript's tool uses alone, a word shaped like a token never recorded; a file the export as made does not hold, made or only named, by its folder alone; how many paths were named outside the export and how many commands could not be read; what changed, by file, in lines, a file the export does not hold under its folder, and what of the judge's was put back; whether the agent added a test, a mutant and the sentence's reason code on a line of the Kernel, three booleans and no name; the result's counts, null when the CLI gave none; the three verdicts. Of the model's text only those words, each held to a pattern: never a text block, a tool's result, a prompt, an answer, or a name the agent chose. Nothing the runner leaves in OUT or prints names the sentence, its code, or the test or mutant the agent added | What CI can hold is a fixture of the runs, honest about what it holds; a word of the model's would leak the answer, and a name the agent chose for its test, its mutant, a file or a search, or the code, would name the rule. An existing file the agent changed, the one Kernel file it edited among them, is kept by its path: it is the repo's own name and says where, not what, which the Factory Builder accepted |
| A failed run | Recorded too; the context changes, never the task, in a pull request of its own that names the failed run; then three fresh runs. The test counts the newest three on the task's sha256 | The measure is of the context; a task changed after a failure would be the proof of concept's stub again |
| A later change to the context | Re-run at the Maintainer's call, not by CI; the record's commit says what was tested | CI cannot run a model, and cannot tell which change to the context matters |

## Why

Slice 0's exit is that an agent given only the repo and one sentence adds a rule to the Kernel and passes the required
check (design §9.1, §9.14). Nothing in CI can run a model or read the private home, so the test is two things: a
runner that makes and judges the runs where the model and the answer are, and a record in the repo that a test in
`make verify` holds. 0042 kept the sentence out of the repo only until the runs were recorded, and recorded the code
and the names the agent chose. The Maintainer chose that the rule is named nowhere here, so the sentence is held by
its sha256 as the answer is, and a run says whether it added each part, which is what the test needs, and not what.
