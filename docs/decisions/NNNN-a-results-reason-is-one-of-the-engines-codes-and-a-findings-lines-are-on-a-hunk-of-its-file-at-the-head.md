# NNNN. A Result's reason is one of the Engine's codes, and a Finding's lines are on a hunk of its file at the head

Status: accepted. The Factory Builder's ruling of 2026-11-05 on the story that follows the harness review's (issue 567), before the first live Run. It adds to decision 0038 a list of the codes a Result's `reason` may be, and to the reasons `apply` refuses a Result two more; and it reads the lines decision 0137 numbers as the hunks a Finding may sit on. Nothing else in either changes.

## Decision

| What | Decided | Because |
|---|---|---|
| A Result's reason | `result/1` holds `reason` to null or one of twelve codes, and no other: the two the model may write, `change_not_reviewed_whole` with `incomplete` and `task_not_a_review` with `refused`, and the ten the Harness writes with a `failed` Result it writes whole, `credential_missing`, `engine_version`, `task_too_large`, `engine_failed`, `engine_timeout`, `no_answer` and `result_invalid` in `harness/engine.py`, and `diff_not_whole`, `head_unreadable` and `rubric_unreadable` in `harness/run.py`. The lists are `harness/engine.py`'s `MODEL_REASONS` and `HARNESS_REASONS`. The schema handed to the CLI narrows `reason` to null and the model's two, as it narrows `status`: `enum` is a keyword P-13 proved, but a null inside it is new to that schema | A reason is a code, never a sentence, and a code the Factory never named is one no reader can act on. `apply` copies the reason into `applied/1` and `outcome/1` |
| A reason its status may give | `apply` refuses a Result whose reason is not one its status may give, the model's on a `failed` Result or the Harness's on an `incomplete` or `refused` one, as `reason_not_the_status`, the Role's (`item`). A Result that did not complete may give no reason, as before | The Harness writes a `failed` Result and the model never does, so a model's code on one, or the Harness's on the model's status, did not come from where it says |
| The model's two codes | The two follow the words `roles/pr-review/prompt.md` already gives each status: `incomplete` "when the change could not be reviewed whole", `refused` "when the Task is not a review you can make". The prompt is left as it is, as a model Lens's input; the CLI is held to the codes by the schema it is handed. A Role that needs another code adds it under a record of its own | The codes say what the prompt says, and no more |
| A Finding's lines | `apply` refuses a Result that posts a Finding, as a review comment or as an annotation, whose lines from `start_line` to `end_line` are not all on one hunk of its file on the head's side, as `finding_not_in_hunk`, the Role's. The hunks are read from the Task's own diff, the text of kind `diff` the model was given (decision 0137): each file by its name after `+++ `, read once before its first hunk, a name git quoted unescaped and one with a space without git's tab, and each hunk's lines from its header's first line and count on the head's side. A file the diff deletes, a hunk that only removes, a file the Task's diff left out, and a name that is no UTF-8 hold no line. Another text's body gives none, however it reads | GitHub refuses a review comment off the diff, and the review is then refused whole, but an annotation it takes wherever it is placed. A Finding names lines of the change the model was shown, and the Task's diff is what it was shown. The facts carry the files and their count, not the hunks |
| A diff cut short | A reviewing Intent whose Task leaves part of the diff out is never asked (`diff_not_whole`, issue 327). Any other Run whose Task leaves a file out may post no Finding on it | It fails closed |

## Why

`result/1` held `reason` to lower-case letters and underscores, with no list and no bound, so a model could write any code and `apply` would copy it into what the Factory records. And `start_line` and `end_line` were bounded to nine digits but not held to the change, so an annotation could be placed on any line of any file. Each is now held to what the Factory itself named or showed: a reason to the Engine's codes, by the status that gives it, and a Finding's lines to a hunk of the diff in the Task.

## Boundaries

| Boundary | Check |
|---|---|
| Each of the model's codes is taken with its status and refused with any other, the Harness's codes with `failed` alone; a Result that did not complete may give no reason; `result/1` holds a reason to null and the twelve codes, and the CLI is handed null and the model's two | `tests/test_apply.py::test_a_reason_is_one_of_the_engines_codes_and_one_its_status_may_give` |
| An answer whose reason is not one of the model's codes, the Harness's among them, is no Result | `tests/test_harness.py::test_an_answer_that_does_not_validate_is_no_result` |
| A Finding on lines of one hunk at the head, its first and last among them, is posted; one a line before or past it, across two hunks, on a hunk that only removes, on a deleted file, on a file the Task's diff does not hold, or with no diff in the Task, is refused, and so is an annotation; a renamed file's lines are its new name's; a line of the change that reads as a hunk's header or a file's name is a line; a file's name is read once, before its first hunk; a name with a space, a quoted name, and its escapes and bytes are read as git writes them, and a quoted name that is no UTF-8 holds no line; another text gives no line | `tests/test_apply.py::test_a_findings_lines_are_on_one_hunk_of_its_file_on_the_heads_side` |
| Each of these rules has a mutant that a test kills | `tools/mutants.py` |
