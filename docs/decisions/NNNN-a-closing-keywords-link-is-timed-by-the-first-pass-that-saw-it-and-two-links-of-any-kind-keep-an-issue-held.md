# NNNN. A closing keyword's link is timed by the first pass that saw it, and two links of any kind at an issue's merge keep it held

Status: accepted. The Factory Builder's rulings of 2026-11-10 on "Facts: a closing keyword's link timed by the first pass that saw it, and the Consumer entry at the merge (after the first cut)" (issue 552): its design, and rulings (1) to (3). It amends decision 0174's rows "The same second", "What carries no time" and "Two links at the merge", for a closing keyword's link.

## Decision

| What | Decided | Because |
|---|---|---|
| The facts | Each linked pull request in `issue-facts/1` carries `keyword`, whether its references name the issue by a closing keyword now, and `keyword_spans`, each time the keyword stood as the Factory's passes saw it: when it was first seen, the `read_at` of the issue's facts in the first pass record that listed it with its keyword, and when it was first seen gone after that, likewise, or null while it stands or until a pass sees it gone. `read_at`, not the pass's `now`, which comes before GitHub is read, and the port takes `read_at` no earlier than it reads the closing references. Each pass record already holds each issue's facts, so it carries the closing references that pass read. The spans are read whole: in order, none before the pull request opened, each ending no earlier than it began and before the next began, and only the last open: a keyword standing now with every span ended was put back since the last pass that saw it, and is read, its new span not begun. A pull request listed for nothing, with no keyword now or once seen, no link by hand and no close it made, defers too, `linked_unreadable` | GitHub dates a cross-reference at the first mention of the issue, not when it became a keyword (`trials/P-48.json`), so the only time a keyword link has is the Factory's own record of seeing it, which no edit after can move back. One span for each time it stood, so that a keyword taken out and put back is two, and the second reaches back to nothing before it began |
| Row 1 at the merge | A keyword link stood at the first merge where one span of it began before the merge's second and was not seen gone before it, as a link by hand stood where it was made before that second (decision 0174). Two links of either kind, neither closed before it, keep the issue `held`, `merged_while_held`, under the rest of decision 0174: an outsider's counts only where a person had admitted it by then, and a person's hands-off beside them excuses them | Done from `held` is a change by the platform the issue Lifecycle does not declare |
| Unlinking | A keyword's link cannot be unlinked by hand, so a pull request linked both ways and unlinked by hand after the merge still stands by its keyword: decision 0174's release by unlinking ends a link by hand alone | A person ends a keyword link's hold by the close this record's "Ending the hold" row names |
| Rows 4 to 7 | They read the links as they stand: a pull request whose keyword an edit took out, and which no link by hand holds, opens nothing, and nor does one whose last link by hand an unlinking undid, an unlinking whose actor is not read until trial P-61 shows who can. Row 1 agrees: a keyword whose every span was seen gone before the merge's second was no link at it, so a person's edit that takes out a mistaken keyword before any merge ends the link it made; one taken out in that second or after still stood, under ruling (1). | An edit after the merge | Once a pass has seen a pull request's keyword the port keeps listing it, with `keyword` false after an edit takes the keyword out, so no edit after the merge moves the issue, and a keyword first seen after the merge, or taken out before it and put back after it, reaches back to nothing | Ruling (1): an admitted outsider who could release the hold by an edit would move held to done, a stranger's change the Lifecycle does not declare |
| The same second | A keyword first seen in the merge's second, or by no pass, is no link before it, and one seen gone in that second or after still stood, and decision 0132's Factory's or person's merge beside another in its second is still `done` | In one second no order can be told |
| Ending the hold | A person's close of the rival after the merge releases it, read only where the closer is a person (ruling (2) (a)). The close's actor is a fact that "Facts: a linked pull request's close and reopening, so that row 1 reads a rival as it stood at the merge" (issue 672) adds, grounded by trial P-61; until then the hold reads as before, and a writer's reopening, a new life, ends it | A keyword link cannot be unlinked by hand, and an edit no longer ends it |
| What waits | The issue port that reads `keyword_spans` from the pass records, which is not built: it reads only records the Factory itself wrote, and takes anything else as no time, and lists only a pull request with a keyword now or once seen, a link by hand, or a close it made, since one listed for nothing defers the issue; the issue world gives every keyword link no span, so it reads as before. The Consumer entry stays as ruled: not read at the merge (ruling Q2 on the issue the Status names) | Ruling (3) |

## Why

Record 0174 placed a link by hand at the merge and left a closing keyword's link with no time. The Factory's pass records are a history GitHub does not keep, and they already hold each issue's linked pull requests, so the first pass that saw a keyword gives its link a time a stranger cannot reach back past.
