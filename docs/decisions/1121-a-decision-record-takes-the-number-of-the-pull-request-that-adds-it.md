# 1121. A decision record takes the number of the pull request that adds it

Status: accepted. The Maintainer's decision of 2026-11-21, on the Solution Architect's design of the same day, relayed by the Factory Builder.

## Decision

| What | Decided | Because |
|---|---|---|
| The number | A decision record takes the number of the pull request that adds it, written with four digits or more, in its file's name and at the head of its title. A pull request adds one record at most, and no two records share a number | The pull request's number is unique and known as soon as it opens. Numbers handed out in advance made records merge strictly in order, so one pull request held in review held every later one |
| The flow | The record is written under a number of the author's choosing, the pull request is opened as a draft, one commit renames the record and every mention of its number to the pull request's number, and the pull request is then marked ready. A pull request closed and opened afresh renames its record again. Its body names "the record this pull request adds", never a number | The number is known only once the pull request opens, and a body that names no number need not change when the number does. The flow is the author's way there; the checks hold what it ends in |
| Where it is held | `tools/check_context.py` takes each record's number from its file, at least four digits, and refuses two records of one number. `tools/check_decisions.py` compares numbers as numbers. The commits' job, `tools/commits_are_the_maintainers.py`, refuses a pull request that adds two records, or one numbered otherwise than by it: on a pull request by the payload's number, on a merge group by the number its ref names. A rename adds the record it names | The commits' job runs from the base (decision 0023), so a change cannot loosen the rule for itself; and a merge group's base is the entry before it in the queue, so the records it reads are its own pull request's |
| What it ends | Records are no longer numbered from 0001 with no gap. A record that replaces another still names one of a lower number, which main holds | Numbers now leave gaps, and follow when a pull request opened, not when it merged |
| The chain before it | Until the records numbered in advance have merged, a record numbered within them, from 0235 to the last the Factory Builder handed out, stands as well, as `CHAINED` in `tools/commits_are_the_maintainers.py` says. It is taken off once the last of them merges | Those pull requests keep their numbers, so none is renamed and no approval is dismissed, and they may merge in any order |
| The limit | A pull request that must add two records is closed and its records are opened in pull requests of their own; one that must replace a record of a higher number, added by a pull request opened after it, is closed and opened afresh, under a higher number. Both are rare | One record to a pull request is what lets the number be the pull request's, and a record replaces only one of a lower number |

## Why

Each record took its number from the Factory Builder before it was written, and the records merged in that order. A pull request held in review held every record after it, and a record that had to move cost a rename and a dismissed approval. The pull request's own number is unique without anyone handing it out, so the order of merging no longer matters.
