# 0043. A scheduled tick is a backstop of hours; the relay carries W-2, and a pass records what started it

Status: accepted. Taken as a working ruling on 2026-10-21 for "Design: a scheduled tick is a backstop of hours, not minutes (P-8 ticks failed)" (issue 246), which the Maintainer may overturn in review. The Maintainer accepted, the same day, that W-2 is not met while the relay is down. It adds to `docs/decisions/0011-the-poller-and-the-view-are-measured.md`, whose thresholds it reads, and to decision 0036, whose next pass it starts.

## Decision

| What | Decided | Because |
|---|---|---|
| The schedule | A backstop of hours, not minutes. In this repo, over 28 hours, 19 of 335 due ticks arrived, the gap between runs was 287 minutes at the 95th percentile, and the first run came 231 minutes after the workflow landed (`trials/P-8.ticks.json`). More schedule lines are the same scheduler more times: three lines five minutes apart gave those figures | Design section 7.3 assumed about 60% of ticks dropped; the measurement is 94% |
| W-2 while the relay is down | Not met, and accepted. A change that produces no event waits for a tick, which came 287 minutes after the last at the 95th percentile, and correctness never depends on it (W-1). What bounds it is that the outage is itself shown within fifteen minutes, on a page that computes it in the browser with nothing having to run, so those hours are hours a person knows about. Until that page exists, in slice 4, it is raised by the first pass after the gap. Option 3, the looping job, is not pursued | No carrier the design has meets W-2 without the relay. The looping job would hold a runner slot for the length of every outage, on terms GitHub has not answered, for an outage the relay's host makes rare. W-2 was always the relay's (decision 0011) |
| A chain | A pass starts its successor only for an item due at its end, and only while the passes of the last hour are fewer than W-4 allows, twenty at the cost `trials/P-8.json` estimated with every page read; anything later waits for a tick, a nudge or a Run's end. A broken chain restarts on a tick, on the relay's nudge, and, from the first day and with the relay down too, at the end of any Run: the poller listens to the completion of the Factory's Run workflows (`workflow_run`), named in its file, never to its own, and reads nothing from the run that ended. `docs/standards/workflows.md` gains that trigger for the poller alone, on these conditions, in the workflows story | Every Run's workflow ends in an event in the Factory's repo. With ticks hours apart, "due sooner than the next tick" would be nearly always, and a successor for an item due later would chain passes back to back until it was due, past W-4. So a successor answers only what is due now, within W-4, as decision 0036 and W-7 want. A fork's run of the same name can cause one pass, which anyone can already, and direct nothing |
| The not-run alert | Set from the relay's cadence, read from the poller's run records, cancelled runs among them, as well as its passes. Nothing the relay sent starting a run for fifteen minutes, W-2's figure, raises one alert for one cause (L-48), held until the relay starts a run again. No pass at all for six hours, above the longest gap the schedule left, is the same alert with a second cause named, the whole poller's, cleared at the next pass. Until the relay runs, in slice 3, only the second is read. `passes_since` starts again only after a gap of the second reading, never at a chain that ended with nothing due. The page computes both readings in the browser from `view/health.json`, so the alert needs no pass to run; until the page exists, in slice 4, the first pass after the gap raises it | Set from the schedule's 287 minutes, an outage would go unseen for hours; set from its nominal five, the alert would fire all day |
| What a pass records of its start | `started_by` in `pass/1`, required, a code read from the run, never from anything a dispatch carries: `schedule`; `own_repo` for `workflow_run`; `successor` for a dispatch by the workflow's own token; `dispatch` for a person's dispatch and any re-run; `relay` for the relay's public event sent by the relay's own account; `public` for that event sent by anyone else. An account is told by its type and id in configuration, never a name's spelling | The alert and decision 0011's thresholds are computed from the records. Without the start, a pass the schedule started after five hours looks like one the relay started. The relay's event is one anyone may cause, so only its account tells the relay's from a stranger's, and a stranger's star can neither silence the alert nor pass for the relay |
| The trials | P-31, the relay's host, joins batch 2 of §6.1 beside P-20, the public event, which runs first of its story; P-31 is a story of its own. The relay stays in slice 3, and slice 0's exit does not change | W-2 rests on the relay alone, so both are settled early. The first approval does not need W-2, since a Run's end starts its passes, so neither is on §9.1's path to it |

## Why

Trial P-8's ticks part failed on 2026-10-20, and section 7.3 leaned on the schedule in three places: as the fallback when the relay is down, as what restarts a broken chain, and, by implication, as what the not-run alert is set from. Nothing built depends on the schedule yet, since the poller, the relay and the nudges are all slice 1 or later, so this is the time to say what each now rests on. The pass record is where the Controller's health is read from, so what started each pass is recorded there as a code, as everything in a pass record is.

## Boundaries

| Boundary | Check |
|---|---|
| A pass records what started it, always, as one of six codes, never a sentence | `tools/check_examples.py`, `examples/invalid/pass.a-start-in-words.json`, `examples/invalid/pass.no-start.json` |
| A scheduled tick can be lost, as the tick probe recorded, and the schedule alone does not carry W-2 | `tests/test_tools.py::test_the_tick_probes_intervals_are_held_to_its_runs` |
| A pass starts its successor only for an item due at its end and within W-4's passes an hour, and a broken chain restarts at a Run's end, the relay's nudge or a tick | waiting on `controller/` |
| The poller listens to the completion of the Run workflows named in its file, never its own, reads nothing from the run that ended, and is the one workflow that may run on `workflow_run` | waiting on `.github/workflows/poller.yml` |
| `started_by` is read from the run, an account by its type and id in configuration, never from a name's spelling or from anything a dispatch carries; the relay's event from any other account is `public`, and a re-run is `dispatch` | waiting on `controller/` |
| The not-run alert fires once after fifteen minutes with no run the relay started, cancelled ones counted, holds until one starts, and names a second cause after six hours with no pass at all, which clears at the next pass and alone restarts `passes_since`; the page computes both in the browser from `view/health.json` | waiting on `controller/` |
