# 0210. A Run that did not succeed and lists no record is read after a second look, and each port waits by the entry's sleep

Status: accepted. The Factory Builder's ruling of 2026-11-13 on the follow-ups of the `reconciliation_unreadable` alert of "Factory alerts" (issue 709), which `docs/decisions/0190-a-pass-that-did-not-succeed-and-lists-no-record-is-read-after-a-second-look.md` left to a ruling of their own. It decides 0190's last row, "A Run that did not succeed and lists no `applied`", and amends `docs/decisions/0112-a-pass-gathers-what-reconciliation-reads-and-carries-what-it-has-read.md`: its row "What it reads of what was recorded", where it says "One that failed and lists none may be yet to, so it too is read again, without being short", and its Boundaries rows on a pass's attempt and on a listed Run, where they say such a pass is read again and leave such a Run to be read again, stand amended by 0190 for a pass and by this record for a Run; the rest of each row stands.

## Decision

| What | Decided | Because |
|---|---|---|
| A Run that did not succeed and lists no `applied` | `adapters/applied.py`'s `effects` looks at it once more in the same pass. Listing none again, it is read: it goes into what the record carries with no `applied/1`, and no later pass asks of it | Decision 0190's reason, for a Run: a completed run uploads nothing more, so "may be yet to" covered only a list that lags. Read again at every pass, each such Run spent one of the 50 reads a pass makes, as the passes did before 0190; a run of failed Runs, as in an outage, could leave reconciliation short for as long as they stayed in the window |
| The wait and each look | As 0190 has them for a pass: one wait of 5 seconds (`WAIT`) before every second look, none when no Run is looked at again; the second looks at most as many as the first. Each look, the first and the second, asks for the Run's list of artifacts uncached (`Cache-Control: no-cache`), through `adapters/artifacts.py`'s `applied`, which now takes `fresh` | The same lag, read by the same port. GitHub lets a list be held for 60 seconds (decision 0036), so a second look answered from the first's would settle nothing, and the Run would be read as having recorded nothing for good |
| What the second look finds | A record: read as any record is. None, or one past its retention: the Run is read, with nothing recorded. A list or a record that cannot be read, or a read never answered: the Run is not read, and what was read is short | As 0190 |
| A Run that succeeded and lists none, or whose first read was never answered | Unchanged: short at its one look, never looked at twice | A Run that succeeded uploaded a record, so none listed is a deletion; a read never answered is no look at all |
| A write such a Run made | Matched to no record, so `write_unmatched` is raised | Reconciliation fails closed, as 0190 has it for a pass |
| The entry's wait | `controller/__main__.py` hands its own `sleep` to the records port, to `effects` and to `passes.written`, through `read` and `recorded_effects`, where each port fell back to `time.sleep` before | A port's wait was the clock's whatever the entry was given, so a test of the entry slept for real and could not see the wait |

## Why

Decision 0190 settled the passes, where the alert was raised, and named the same shape in the Runs as left to its own ruling. The Runs' read had the same cap and the same fallback, so a stretch of Runs that failed before they recorded anything, as an outage makes, would have spent the cap at every pass in the same way. Reading them after a second look, as 0190 reads a pass, costs one wait of 5 seconds in a pass that finds one, and fails closed: a write such a Run made is matched to no record. The waits had to reach the entry's own sleep for a test to hold them; before, each port slept on the clock whatever the entry was given.
