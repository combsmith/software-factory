# 0103. A check a job creates reads as the first suite's workflow, an upload can turn CodeQL neutral, and the queue's base and a stale dismissal hold

Status: accepted. P-35, P-36, P-37 and P-38, run on 2026-10-31, under the orchestrator's rulings of 2026-10-31.

## Decision

| What | Decided | Because |
|---|---|---|
| P-35 | `trials/P-35.json`, fail on its last part: a check run a job creates with `GITHUB_TOKEN` and `checks: write` lands in the first Actions suite on the head and reads with that suite's path, another workflow's where that suite is another's. The rest was as asked: a job a pull request adds under a required check's name reports with its own file's path, no path carried a ref suffix, and CodeQL's check has no workflow run. A dynamic run's path is given over REST alone: GraphQL gives its file as null | The design expected such a check under its own workflow's path |
| What the token can change | Of another job's check, its `external_id` and output title. Not its status or conclusion (403). Not its name or `details_url`: those answer 200 and stay as they were, while the job ran and after it failed. So every check under a name stays readable | Each field was tried alone (`trials/P-35.json`) |
| What the path pin proves | The App, and not which file ran. Decision 0026 keeps the pin. Once the real check is listed, both are read and any failing one fails the Lens, in either order. Until then a forged success stands alone and reads as passing: a job with `needs` has no check run until it starts, and `verify` waits on the mutants. A null path under a Lens's name makes the Lens unreadable, for the Maintainer | A forged check with the App and path of a real one cannot be told from it by those two alone |
| Who can post | A job on a branch with no pull request can post to another branch's head, where it reads with that head's App and path, so the target's diff touches no protected path. It needs write access to push the workflow. A fork's token is read-only by GitHub's documents, not tried here | `trials/P-35.json` posted to another head and was answered 201 |
| Not run | Whether the ruleset's required `verify` accepts a forged check on a merge group's head | No trial asked it |
| The port's rule | Issue 439, "Checks port: a required Lens's check is read only where its details URL is the job's own, as P-35 found": a check under a required Lens's name whose `detailsUrl` is not `/actions/runs/{run}/job/{id}` of its own run and id is unreadable. It closes the window. A created check's stayed `/runs/{id}`: a job asking for a job's form when it posted, or by PATCH on its own created check with the id of the run its suite is in, or its own, was answered 200 or 201 and left as it was, in progress and completed. A job's `external_id` can be forged. The tell rests on those attempts, with `GITHUB_TOKEN`, and is no promise from GitHub | It tells a real job from a created check where the App and path cannot |
| What it gates | That rule gates the first approval, as a sub-issue of the epic for it. It does not gate the first cut: the cut reads `verify` on main's head after the real job has finished, every check under that name must pass, and a held merge window leaves no one posting | The orchestrator's ruling of 2026-10-31 |
| A change to `.github/` | The Maintainer's accepted risk, in his words of 2026-10-31: a model's review is enough, a pull request touching workflows follows the same path as code, and the machine user may approve it. No change to `lens_inputs`. A change adding a workflow reaches `issue_approval` on a model Lens's review alone. What remains after the port's rule above: a model-approved workflow could hold secrets or post other checks | His ruling, asked by the orchestrator once this was run through the Kernel |
| The Controller's half of P-35 | Stands on the reader's read, not run: the reader read the path in P-8, and the Controller holds each permission the reader does | Ruling of 2026-10-31 |
| P-36 | `trials/P-36.json`, fail: it can. Under default setup GitHub would not process the upload, yet CodeQL's check run went from `success` to `neutral`, on the same id, on each of two pull requests. Overturning a failing verdict is not shown: on the file meant to fail it, CodeQL's analysis recorded two results and its check still concluded `success`. `tools/check_workflows.py` already refuses `security-events: write` on any job, and `tools/check_apps.py` for the Factory's Apps; these are the rule. The Kernel reads `neutral` as unreadable, so the Lens does not pass | The design expected "It cannot" |
| P-37 | `trials/P-37.json`, pass, read only from combsmith/software-factory's own queue, which builds five groups at once; the canary's builds one. In all 228 groups the commit the branch names is the head's one parent. In all 35 groups built while the group ahead still ran whose log says so, `merge_group.base_sha` is that commit, the head of the group ahead. 15 older ones have no such log line. The fake applies no rule for this value, so a test holds it and no rule is grounded | Decision 0023 left the value the event carries to this trial |
| P-38 | `trials/P-38.json`, pass: a person's push dismissed each approval on the pull request and is named the dismisser, with the push's commit and no message, and each approval stays on its commit with its reviewer. P-7 shows an App's push | Decision 0025 reads an approved contract at that commit |
| The fake's rules | `actions_runs_a_job_under_any_name` and `a_persons_push_names_the_person_as_dismisser` are grounded, each read by the port. `a_check_names_the_workflow_that_ran_it` and `only_codeql_gives_the_code_scanning_verdict` are contradicted, and `a_contract_approval_stays_on_its_commit` and `an_acceptance_result_names_its_reporter` are not fully shown; each stays unverified, with why. Changing the fake is "Fake GitHub: the check rules P-35 and P-36 contradict" (issue 440) | A rule is grounded only where a fixture shows what the fake assumes (L-51) |

## Why

The Kernel reads a required Lens by its App and file because any job can post under any name. These trials show the file is weaker evidence than it looked, and say which reads still hold, and from when.
