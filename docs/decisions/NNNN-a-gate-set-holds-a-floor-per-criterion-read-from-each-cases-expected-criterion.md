# NNNN. A gate set holds a floor per criterion, read from each case's expected criterion

Status: accepted. The Factory Builder's assignment of 2026-11-09 of issue 692, "A gate set holds a floor per criterion, read from each case's expected criterion", a precondition of gate v1 from the Evals v2 session. The Maintainer accepted publishing each criterion's counts in a gate set's report. It builds on decision 0164's report of counts alone and decision 0169's pool.

## Decision

| What | Decided | Because |
|---|---|---|
| The floor | A gate set's manifest may give `criterion_bars`, `{criterion: [n, d]}`: of the case-runs of the cases whose expected criterion is that criterion, at least n/d pass. A criterion it does not name has no floor. Only a gate set may give it; each key is a criterion its Role's rubric names, and each a whole fraction, d at least one and n no more than d | A gate set's bars are one per kind, `met` and `finding`. A reviewer blind to one criterion still clears both while that criterion's cases are few among the findings |
| Where a case's criterion comes from | Each fetched case's `expected.criterion`, as `kinds_of` reads each kind (`criteria_of`); the manifest carries none per case | The cases' own words are what the job scores against, and a manifest that named them would show the set's composition beside its hashes |
| What the report says | `eval-aggregate/1` gains `criteria`, `{criterion: {cases, passed, interval}}` of each criterion the set's cases expect, counts alone, null where the kinds are; and `criterion_bars`, the floors applied | So that the pool can sum each criterion over dispatches, as it sums each kind. It publishes how many of the set's cases name each criterion, which the Maintainer accepted |
| How one report is held | `aggregate_verdict` holds each criterion's counts to the set's count and the report's passes, each interval to its counts, each criterion by its id and with a case at least, every floor's criterion counted, and none where no kind was read (`count_differs`); the floors to the manifest's (`bars_differ`). A single report is never failed by a floor | A floor, as each kind's bar, applies to case-runs summed over the pool (decision 0164's condition) |
| How the pool is held | `pooled_verdict` holds every report to the same criteria, each with the same cases (`count_differs`), sums each criterion's cases and passes, and holds each named criterion to its floor, `criterion_failed`, after each kind's bar | Every report is of one set, so one that counts other criteria is not the job's |
| Its record | `bars_said`, the sentence a gate set's record holds word for word, adds its floors where it gives any | The record states what the manifest gives, as decision 0169 has it |
| Residual: a floor is as strong as its manifest | A gate set's manifest is under `evals/`, which no person need approve, so a later edit there and in its record can lower or drop a floor; unlike each kind's bar, a floor has no level beneath which it cannot go. That is no lower than the gate was before floors, and decision 0169's residual on who may change a gate set stands for it | Written down, so that the gap is not silent (the security read of this change) |

## Why

The kinds' bars measure a reviewer over every criterion together. A reviewer blind to one criterion loses only that criterion's share of a kind, which, among forty cases, can still leave the kind above its bar. A floor per graded criterion closes that, without a rule per case, which would need the ledger read: each criterion is counted where the cases are, published as counts alone, and summed over the pool as the kinds are.
