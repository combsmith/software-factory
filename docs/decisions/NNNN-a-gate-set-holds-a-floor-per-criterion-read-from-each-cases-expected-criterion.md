# NNNN. A gate set holds a floor per criterion, read from each case's expected criterion

Status: accepted. The Factory Builder's assignment of 2026-11-09 of issue 692, "A gate set holds a floor per criterion, read from each case's expected criterion", a precondition of gate v1 from the Evals v2 session, and the Factory Builder's two rulings on it of the same day: counts are published for the floored criteria alone, each of `ORIGIN_LEAST` cases at least, and a floor counts the cases that expect a Finding on its criterion. The Maintainer accepted publishing counts, not single cases' outcomes. It builds on decision 0164's report of counts alone and decision 0169's pool.

## Decision

| What | Decided | Because |
|---|---|---|
| The floor | A gate set's manifest may give `criterion_bars`, `{criterion: [n, d]}`: of the case-runs of the cases that expect a Finding on that criterion, at least n/d pass. A criterion it does not name has no floor. Only a gate set may give it; each key is a criterion its Role's rubric names, and each a whole fraction, d at least one and n no more than d | A gate set's bars are one per kind. A reviewer blind to one criterion still clears both while that criterion's cases are few among the findings |
| What it counts | The cases that expect a Finding on its criterion, and no clean case of it: the floor measures recall on that criterion | A reviewer blind to a criterion passes its clean cases by raising nothing, so counting them would let it clear the floor: with ten of each under a half, a reviewer that raises nothing would score ten of twenty. False positives on clean cases stay with the met kind's bar, unchanged |
| Where a case's criterion comes from | Each fetched case's `expected`, as `kinds_of` reads each kind (`criteria_of`); the manifest carries none per case, and no case's text names a published criterion: only the manifest's floors are counted | The cases' own words are what the job scores against; a manifest that named them would show the set's composition beside its hashes |
| The least | A floored criterion needs `FLOOR_LEAST`, `ORIGIN_LEAST`'s ten, cases that expect a Finding on it. With fewer, `fetch` stops the dispatch, `eval_floor_short`, before any case is asked. So it does where the cases that expect a Finding on no floored criterion are some but fewer than ten: the kind's count less the floors' publishes their count too | A count of a group of one is that case's verdict. Decision 0164 holds every published group to the same least so that no count becomes an oracle on one held-out case |
| What the report says | `eval-aggregate/1` gains `criteria`, `{criterion: {cases, passed, interval}}` of each floored criterion and no other, counts alone, null where the kinds are; and `criterion_bars`, the floors applied. No criterion the set does not floor is broken out, but the kind's counts less the floors' are those of the cases that expect a Finding on no floored criterion, so that group is held to none or ten at least too | So that the pool can sum each floored criterion over dispatches, as it sums each kind, and nothing more is published than a floor needs |
| How one report is held | `aggregate_verdict` holds the criteria to the floors, each of `FLOOR_LEAST` cases at least, together within the kind's cases, its passes and its failures, and leaving none of its cases or `FLOOR_LEAST` at least, each interval its counts', and none where no kind was read (`count_differs`); the floors to the manifest's (`bars_differ`). A single report is never failed by a floor | A floor, as each kind's bar, applies to case-runs summed over the pool (decision 0164's condition) |
| How the pool is held | `pooled_verdict` holds every report to the same cases of each floored criterion (`count_differs`), sums each criterion's cases and passes, and holds each to its floor, `criterion_failed`, after each kind's bar | Every report is of one set, so one that counts other cases is not the job's |
| Its record | `bars_said`, the sentence a gate set's record holds word for word, adds its floors where it gives any | The record states what the manifest gives, as decision 0169 has it |
| Residual: a count still moves by one case | A floored criterion's passes, published on every dispatch, still change by one when one of its cases' outcome does. With ten cases at least, which case moved cannot be told from the counts, as for a kind or a group of natural cases | Written down, as the Factory Builder asked: ten is the least below which a count would name its case outright |
| Residual: a floor is as strong as its manifest | A gate set's manifest is under `evals/`, which no person need approve, so a later edit there and in its record can lower or drop a floor; unlike each kind's bar, a floor has no level beneath which it cannot go. That is no lower than the gate was before floors, and decision 0169's residual on who may change a gate set stands for it | Written down, so that the gap is not silent (the security read of this change) |
| Residual: the rubric read is the job's own | `held` checks each floor's criterion against the rubric of the checkout the job runs, not the judged commit's; a criterion added at the judged commit would make the set `eval_set_unreadable` until the job's Release has it | That fails closed (lane d's read of this change) |

## Why

The kinds' bars measure a reviewer over every criterion together. A reviewer blind to one criterion loses only that criterion's share of a kind, which, among forty cases, can still leave the kind above its bar. A floor per graded criterion closes that, without a rule per case, which would need the ledger read: each floored criterion's findings are counted where the cases are, published as counts alone of at least ten, and summed over the pool as the kinds are.
