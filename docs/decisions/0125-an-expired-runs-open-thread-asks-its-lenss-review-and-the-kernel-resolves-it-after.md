# 0125. An expired Run's open thread asks its Lens's review, and is closed once a later review supersedes it

Status: accepted. The Factory Builder's ruling of 2026-11-02 on "An expired Lens Run's open threads can be closed without a person, by that Lens's ruling carried out by the queue App" (issue 420), part of "Epic: slice 1, first approval. A Release on next reviews a pull request to this repo, and the machine user's approval stands" (issue 182): option B, the thread closed once its Lens has reviewed again and never by a ruling, with a Solution Architect's read agreeing. It removes the limit of decision 0096's row "The limit", and adds a way to decision 0086's row "When a Lens's thread is closed": the queue App's resolution of an expired Run's thread once its Lens has reviewed again. The Maintainer may overturn either in review.

## Decision

| What | Decided | Because |
|---|---|---|
| Which thread | An expired Run's thread: a required model Lens's thread whose category, severity and ruling the port could not join, and whose Lens's latest Run that started at or before the thread opened is one `expired_reviews` names. `kernel/derive.py`'s `expired_threads` reads it from the facts and the run records, with no new fact. Any other thread with no category stays `thread_unreadable` | A Lens's Runs on an item run one at a time (section 2, a concurrency key per Work item), so a thread opens between its Run's start and the next's. Nothing else says why a category is missing, so nothing else is read past |
| How it is read | `as_read` marks it `expired`, and `superseded` once its Lens has a review that succeeded and started after the Run that opened it. Its category, severity and ruling stay as the port gave them: the port joins no ruling to it, and nothing makes one up. Each thread is marked by its place in the list, never its id, and a mark the facts arrive with is dropped, as no fact | Its Finding is gone, so there is nothing to rule on |
| Until it closes | It gates at any severity, as a security Finding does (`kernel/gate.py`'s `gating_threads`), and decision 0096's re-ask admits its Lens's review of the current content while it is open | It may have been a security Finding. The review is the action the Kernel already asks for |
| When it is closed | While open and once superseded, it is the Kernel's `resolve_thread` act, as decision 0086 has it, and the queue App's resolution closes it (`closed()`). That does not depend on the current content, so a push after the review does not reopen it. A person's resolution closes it at any time, as any Lens's thread. The Lens's own App, the author's or any other closes nothing, and the thread it resolved stays unreadable, since it is no longer the queue App's to resolve; the queue App's before the review closes nothing until the review has run | The fresh review says what the Lens now holds of the change, and anything still standing it raises on a thread of its own (decision 0075) |
| Where it is read | In `derive`, before every reading of the item, queued or not, so `reading` and the queue's gates read the same facts. The facts given are never changed | One reading of the threads, wherever the Kernel reads them |
| What is not built | The queue App's act is `not_built` until "A narrow queue App, combsmith-sf-queue, enqueues and dequeues with contents and pull-request write alone (P-2)" (issue 381) lands. Until then the act is recorded and nothing closes live | Decision 0051 |
| The residual risk | The thread closes because the fresh review did not raise its problem again, not on a ruling. Its category cannot be read, so it may have been a security Finding. A problem the thread held that the fresh review of the current content does not raise, security included, is no longer held once the thread closes. That is the miss decision 0075 accepts for a thread that is gone. It is not the acceptance of a declined or deferred security Finding (decisions 0007 and 0086), and those guards stand. It applies only to pull requests open past the 90-day retention, and a person may resolve such a thread at any time | The other route, a ruling by thread id, changes `task/1`, `result/1`, `applied/1` and the port, and puts comment text any writer can edit in front of the model. A Lens owning security never closing its threads would close none |
| What the join assumes | A start is GitHub's `run_started_at`, which a re-run moves later, so a thread its first attempt opened precedes it. While a re-run of the Lens on the item starts after the thread opened, and was dispatched before it or at a time that cannot be read, nothing is read past the thread: it stays unreadable, and a person resolves it. A thread opened in the same second a later Run of its Lens starts is read as that Run's. An opening time that cannot be read joins no Run | Each reads the safe way: what cannot be joined stays unreadable |

## Why

A pull request open past the 90 days an artifact is kept could not converge while its expired Lens Run's thread was open: the thread could not be read, and only a person could close it. The fresh review the Kernel already asks for is the Lens's judgement of the content as it now is, so the old thread is closed once it has run.
