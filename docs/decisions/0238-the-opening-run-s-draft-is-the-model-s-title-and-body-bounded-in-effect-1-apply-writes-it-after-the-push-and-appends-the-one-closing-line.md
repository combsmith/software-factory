# 0238. The opening Run's draft is the model's title and body, bounded in effect/1; `apply` writes it after the push and appends the one closing line

Status: accepted. Taken on the Factory Builder's rulings of 2026-11-20 for "The opening Run lands its one commit and opens the draft: the push write, apply's dispatch and `#342`'s writer (slice 2, S6)" (issue 838): the draft's title and body come from the Result; `apply` appends its own closing line, the only link in the draft; `apply` refuses link-shaped text in the Result's own words, in a guard of its own; the bounds live in the schema as `maxLength`, the one source of truth, as `patch.body`'s does; the draft goes to the default branch from the work branch the Decision admitted, and a Run admitted on a work branch at the commit an earlier opening Run of this issue pushed pushes nothing. It builds the Effect that "Acceptance: a pull request the Factory opens is bound to its issue by the Run that opened it" (issue 342) left waiting, amends decision 0097's row "The record", and names what decision 0102's row "When the Factory opens its own" still waits on.

## Decision

| What | Decided | Because |
|---|---|---|
| The Effect | `effect/1` gains `open_pull_request`, one to a Result: the model's `title` and `body`, each text under a `body` (the title as `{"body": ...}`, as a push's patch is), both required, the title with at least one character that is not white space and the body not empty, and nothing else. No Role permits it yet. The title's pattern also refuses a title that ends in a line break, as the validator refuses any value under a pattern that does; no one-line title needs one | A string a Run carries is a code unless it is named `body` (`schemas/AGENTS.md`), and the title is the model's text. A Result that names where its draft opens could open it anywhere |
| What is `apply`'s | The branch the draft is opened from, the work branch the Decision admitted (`factory-work/issue-<N>-<k>`); the branch it is opened to, the default branch; that it is a draft; and the closing line, the one link in the draft, which closes exactly the Run's issue and which `apply` appends to the model's body. Each is read from the Decision and the issue, never the Result | `apply` decides where a write lands, as it does for a push's commit and a review's (decision 0188). One closing line written by `apply` means the draft closes exactly its issue, and no text of the model's links anything |
| The bounds | GitHub refuses a pull request whose title is over 256 characters, or whose body is over 65,536. The title is the model's alone: at most 256. The model's body is at most 65,000, leaving 536 characters for `apply`'s closing line, far more than a line that closes one issue by its number takes. Each is stated in `schemas/effect.schema.json` as `maxLength`, and nowhere else, counted in code points as the validator counts them, a character outside the Basic Multilingual Plane as one. A Result over either is no Result, `result_invalid`, the Role's. A stated limit: no trial grounds the unit GitHub counts a title or a body in, so a draft near a bound in characters outside the Basic Multilingual Plane may pass here and be refused by GitHub after the push. The writer, built in a pull request of its own, is to refuse before any token is minted a title or a body whose UTF-8 encoding is over GitHub's limit in bytes | A guard writes no number, so the schema is the one source of truth, as `patch.body`'s 200,000 is. A bound GitHub alone held would be a failed write after the push, not a refusal before any token is minted |
| Alone or after a push | The schema lets a Result carry `open_pull_request` with `push_commits` or alone; it cannot say which, as the validator reads no keyword that ties one list to another. `apply` is to hold it from the Decision, as decision 0219's row "Who opens the draft" has it. Where the admitted branch head is none, the Result pushes and opens, and an opening with no push is refused before any token is minted. Where it is a commit, the Task permits no `push_commits`, and the Result opens alone only if that commit is the one an earlier opening Run of this issue pushed, as that Run's `applied/1` records its push's landed commit; a branch at any other commit is refused before any token is minted, and no draft is opened from it | Section 4.1's recovery, as decision 0219 has it: the branch name is the recovery key, and an opening `apply` that died after its push leaves its whole commit on the branch, from which the next opens the draft and pushes nothing; a branch at another commit holds what no Run of this issue handed over |
| The order | `apply` writes the push first, then the opening, then the rest: `harness/apply.py`'s `ORDER` gains `open_pull_request` after `push_commits`. `effect/1`'s types and `applied/1`'s list them in that order | GitHub opens no pull request whose head holds no commit the base does not; the draft must hold the commit just pushed. An opening whose push did not land is not sent |
| The text | `apply` refuses, before it mints any token, a reference GitHub could read as a link (`#` and a digit, an issue or pull-request URL, `owner/repo#`), an @-mention, or a closing keyword (close, fix, resolve and their forms) in the Result's title or body: a pure guard of `guards/`, built in a pull request of its own, which adds its row below | The closing line is the draft's one link. A link in the model's text could close, or bind, another issue, or call a person, from text an item's author can steer |
| The record | `applied/1` records `open_pull_request` as one of `effect/1`'s types, which a Result now asks for, keyed by the pull request's number as read back, through `harness/apply.py`'s `opened` (decision 0097). This amends decision 0097's row "The record", which listed it "as one no Result asks for yet" | The writer joins the Effect a Result asks for to the record decision 0097 already reads |
| What waits | The writer, a port of `adapters/` that opens the draft and reads it back; `apply`'s dispatch, its order, the hold of a push and an opening against the admitted branch head, its call of the guard and its call of `opened` (a hand pull request, decisions 0052 and 0153); the guard; the grant in `config/apps.json` for `effect:open_pull_request`, a protected edit, which lands with the hand pull request that wires the dispatch or after it, never before, since until then `apply`'s `ORDER` lists no opening and one asked beside a push would be dropped unrecorded; and the Role named in `config/defaults.json`, by hand, after all of them (decision 0215). Before the first live opening, a hand pull request is also to add the opening Role's App, `qa-lead`'s (decision 0219), to `openers` in `config/hooks.json` by its login, `combsmith-sf-qa-lead[bot]`, and its bot account's id as a payload gives it, read once the Maintainer has registered the App: decision 0102's row "When the Factory opens its own" has each account join by a decision, and a pull request the App opens fails `commits` until it does | This record decides the Effect's shape; the rest lands with its own check |

## Why

Decision 0097 built the record that binds a pull request to the Run that opened it, and left its writer waiting on the push. Decision 0219 chose who opens the draft and how a Run that died after its push recovers. What was left open was what the Result says. Letting the model write the title and body, and nothing else, keeps every fact of where the draft lands with `apply`, and one closing line of `apply`'s own keeps the draft bound to exactly its issue. GitHub's own limits, less that line, are the bounds, written once where the validator reads them, since a guard may not write a number.
