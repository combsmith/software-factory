# 0238. The opening Run's draft is the model's title and body, bounded in effect/1; `apply` writes it after the push and appends the one closing line

Status: accepted. Taken on the Factory Builder's rulings of 2026-11-20 for "The opening Run lands its one commit and opens the draft: the push write, apply's dispatch and `#342`'s writer (slice 2, S6)" (issue 838): the draft's title and body come from the Result; `apply` appends its own closing line, the only link in the draft; `apply` refuses link-shaped text in the Result's own words, in a guard of its own; the bounds live in the schema as `maxLength`, the one source of truth, as `patch.body`'s does; the draft goes to the default branch from the work branch the Decision admitted, and a Run admitted on a branch already pushed pushes nothing. It builds the Effect that "Acceptance: a pull request the Factory opens is bound to its issue by the Run that opened it" (issue 342) left waiting, amends decision 0097's row "The record", and names what decision 0102's row "When the Factory opens its own" still waits on.

## Decision

| What | Decided | Because |
|---|---|---|
| The Effect | `effect/1` gains `open_pull_request`, one to a Result: the model's `title` and `body`, each text under a `body` (the title as `{"body": ...}`, as a push's patch is), both required, neither empty, and nothing else. No Role permits it yet | A string a Run carries is a code unless it is named `body` (`schemas/AGENTS.md`), and the title is the model's text. A Result that names where its draft opens could open it anywhere |
| What is `apply`'s | The branch the draft is opened from, the work branch the Decision admitted (`factory-work/issue-<N>-<k>`); the branch it is opened to, the default branch; that it is a draft; and the closing line, the one link in the draft, which closes exactly the Run's issue and which `apply` appends to the model's body. Each is read from the Decision and the issue, never the Result | `apply` decides where a write lands, as it does for a push's commit and a review's (decision 0188). One closing line written by `apply` means the draft closes exactly its issue, and no text of the model's links anything |
| The bounds | GitHub refuses a pull request whose title is over 256 characters, or whose body is over 65,536. The title is the model's alone: at most 256. The model's body is at most 65,000, leaving 536 characters for `apply`'s closing line, far more than a line that closes one issue by its number takes. Each is stated in `schemas/effect.schema.json` as `maxLength`, and nowhere else, counted in characters as the validator counts them. A Result over either is no Result, `result_invalid`, the Role's | A guard writes no number, so the schema is the one source of truth, as `patch.body`'s 200,000 is. A bound GitHub alone held would be a failed write after the push, not a refusal before any token is minted |
| Alone or after a push | The schema lets a Result carry `open_pull_request` with `push_commits` or alone; it cannot say which, as the validator reads no keyword that ties one list to another. `apply` holds it from the Decision: where the admitted branch head is none, the Result pushes and opens; where it is a commit, a Run died after its push, and the Result opens alone and pushes nothing, and a push is refused | Section 4.1's recovery, as decision 0219 has it: the branch name is the recovery key, and an opening Run that finds its branch pushed opens the draft from what is there |
| The order | `apply` writes the push first, then the opening, then the rest: `harness/apply.py`'s `ORDER` gains `open_pull_request` after `push_commits`. `effect/1`'s types and `applied/1`'s list them in that order | GitHub opens no pull request whose head holds no commit the base does not; the draft must hold the commit just pushed. An opening whose push did not land is not sent |
| The text | `apply` refuses, before it mints any token, a reference GitHub could read as a link (`#` and a digit, an issue or pull-request URL, `owner/repo#`), an @-mention, or a closing keyword (close, fix, resolve and their forms) in the Result's title or body: a pure guard of `guards/`, built in a pull request of its own, which adds its row below | The closing line is the draft's one link. A link in the model's text could close, or bind, another issue, or call a person, from text an item's author can steer |
| The record | `applied/1` records `open_pull_request` as one of `effect/1`'s types, which a Result now asks for, keyed by the pull request's number as read back, through `harness/apply.py`'s `opened` (decision 0097). This amends decision 0097's row "The record", which listed it "as one no Result asks for yet" | The writer joins the Effect a Result asks for to the record decision 0097 already reads |
| Decision 0102's list | The opening Role's App, `qa-lead`'s (decision 0219), joins `openers` in `config/hooks.json` by its login, `combsmith-sf-qa-lead[bot]`, and its bot account's id as a payload gives it, in a hand pull request, before the first live opening; the id is read once the Maintainer has registered the App | Decision 0102's row "When the Factory opens its own": each account joins by a decision, and a pull request the App opens fails `commits` until it does |
| What waits | The writer, a port of `adapters/` that opens the draft and reads it back; `apply`'s dispatch, its order, the hold of a push against the admitted branch head and its call of `opened` (a hand pull request, decisions 0052 and 0153); the guard; the grant in `config/apps.json` for `effect:open_pull_request`, a protected edit; and the Role named in `config/defaults.json`, by hand, after all of them (decision 0215) | This record decides the Effect's shape; the rest lands with its own check |

## Why

Decision 0097 built the record that binds a pull request to the Run that opened it, and left its writer waiting on the push. Decision 0219 chose who opens the draft and how a Run that died after its push recovers. What was left open was what the Result says. Letting the model write the title and body, and nothing else, keeps every fact of where the draft lands with `apply`, and one closing line of `apply`'s own keeps the draft bound to exactly its issue. GitHub's own limits, less that line, are the bounds, written once where the validator reads them, since a guard may not write a number.
