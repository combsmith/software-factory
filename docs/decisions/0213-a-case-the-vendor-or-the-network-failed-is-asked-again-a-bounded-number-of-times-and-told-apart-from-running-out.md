# 0213. A case the vendor or the network failed is asked again a bounded number of times, and told apart from running out

Status: accepted. The Factory Builder's ruling of 2026-11-13 on the second half of "The tier's limits are set from large cases with the read tools on, and a transient fault is retried" (issue 615). The first half, the limits measured on large cases, costs model spend and waits for the Maintainer; its plan is on the issue. It adds a code to `eval-report/1`, `eval-ledger/1` and `eval-aggregate/1`, `vendor_unavailable`, and two fields to a cause, and leaves decision 0131's causes and decision 0120's faults as they were.

## Decision

| What | Decided | Because |
|---|---|---|
| How the CLI says the vendor failed | It ends the run with `is_error` true, `subtype` `success`, exit 1 and `terminal_reason` `api_error`, with the vendor's HTTP status in `api_error_status`, or none where the connection itself failed. It has already retried a 500, a 429, a 401 and a refused connection for about three minutes by then, and gave up on a 529 in seconds | A probe of the CLI at 2.1.322, against a stand-in for the vendor's API on the runner's own host with a dummy key, a config folder of its own and no network beyond it: 529, 500, 429, 401 and a refused port, each recorded. The two fields are older than the probe: `trials/P-13.json`, at 2.1.302, holds both, from a run that succeeded (`api_error_status` null, `terminal_reason` `completed`). `trials/P-13.v2-1-306.json`, at the pin, holds neither, so a failed call is not trialled at the pin, which a case's own answer at the next eval will show |
| What is transient | A case's Result the Engine failed, `engine_failed`, with the call ending at `api_error` and the status a 5xx, an overload's 529 among them, or none. Nothing else: not a 4xx, whose cause a later call meets again, a rate limit's 429 among them; not a model that ran out, `no_answer`; not any other way the CLI ends | A fault of the vendor's or of the way to it is no answer of the reviewer's, and a later call may not meet it |
| What is done with it | The case is asked again, at most twice more (`RETRIES`), each after a wait of 30 seconds (`RETRY_WAIT`), only where the time left of the job's budget holds the wait and the case's whole time, read again after the wait. The case's Task, head and Run id are the same | The CLI has retried within the call already; a few more asks, a wait apart, outlast a short outage without spending a gate on it, and the job still ends before its own timeout |
| Which call's word | Of a case's several calls, where a private replay turns more than one on, the first that did not succeed, the one whose Result `passes.union` returns; each attempt starts with none | A later call's word would judge a Result it did not give |
| What it costs | Every attempt's use is the case's: its turns, cost and seconds summed onto the last attempt's Result, as a case's several calls are | A report that counted only the last would understate what the case spent |
| A case still failed | `vendor_unavailable`: an Engine fault, in `ENGINE_FAULTS`, so it closes the run as any of the Engine's faults does, told apart from `no_answer` and `engine_failed` | The issue asks that a transient fault be reported apart from running out; it is still no measure of the reviewer, so no bar can be held over it |
| What the report says | A case's cause gains `terminal_reason`, one of `api_error`, `structured_output_retry_exhausted` or `other`, and `api_error_status`, an integer from 100 to 599; a case asked again carries `retried`, how many times. A gate set's report carries one total, `retried`, of its own cases asked again: never per case, criterion or kind, so that it tells nothing of the set's make-up; its ledger marks each case, its preflight's among them | Never words in a report (decision 0131); a gate set's report is counts alone (`harness/eval/AGENTS.md`) |

## Why

A vendor's outage or a dropped connection failed a case as the Engine's fault, `engine_failed`, which closes the gate and spends the commit. Most such faults pass within minutes, and the CLI's own retries already cover the first few. Asking the case again a few times, a wait apart and inside the job's budget, keeps a short outage from costing a cut, while a long one still closes the gate, now under a code that says so. A 4xx is left alone: an expired credential or a rate limit is met again on the next call.
