# 0054. `apply` writes a Role's Effects with a token narrowed to them, and claims only what it reads back

Status: accepted. Taken as working rulings on 2026-10-22, which the Maintainer may overturn in review, for "Harness: run and apply for the review Intent, and the model holds no credential that can write" (issue 194), its second pull request. It adds to `docs/decisions/0050-the-model-is-given-a-task-and-no-tool-and-apply-writes-only-what-it-reads-back.md`, whose `apply` it builds, and to `docs/decisions/0051-the-controllers-writes-go-through-one-credential-each-and-every-one-is-recorded.md`, whose port it writes through.

## Decision

| What | Decided | Because |
|---|---|---|
| What a Result is held to | The Decision that admitted its Run, found in the pass record by the Run id, and the Role's manifest: its Role, Intent, content and permitted Effects. The Result is taken by the digest `run` reported, and held to `result/1` | A Run no Decision admitted does nothing (section 3.5); the commit bundle is taken by its digest, never its name (section 3.6) |
| A change under the Run | Before any Effect, `apply` reads the item again and writes nothing, the Run `superseded`, when the item is closed, its content moved, the Factory paused or its Pause unreadable, the item held, or the Kernel, asked again with this Run left out of the Runs, of those counted active and, by its own `GITHUB_RUN_ID`, of those listed before their name, does not admit this Run's Intent on this content. Each has its own code, in that order | A hold added while a Run waited for a runner must still bind (I-21, I-38); a Run in progress admits nothing, and this one is in progress (decision 0036) |
| A Result that may not be written | `apply` writes nothing, the fault the Role's (`item`), for a Result not this Run's or Release's, not completed, uncovered, asking for an Effect the Task does not permit, naming an Effect, a Finding or a Disposition twice, acting on a thread off the item, posting a raised Finding other than exactly once, a non-gating one on a thread or a gating one as an annotation, or one with no place; a Disposition of neither half or both, on a Finding the Task does not list, or the half its Role may not make: a proposal is the author Role's and a decision the owner's of the Finding's category; or a `security` thread resolved at all: its owner may accept only on the author's proposal of fixed or not applicable, which is in another Run's Result, and comes to the owner's Task with the fix Intent. A Result that failed for the Engine, or whose rubric cannot be read, is the Factory's (`environment`) | Sections 3.6 to 3.8 and 4.3; decisions 0029 and 0038. A thread id is global, and the App's token reaches every item it is installed on |
| What `apply` decides in a write | A review is a comment on the commit the Decision admitted, never an approval. A check run's name is `factory / ` and the Role, its conclusion `success`, and its `external_id` the Run's and the Effect's. A comment carries when the Run began and its place among the Run's comments | A Result names no one and no commit (decision 0038) |
| The token | `adapters/identity.py` signs the Role App's JWT with `openssl`, the key handed through a pipe, `/dev/fd/N`, and never written; mints a token for the item's repo alone with exactly the permissions the Effects' needs name in `config/apps.json`, each within the App's grant for that need; holds GitHub's answer to that repo and those permissions; keeps the token out of every `repr` and error; and revokes it when the writes end, whatever happened, a revocation only on GitHub's 204. Nothing is minted for a Result that is refused | Ruling 6; the standard library cannot sign RS256 and the repo installs nothing |
| The writes | A Role's writes go through `adapters/effects.py` beside the Controller's, each through the Role App's token held by `Allowed` to that one item: a review, recovered as one by this App on this commit; a check run, recovered by its `external_id` on the commit, made complete with at most fifty annotations; a thread's resolution, recovered by its resolved flag and refused off the item; a comment on the item, recovered by this App's comments since the Run began, by order and never by text. Each is sent once and never retried. A 401 or 403 ends every later write on the credential. A reply on a thread is not built yet | Section 3.6's recovery keys; decision 0051's credential and its answers |
| What is claimed | An Effect is `applied` or `already_applied` only with the key it was read back by, and each Finding it posted only with the surface it was read back on: a review comment's thread, or the check run's key and the Finding's ref. Anything less is `failed`, `not_read_back`, and the Run ends `environment`, `effect_failed`. A posted Finding is written whole as `finding/1`, its `id` `f_` and the first sixteen hex of the sha256 of its Lens, surface type and key, its source the Task's Role and App, its content the Task's. `applied/1` lists every Effect the Result asked for, `refused` with the code when the Result was refused | L-41; section 3.7: a Finding's id is from its source and its surface, never its text |
| The re-read's credential | `apply` reads the item and the run records again with the Role App's own installation token, minted read-only for exactly the needs `harness/apply.py`'s `READS` names: every fact the Kernel is asked on, and the run records with each failed Run's outcome. The Maintainer expands `combsmith-sf-pr-review` for it, rather than giving `factory-apply` a second key, so decision 0035 stands: `checks: write`, `actions: read` and `issues: read` beside its `contents`, `metadata` and `pull_requests` (2026-10-22) | One job, one key; the Kernel asked again on facts read short is no re-read |
| The Role App's grants | Until the registration changes and trial P-39 reads it again, `config/apps.json` grants none of it: the need `effect:create_check_run` waits, so a Result that asks for a check run ends `environment`, `effect_not_grantable`, and no read token can be minted. The one pull request that records the re-run P-39 maps the needs and the grants | `tools/check_apps.py` holds each grant to what P-39 recorded |
| What waits | The `apply` step's wiring: its command, and its live re-read through the facts and records ports, which needs the Bot accounts the poller's reads need too, with "Workflows: the frozen entry shim, the poller, the Run's three jobs and the nudge, each held to its shape" (issue 196). A Role's push and its refusals come with the fix Intent, waiting on `harness/push.py` | The job's reads are the poller's, and are configured once |

## Why

`apply` is the one place a Role's Result becomes a write. Everything it may refuse is decided before a token exists, so a
Result that is not to be written never holds a credential that can write. Every write is claimed from what GitHub read
back, so a claim in `applied/1` is never the model's word.
