# 0065. The pass, the Run's three jobs and the approving act are held word for word, and each runs one Release

Status: accepted. A working ruling of 2026-10-26 for "Workflows: the frozen entry shim, the poller, the Run's three jobs and the nudge, each held to its shape" (issue 196), its PR 2b-2, with the Maintainer's answers of 2026-10-21 on rulings 7 and 8 and the orchestration session's ruling of 2026-10-26 on the Release's name. The Maintainer may overturn it in review. It adds to `docs/decisions/0058-a-run-holds-its-items-lane-from-run-to-apply-and-starts-only-from-the-passs-own-token.md`, whose `.github/workflows/run-jobs.yml` it writes, to `docs/decisions/0055-the-approving-act-holds-the-machine-users-token-alone-approves-the-commit-it-re-read-and-says-whose-fault-each-failure-was.md`, whose job it writes, and to `docs/decisions/0064-a-runs-steps-read-with-their-own-key-and-revoke-it-and-every-run-leaves-its-outcome.md`, whose steps they run.

## Decision

| What | Decided | Because |
|---|---|---|
| Held word for word | `.github/workflows/pass.yml`, `.github/workflows/run-jobs.yml` and `.github/workflows/approve-job.yml` run on `workflow_call` alone, and each is `tools/check_workflows.py`'s own text, word for word but for its comments: where each credential is, and in what order the steps run, is reviewed in the check and changed only with it. `.github/` is the Maintainer's to approve | A shape a rule only partly reads leaves a step free to move a key beside the model |
| The pass | One job, `pass`, on `factory-poller`, `actions: write` and `contents: read`. It checks out the Channel with its tags, runs the entry, `controller/__main__.py`, with the Controller's key, uploads `pass/1` as the artifact `pass` before anything is dispatched, runs the writes with the key and the pass's own token, and uploads `written/1` whatever failed | Design section 2.3: no Run starts from a Decision with no record |
| The Run's three jobs | `run`, on `factory-run`: the Channel checked out; the commit handed on; the CLI installed; the reader's step with `READER_APP_KEY` alone; the Engine's step with `CLAUDE_CODE_OAUTH_TOKEN` alone, the Engine setting the scrub and `--tools ""`; the Result uploaded, its artifact id and digest the job's outputs. `verify`, on no environment, with no secret and no cache. `apply`, on `factory-apply`, `if: always()` once `run` has handed on its commit, `NEEDS`, its steps under `if: always()`, the outcome's upload last | The Maintainer's answer (b): the reader's key revoked before the model's step; decision 0054: `apply` always runs, and its code decides that nothing is written |
| The act's job | `approve`, on `factory-approve`, with `APPROVER_TOKEN` alone, its outcome left by the same last step as `apply`'s and uploaded whatever failed. Its checkout is the Channel's: decision 0055's "no `ref:` checkout" is read as no checkout of the item's code, since every job runs the Release (the workflows story's ruling 14) | One Release for every job |
| The CLI | The second exempt install, held word for word with the file: the Engine's pin from `config/harness.json`, fetched over HTTPS alone from the vendor's release path for linux-x64, its sha256 the one `CLI_CHECKSUMS` holds for that version, as the vendor's release manifest gives it, checked before it is moved onto the path. A pin with no checksum there is refused, so a pull request that moves the pin adds its checksum | The Maintainer's answer (a) |
| The Release's name | Each workflow's first job checks out the Channel, `factory/v0-next`, once, and hands on the commit it got, `python3 -m harness.steps`; every later job checks out exactly that commit, with its tags, and no job checks out the Channel again. Only a step that needs the name reads it, the entry, `apply`, the outcome and the act, by `release` in `harness/steps.py`, one entry point: the one tag `factory/vX.Y.Z` on the commit checked out, `git tag --points-at HEAD`. The Channel's tag is no Release's; none refuses, `release_untagged`, and two refuse, `release_twice`, rather than pick, each before any key is read. It is replaced by release/current.py of the Release story's first pull request, over adapters/tags.py, and the Channel checkout by a context value for the called workflow's own commit once a trial finds one | The Release story's ruling 11; no context of the run that woke the pass is read |
| The accepted miss | If `next` moves away and back between the shim's call and the checkout, the called file and the code checked out are of different Releases | As the Release story's ruling 11 accepts; `apply` refuses a Result of another Release than its record's. And a `run` whose checkout of the Channel fails hands on no commit, so `apply` does not run and the Run leaves no outcome: read as a failed Run that left none, an attempt the Run ceiling bounds, never a checkout of the home branch's code with a key |
| The steps' workflow form | A `run:` line is `python3 -m <module>` alone, so each step with no argument reads the Run's inputs, `NAME`, `ITEM` and `PASS`, from its environment and its folders by fixed names; `run` hands on its digest as its step's output | `tools/check_workflows.py`'s `install` |
| A key's one file | `CONTROLLER_APP_KEY` and `factory-poller` are named in `.github/workflows/pass.yml` alone, in any case, as GitHub reads them; `READER_APP_KEY`, `PR_REVIEW_APP_KEY`, `factory-run` and `factory-apply` in `.github/workflows/run-jobs.yml` alone; `APPROVER_TOKEN` and `factory-approve` in `.github/workflows/approve-job.yml` alone | Decision 0035: each key lives in the environment of the one job that holds it |
| The pass's token | `config/controller.json`'s `accounts.workflow_token` is `github-actions[bot]`, id 41898282, from trial P-9, as the workflows story's ruling 10 has this pull request set it | The records port counts a Run by its dispatcher |
| Dormant | Nothing calls these files until the workflows story's third pull request lands the shims, under the Maintainer's Pause | Its ruling 11 |

## Why

The steps the Run's jobs run landed in decision 0064; these are the files that call them. Holding each file word for word is the rule the Run's shim, run.yml, is already held by, and it is the only reading under which a key cannot drift onto the model's step unseen.
