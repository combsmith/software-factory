# 0170. A gate set's dispatch asks its preflight first, and a broken one stops it before any of the set's cases is asked

Status: accepted. The Factory Builder's ruling of 2026-11-08 on issue 613, "The gate pools k dispatches on one commit and reads all of them", approving lane d's design of the preflight, points 1 to 5, with two additions: say that five cases make a false stop negligible, and hold mechanically that no preflight case is a gate set's. It is the second of the issue's two pull requests; the first, the pooled gate, is decision 0169, "A gate set's gate pools every dispatch on the commit, under the set's own bars, and a development set stays the best of several". A development set's run is unchanged.

## Decision

| What | Decided | Because |
|---|---|---|
| Which cases | A gate set's manifest names its preflight, `preflight`: three to five case ids of the review Intent's development set, `evals/pr-review`, each once. The Maintainer picks them in seating the set. Each case is read as the development set names it, by its id and sha256, in the gate set's order. No other set names a preflight | The issue's: a few development cases, so that a broken pipeline shows on them. Their outcomes are told case by case in the development set's own reports already, so counting them here tells nothing new |
| None a gate set's | No preflight id is a case of the gate set itself (`held`), and no preflight case is a case of any gate set under `evals/`, by its id or its hash (`preflight_of`, at the plan and at every step after it). A development set that is a gate set, or of another Role or Intent, an id it does not name, or a manifest under `evals/` that cannot be read, is `eval_set_unreadable`; a case a gate set names is `eval_set_overlaps_a_gate_set`. `tools/check_examples.py` holds a gate set in `LIVE` to the same | The Builder's ruling: checked mechanically, not by convention. A held-out case asked as a preflight would have its outcome counted beside the set's |
| When | `plan` reads the preflight and keeps it; a development set changed after it is `eval_set_changed`. `fetch` reads its cases first, as it reads the set's, into the scratch's own folder of them; their heads beside the set's, by their ids. `run` asks them first, before any of the set's own, within the same budget | No new step and no new credential: `.github/workflows/eval.yml` is unchanged |
| What stops a dispatch | Before any of the set's own cases is asked, the dispatch stops if a preflight case was stopped by the Engine or the run (a code of `ENGINE_FAULTS` or `RUN_FAULTS`, a case not fetched among them), or if none of them passed (`preflight_stops`). Each of the set's cases is then `unanswered`, and the report is still written for the upload. A preflight case the reviewer missed, beside others it passed, stops nothing | The preflight weighs the pipeline, not the reviewer; the gate weighs the reviewer. A gate set is fresh for each Release and never replayed (issue 562, "A fresh held-out gate set for the Release after v0.1.0, never replayed"), so a pipeline broken partway spends no held-out case once its preflight has stopped it |
| A false stop | If each preflight case is passed 85% of the time, independently, a working reviewer misses all three about 0.3% of the time, and all five about 0.008% of the time. Five preflight cases make a false stop negligible, for the Maintainer to weigh in picking them | The Builder's ruling: the "none passed" stop stays, to catch a scorer that fails every case |
| What it reports | `eval-aggregate/1` gains `preflight`: its cases, how many passed and each code of one not read, by how many, counts alone. Nothing of it is in the set's counts, kinds, usage or pool. `eval-ledger/1` gains `preflight`: each case as the set's are listed, but for whether it is natural, with its Result, sealed with the rest | So that a stopped dispatch says why, by counts and codes alone, as the rest of the report does |
| How the gate reads it | `aggregate_verdict` holds the preflight's counts to the set's preflight (`count_differs` otherwise), and reads a report whose preflight should have stopped it as `preflight_failed`, whatever came after; the pool reads that as a faulted dispatch, `eval_dispatch_faulted`, and closes the commit. The judge's line says the preflight's counts and codes | The Release's gate needs nothing new: a stopped dispatch is faulted, as decision 0169 has it for the Engine's or the run's |
| Residual: a fault after the preflight | A pipeline that breaks only after the preflight has passed, partway through the set's cases, still spends the cases asked before it broke; the gate reads that dispatch as faulted, as before | The preflight shows a pipeline broken from the start, which is the common case; nothing short of asking each case can show the rest |
| Residual: a gate set no longer under `evals/` | The overlap is held against the gate sets under `evals/` at the commit, as `held_out` holds a development set's cases. A gate set whose manifest was removed after its Release, or one whose seating is still a pull request, is not among them, so its cases could be named in the development set and as its preflight. The preflight would tell only a count of three to five of them, where a development set's own report tells each (the security read) | Keeping every gate set's cases on a list that is never removed would close it for both, a change of its own |
| Residual: the preflight spends the run's time | Its cases are asked within the run step's budget, before the set's: a case of the set not reached in time is `unanswered`, and the dispatch is faulted, as for any run that runs out of time | Three to five cases are a small share of a run of forty or more |

## Why

A dispatch over a gate set spends held-out cases: the set is fresh for a Release and is never replayed. A pipeline that broke before or during the run (a credential gone, an Engine pin that no longer answers, a scorer that fails everything) would have spent a set on nothing, and its report would read as a reviewer that failed. Asking a few development cases first, whose outcomes are public already, shows a broken pipeline before any held-out case is asked, and says so by a code of its own. The stop is narrow: a fault, or not one case passed. A reviewer that misses some easy cases is the gate's to weigh, not the preflight's.
