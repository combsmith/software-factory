# NNNN. A gate set's gate pools every dispatch on the commit, under the set's own bars, and a development set stays the best of several

Status: accepted. The Factory Builder's ruling of 2026-11-08 on issue 613, "The gate pools k dispatches on one commit and reads all of them", approving lane d's design, defaults 1 to 7, and the Maintainer's condition on it, restated in decision 0164: a gate's bar applies to case-runs summed, and no automated process reads a ledger. It is the first of two pull requests under the issue; the preflight is the second. For a gate set alone, it amends decision 0150's rows "The bar", "Where it sits" and "What the bar does not hold", each where it fixes the bars in `harness/eval/__init__.py` or lets the gate take the newest dispatch that succeeded. A development set, and everything else in 0150 and 0164, are unchanged.

## Decision

| What | Decided | Because |
|---|---|---|
| Which set the gate reads | The gate set `config/harness.json` names, `gate_set`, read at the commit through the transport. Until it names one, the review Intent's set, `evals/pr-review`, as before. A name of more than one part, or a configuration not read whole, closes the gate, `eval_set_unreadable`, and so does a set named that is not a gate set, or the review Intent's read where none is named that is | No gate set exists yet: held-out v2 and the Maintainer's certificate are both to come. The pool lands now and acts when a set is seated. Neither `config/harness.json` nor `evals/` is a protected path: the first is an input of the review Lens, and its change needs a person's approval; the second is the `verify` Lens's alone, reviewed by the model Lenses (the security read) |
| What is pooled | A gate set's reports alone, `eval-aggregate/1`, whose counts of each kind can be summed. A development set's report holds no count of a kind (decisions 0094 and 0099), so its gate keeps reading the newest successful dispatch | Pooling a development set would put a count of a kind in its public report, which 0099 refuses |
| Which dispatches count | Every dispatch of `.github/workflows/eval.yml` on the commit that has completed, whatever it concluded, oldest first. One still running, or an answer that holds a run of another commit, workflow or event, or is not whole, leaves the commit unjudged, `eval_not_run`. One whose report names another set, by its count and the sha256 of its manifest, is another set's and not counted | So that no dispatch is passed over for a better one. Another set's runs on the commit are not this set's evidence |
| A faulted dispatch | Any dispatch on the commit, of whatever set, that concluded neither success nor failure (cancelled, timed out or skipped), or was run again (its `run_attempt` not 1), or whose report is not read whole or names no set by its count and sha256 alone; and a counted one whose report is unreadable to `aggregate_verdict`, or says a fault of the Engine or the run, closes the gate for the commit, `eval_dispatch_faulted`. A dispatch that failed only by its own run falling under the bar, `case_failed`, is no fault, and is pooled. A report of another commit or Release, or whose counts do not add up, closes it by its own code. A report-less dispatch of any set closes it too, as its set cannot be told. A dispatch run again is a fault, as the list shows a run's latest attempt alone (P-27, decision 0111), so that an attempt that faulted, or fell under the bar, would be hidden (the Claude review) | A failed or faulted run must leave a trace, or a rerun is the best of several. The bar is the pool's, so one run under it says nothing alone |
| How many | `POOL_LEAST`, three dispatches at least, every one pooled: a fourth adds to the pool and replaces none. Fewer is `eval_pool_short` | The issue's k = 3, and the evals-strategy review's case: one run of 40 cannot tell 85% from 95% |
| The pooled verdict | `harness.eval.pooled_verdict`: each report held whole by `aggregate_verdict`, each with its kinds read and its split held (`eval_split_short` otherwise); each kind's cases and passes summed over all of them, `pooled`, and each sum held to the set's bar, `case_failed` under it | The Maintainer's condition: bars apply to summed case-runs |
| The bars and the least of a kind | A gate set's manifest gives its own bars, `bars`, a whole fraction for each kind, and its own least of a kind, `kind_least`, and names its record, `record`. No other set gives any: a development set's are `BAR_OF_A_KIND` and `KIND_LEAST`. The job writes and the gate holds a gate set's report to its own (`bars_of`, `kind_least_of`), the fewest passes they allow read at every split of the kinds, as rounding can make a split between the ends ask fewer (Codex's read). A bar is of one case at least and asks no more than every case. Neither is under the development set's, `BAR_OF_A_KIND` and `KIND_LEAST`, as a whole fraction compared by multiplying: a manifest, which no person need approve, can raise the gate and not lower it (the security read). A record of its own may lower the floor | The issue's: the bars are the set's, not the code's, so that a new set can be seated with bars of its own |
| Where the bars are stated | The record the manifest names holds the sentence `harness.eval.bars_said` gives, word for word; `tools/check_examples.py` holds a gate set's manifest in `LIVE` to it. Nothing reads a record at run time. A set at the development set's floor says: Its bars: finding 3 of 10, met 9 of 10; at least 20 cases of each kind. An example of a manifest is held as the job reads it, `held`, and not by its schema alone | The Builder's ruling: a check holds the bars to the record, and no markdown is parsed in the job or the gate |
| The blocking word | Pooled, true only where every report's is. It closes nothing by itself, as decision 0150 has it | Unchanged from 0150. A rule that every run must pass every blocking case would overturn it |
| The preflight | A few development cases scored apart in each dispatch, so that a broken pipeline shows on them, is the second pull request under the issue | It changes the eval workflow and the run step, and is apart from the gate |
| Residual: a development set stays the best of several | `pr-review`, which gates v0.1.x until v2 is seated, is still judged by its newest successful dispatch. Re-dispatching on a commit until a run succeeds is still possible there, as decision 0150's row "What the bar does not hold" says, and only the Maintainer dispatches. The gap is closed only when a gate set is named | Written down, so that the gap is not silent (the Builder's ruling) |
| Residual: another set's faulted dispatch | A dispatch that uploaded no report cannot be told by its set, and the conclusion is read before the report, so a development set's dispatch on the same commit that was cancelled, faulted before its upload or run again closes a gate set's pool. That fails closed: the cut moves to a new commit |
| Residual: a run deleted | A writer can delete a run, and the list then holds no trace of it; the run number counts every commit's runs, so no gap shows. No App holds `actions: write`, so it takes a person who can write (the reads of this record) |
| Residual: who may change a gate set | A gate set's manifest is under `evals/`, which no person need approve, and the name of the set in `config/harness.json`, which one must. The floor holds the bars; protecting `evals/` is a change to `config/hooks.json`, the Maintainer's | Written down, so that the gap is not silent (the Builder's ruling) |
| Residual: seating a gate set | Naming one in `config/harness.json`, its manifest under `evals/` in `LIVE`, and its record, are each a change of their own, with the held-out v2 set | Written down, so that the gap is not silent (the Builder's ruling) |

## Why

The gate took the newest dispatch on a commit that succeeded. A failed or faulted dispatch left no trace, so re-dispatching until one passed made the gate the best of several runs: over three tries, a reviewer at 85% clears a bar of 90% about 60% of the time. Counting every dispatch, and summing the kinds over three at least, makes a pass the evidence of every run the Maintainer made, not of the luckiest. A fault closes the commit rather than being retried past. The bars are moved from the code to the set, so a set seated later carries the bars it was made for, stated in its record and held there.
