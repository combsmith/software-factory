# 0069. What a Lens recorded holds its threads, and gives each its category

Status: accepted. The Factory Builder's rulings of 2026-10-26 on "Threads port: a Lens's recorded Finding comment missing from the threads read leaves it unreadable" (issue 338, the second part of issue 331, "Threads port: a thread's resolver is read from its timeline event, by id and type (P-49)"): the thread and its opener in place of a comment id, the retention miss accepted, and option (a), that the issue builds `adapters/applied.py` and the join with it. The Maintainer may overturn it in review. It holds what decision 0067 left open, a thread whose first comment was deleted, and builds the join decisions 0015, 0018, 0022, 0026 and 0038 waited on.

## Decision

| What | Decided | Because |
|---|---|---|
| What a Lens recorded | `adapters/applied.py` reads the `applied/1` of every completed Run of a model Lens on an open pull request of the home repo, whatever its conclusion, by the GitHub run its run-name names: the records port hands each Run id's GitHub runs beside its list, and a Run named by none or by two is not read. Each Finding it posted on a thread is kept by the thread's id, its surface key | `applied/1` records a posted Finding as `finding/1`, whose surface is the thread; no run record holds a GitHub run id, and a write may land before a later one fails |
| The thread and its opener | Every thread a Lens recorded must be in the threads read and still opened by that Lens, told by its account (decision 0067). A recorded thread that is missing, or opened by anyone else, leaves the threads read not whole, and the Kernel defers. No comment id is kept, and `finding/1` does not change | GitHub keeps a thread's id when its first comment is deleted and reads its reply as the first (`trials/P-49.json`), and keeps no link from the reply to the comment (`trials/P-53.json`): a person's reply after a deleted Lens comment would read as the person's thread |
| The Lens's own reply | A thread whose first comment was deleted after the Lens itself replied is still the Lens's: whole, and it gates on its Finding. The comment's text is lost, and the thread is read at its reply's time | The opener is the Lens, by its account; the Finding it recorded still names the thread |
| The join | A Lens's thread takes its category and severity from that Lens's one Finding on it, never from its text. A thread its Lens recorded no Finding on, recorded two on, or whose Finding names a category the authority table gives that Lens no ownership of, has neither: the Kernel defers on a required Lens's open thread, as it did before. A thread two Lenses recorded is no one's, and leaves the read not whole | Fail closed (I-13): a category taken from a wrong Finding could hide a gate. The authority table says who owns each category (section 3.8) |
| What gates | Once this lands, a Lens's Finding gates by its category and severity for the first time: before it, every required Lens's open thread had neither, and deferred its pull request | The Maintainer should see the change in behaviour |
| What cannot be read | A run list read short, an `applied/1` that cannot be read, nested deeper than Python parses, is another Run's or holds another Lens's Finding on any surface, and an artifact list that does not answer, leave that pull request's threads not whole. One pull request's record that cannot be read leaves the others as they are, and ends no pass | What cannot be read is never read as none |
| A deleted record | A Lens Run that succeeded uploaded its `applied/1` whatever it wrote, so one that lists none was deleted, and leaves the threads not whole; one listed late, just after its Run completed, reads the same until the next pass. A Run that did not succeed may have uploaded none, and is read as recording nothing | Deleting the artifact, which a writer can, would otherwise undo the opener rule (the security pass on this record) |
| A deleted comment's cost | A Lens comment deleted whole, its thread gone, leaves the pull request's threads not whole until the record that names it is past retention, even if the thread had been resolved. No read tells a thread resolved before it went. The Factory Builder ruled to keep it so for now (option (a)); "Applied port: a later review by the same Lens supersedes its earlier records for a thread that is gone" (issue 347) lets a fresh review release it. A person's label is not taken as an override: who may apply one needs its own decision (decisions 0052 and 0061) | Fail closed: a thread that is gone cannot be told closed |
| Retention, the accepted miss | An `applied/1` past the artifact retention is read as recording nothing, as an expired outcome is (decision 0049). The retention is 90 days, read from the repository's and the org's Actions settings on 2026-10-26. The stale rule only marks a pull request's attention, and never closes or holds one, so a pull request can outlive the window. Then a recorded thread deleted whole goes unmissed, and an open Lens thread has no category, so a required Lens's defers until a person resolves it. "Kernel: a Lens review whose applied/1 is past retention on an open pull request is asked for again" (issue 346) asks for a fresh review instead | The ruling: never read as whole by default; a read that fails for any other reason stays unreadable |
| Where it is read | Wherever a snapshot is: the pass, the Run's read step and `apply`'s read again. The snapshot takes what the Lenses recorded as a required argument, so no caller can leave it out. Each reads its Lens Runs' artifacts with the token it lists runs with. The pass's and the read step's Apps hold `actions: read`; the read step lists runs for the first time here. `apply`'s read again uses the pr-review App's token, which `config/apps.json` grants no `actions` permission: its run list and the pass record, read before this record, and now these artifacts, are refused there until the Maintainer grants it, and `apply` then writes nothing, failing closed. The approving act reads them with the machine user's token, which must be able to read the repository's Actions artifacts, or the approval defers | A Task built on, or a write made after, a threads read the pass would not take is refused alike |
| The cost | One small download for each completed Lens Run on each open pull request, each pass, bounded as an outcome's is | Accepted by the ruling |
| A re-run | A Run re-run lists one `applied` artifact for each attempt that uploaded one; two of the name are not read whole, as two outcomes are not (decision 0049). Not verified on GitHub | The Maintainer may want a trial; until then a re-run Lens Run's pull request defers |

## Why

`adapters/threads.py` reads a thread's opener from its first comment, and GitHub gives that comment's place to its
reply once the comment is deleted. Comparing against an earlier pass's read would keep state between passes and miss
a deletion made before any pass saw the comment. The Lens's own record, which `apply` writes from what it read back,
is the one source that says which threads are the Lens's, and it is read at every pass. The same read is what the
join needed, so one port reads both.
